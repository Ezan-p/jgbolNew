# 神石祈福实现与调试说明

更新日期：2026-10-26。入口为「活动 → 奇闻 → 神石祈福」，15级开放，原生界面为 qiFuUI。本次补齐魂魄／神仙献祭、元宝奖励、费用显示、留存魂元与连续祈福，并验证真实协议和原客户端界面。

## 1. 当前玩法

1. 点击“祈福”，选择魂魄或二、三星闲置神仙；可以混合选择。
2. 已选祭品价值加上上次留存魂元，达到本次费用后可确认。
3. 确认后一次性消耗所选祭品，扣除本次魂元费用，剩余魂元永久留存，并获得一份元宝奖励。
4. 领取展示完成后可继续祈福；魂元结余足够时，不必再选祭品。

| 项目 | 规则与来源 |
| --- | --- |
| 第一次费用 | 200魂元，原CSV |
| 第二次费用 | 500魂元，原CSV |
| 第三次及之后 | 1000魂元；原客户端超出CSV范围时使用最后一行，本地据此不设每日三次硬上限 |
| 每日重置 | UTC+8零点后，下一次按第一次费用计算；沿用本地活动日切策略 |
| 元宝奖励 | 每次从10、20、30元宝中等概率抽取一档；奖励种类有原版依据，金额与概率为离线推定 |
| 其他消耗 | 不额外扣元宝、银币、体力或精力 |
| 取消选择 | 不消耗任何物品；服务端确认成功后才扣除 |
| 高等级神仙 | 原版对2级及以上神仙弹二次确认；允许确认后献祭，养成材料不返还 |

原界面选中魂魄时提交该条目当前显示的整组数量，没有新增数量输入框。多交的魂元保留，可以用于后续祈福；服务端严格校验提交数量不超过库存。

### 祭品价值

直接读取 [cortege_quality.csv](../analysis/configs/cortege_quality.csv)，不另行拟造换算比例。

| 星级 | 每个魂魄的魂元 | 每个神仙的魂元 | 可用范围 |
| --- | --- | --- | --- |
| 一星 | 0 | 0 | 拒绝零价值祭品 |
| 二星 | 1 | 4 | 魂魄、闲置神仙 |
| 三星 | 2 | 18 | 魂魄、闲置神仙 |
| 四星 | 4 | 0 | 仅魂魄，可手动选择 |
| 五星 | 8 | 0 | 仅魂魄，可手动选择 |

“全选2、3星魂”不会选择四、五星魂魄；神仙列表沿用原版的星级、上阵和助威过滤。锁定、待处理培养结果或携带非天生绑定物品的神仙由服务端拒绝；应先解除对应状态或卸下精魄。四、五星神仙不得献祭。

例如首次交入26个五星魂魄，价值208魂元：消耗200，留存8。首次交入二星神仙1名、三星神仙1名和原有178魂元，则正好达到200。

## 2. 本次修复的关键问题

### 原生魂魄对象类型写错

原版 object_type.spirit=10，object_type.calc=7。旧服务端和旧测试都用7作为魂魄，导致测试能过、真实客户端却无法提交魂魄祈福。

现以原版10接收魂魄，4接收神仙，拒绝7及其他无关类型。协议仍使用1085，没有修改APK或请求结构；旧测试同步改为真实枚举，并增加原始枚举核对。

### 所有带天生法术的神仙被误拦截

formation.prepare 为每位神仙维护天生法术，其 owner_id 和 innate_owner_id 均指向神仙。旧祈福逻辑拒绝任何有 owner_id 绑定的神仙，实际把天生法术也当成了“尚未卸下精魄”。

现明确区分：天生法术允许存在，成功献祭时与所属神仙一起删除；精魄及其他非天生绑定物品仍要求先卸下。不会遗留孤立法术，也不会删除其他神仙的装备或法术。

### 奖励与原版说明不符

原版说明图明确写的是获得元宝，旧配置却奖励包子、召唤符或精力道具。现改为货币类型11，通过统一奖励函数直接增加 gold_coin，事件52中的奖励弹窗与实际到账数相同。

默认金额10／20／30及等概率分布没有找到官方服务端依据，属于推定，集中配置在 [activity_rules.json](../server_config/activity_rules.json) 的 pray_rewards 中。加载时校验该奖池只能包含元宝。

### 费用显示与实际扣费不一致

本地 pray_spirit_times 存储“今日已成功次数”，从0开始；原版界面直接用该值索引CSV，未找到索引时落到最后一档。因此旧界面首次会显示1000，第二次显示200，而服务端实际依次扣200、500。

[pray_client.lua](../network_redirect/pray_client.lua) 在打开选择窗口时，把原CSV映射为已完成次数0→200、1→500、2及以上→1000。显示、可确认判断与服务端一致，不预扣资源、不篡改玩家次数。补丁支持重复安装和卸载恢复，随现有 summon.client_source 注入链加载。

费用表有三行并不直接证明每日只能祈福三次。原客户端的表尾回退提供了继续祈福的实现依据，本地取消旧硬上限。**官方服务端是否另有限制仍无法确认**；本地行为已在此明确列出。

## 3. 结算、存档与异常处理

主要实现位于 [activity_pray.py](../network_redirect/activity_pray.py)，由活动路由调用。

- 先校验等级、类型、编号、数量、去重、持有量、神仙状态及魂元，再统一扣除并发奖。
- object_count 必须与列表长度相符，最多255项；神仙每项数量只能是1。同一祭品重复提交、未知对象、负数／零数量、魂元不足均拒绝。
- 只使用服务端库存、原CSV和留存魂元计算结果，不接受客户端提交的价值、费用或奖励。
- 成功后更新角色次数、魂元、元宝、神仙／法术列表及魂魄快照，再发送奖励事件。
- Backend在角色副本上执行，响应编码成功后提交SQLite；业务失败或编码失败不残留扣除或奖励。
- spirit_retain 和 pray_spirit_times 继续使用既有存档字段，无需重建角色。旧版已发道具不追缴，也不补发历史元宝。
- activity.pray_total 记录本版累计成功次数，用于成就109“天降鸿福”；跨日时今日次数下降也不会漏记首次成功。
- UTC+8日切只重置次数，不清空魂元；回到已处理日期之前的请求会被拒绝，避免恢复廉价档位。
- 留存魂元与元宝的结果不得超过有符号32位协议范围，溢出时不扣物品。

同一服务会话中相同请求序号与内容使用Backend缓存，重放不重复消耗；过期序号拒绝。**服务重启后的库存和次数会恢复，但请求缓存本身不持久化**，不能把旧请求跨服务重启重放的幂等性视为已保证。普通客户端重连使用当前状态发起新操作。
