# VIP 模块规则与调试

本文对应金箍棒 3.87 原客户端、本地离线服务。2026-10-24 修复。**【A】表示原包 CSV、Lua 字节码或协议能够确认的规则；【B】表示缺失原服务端后采用的推测与本地实现策略，不代表官方数据。**

## 实现范围

VIP1～VIP10 页面、左右翻页、充值进度、特权文案、礼包预览、逐级领取、礼包开包、每日灵玉／元宝福利、VIP 乾坤袋、模拟充值升级，以及关联玩法的 VIP 次数与门槛。

充值经用户明确授权采用本地模拟：从 VIP、集市或仙灵店铺点击充值，选择元宝档位，即可到账与升级。页面标明“不扣款”，不会调用渠道支付。2026-10-26状态复核：真实支付与月卡购买仍未接入；福利首充奖励已通过 `1201/flag=6` 接入，充值页的 `pressFirstCharge` 专用活动按钮仍被补丁拦截，不能统称所有首充功能未实现。仙灵店铺已在后续扩展中修复，原版与推定规则及验证见 [仙灵店铺与集市模拟充值](仙灵店铺与集市模拟充值.md)。邀请好友 VIP 奖励未接入。

当前订单只覆盖 `1111/event_id=250` 本地模拟充值，以及福利处理器的 `1112/event_id=3,item_id=8` 成长基金；其他事件须单独接入。召唤的 `paid_daily_limit` 仍由各VIP共用，未按等级区分付费日限。完整剩余范围及本次静态复核边界见[当前功能差异清单](当前游戏与原版功能差异及未实现模块清单.md)，下文原测试数字保留其历史含义。

证据均保留在项目中，可直接复核：

【A】每日福利要求有可领取灵玉，并且 `take_vip_gold_time` 已跨日。VIP1～3 的文案为灵玉，VIP4 起包含元宝及灵玉。具体金额由服务端下发，不在原版文案中写死。

【A】礼包领取要求当前等级不低于目标等级，且 `vip_gift` 对应位未领取。VIP n 使用 `1 << n`，第 0 位保留。领取给一个相应礼包道具，开包才发礼包内奖励。原客户端会继续请求下一档未领礼包，服务端逐次校验。

【A】配置中的 `charge_gold` 供部分等级页展示门槛；`next_charge_gold-charge_gold` 是升级差额，负值按 0 展示。原字节码另有 VIP1～6 的后备数组及地区换算，但服务端配置优先；不能把后备展示数组当成已恢复的官方升级表。

【A】`day_pick_cortege_limit` 是按召唤档位索引的表，不能下发为单个整数。本次沿用现有召唤配置的各档付费日上限，不改变召唤概率。

## 【B】缺失服务端配置与推测规则

### 升级与每日奖励

主配置：[server_config/vip_rules.json](../server_config/vip_rules.json)，明确标记 `mode=inferred`。累计模拟充值元宝决定 VIP，消费元宝不降级；已有本地存档的 VIP 等级不主动降低。最高 VIP10，继续充值仍到账，不创建 VIP11。

| VIP | 累计充值元宝门槛 | 每日元宝 | 每日灵玉（道具1140） |
|---|---:|---:|---:|
| 0 | 0 | 0 | 0 |
| 1 | 100 | 0 | 10 |
| 2 | 500 | 0 | 20 |
| 3 | 1000 | 0 | 30 |
| 4 | 2000 | 20 | 40 |
| 5 | 5000 | 30 | 50 |
| 6 | 10000 | 40 | 60 |
| 7 | 20000 | 50 | 80 |
| 8 | 50000 | 60 | 100 |
| 9 | 100000 | 80 | 120 |
| 10 | 200000 | 100 | 150 |

【B】六档模拟充值为 100、500、1000、5000、10000、50000 元宝，无首充倍赠。采用独立离线操作 `1111/event_id=250`，这是本地扩展，不冒充原版支付事件。商品金额仅从服务端配置读取，忽略客户端伪造金额。

【B】每日按 UTC+8 零点重置。领取后当天升级不补差额，不再次领取。离线错过的福利不补发。领取时间、礼包位图与充值订单写入 SQLite 存档；同订单重发、断线重试或重启后重发均不会重复到账。相同订单号变更商品会被拒绝。

### 普通账号额度和迁移

【B】旧离线配置曾对所有账号给予较高固定额度，造成 VIP1 反而少于普通账号。本次普通账号设为：包子／仙丹各 3 次、普通关卡刷新 0 次、封神榜 5 次、渡劫免费刷新 3 次、天缘总次数 1 次、免费占星 5 次、付费购买占星 0 次。分别保存在 `journey_rules.json`、`activity_rules.json`、`reborn_rules.json`。VIP1 起采用上表。

【B】天缘道具次数解释为免费首挑战以外的次数，因此下发总次数为“上表道具次数 + 1”，月卡再按原客户端规则加 1。该解释同时满足原版特权文案和首次免费分支；原服务端总次数配置未取得。

【B】包子／仙丹购买与背包使用沿用现有服务共用每日计数；客户端只有对应的一组计数，是否曾由官方服务端另设隐藏计数无法确认。

【B】升级保留已经用掉的挑战次数，剩余量由新上限减已用量计算；占星在已建立当日记录后升级，增加新旧上限差额。旧存档没有占星额度版本标记时，保留当日剩余量和待领命星，次日按新额度重置，不猜测扣除以前已付费购买的次数。

### VIP 乾坤袋

【A】VIP1门槛、道具编号1031、单次最多15个来自原客户端。2026-10-26按用户提供表格将四种乾坤袋统一为12个品质池：VIP低／中／高概率65%／30%／5%，再按类别权重和具体模板等概率抽取。旧5项VIP池已移除。

完整数量、所有候选ID、单项概率、离线随机技术和验证见[四种乾坤袋概率池实现说明](四种乾坤袋概率池实现说明.md)，有效配置为`server_config/qiankun_bag_rules.json`【B用户设计】。VIP高档包含全部五星武器、防具、主动法术及低权重法宝、被动法术、大乘经；碎片每次5个，装备／法术／召唤符每次1件。

不设隐藏保底。扣袋、发奖和存档使用既有事务边界。礼包1101～1110继续按原CSV固定内容发放，不使用乾坤袋奖池。

## 修复点与验证

- 补齐原版配置类型1，包括等级页必需的 `charge_gold`、福利数值和按档位索引的召唤上限。实机回放曾捕获 `tmp_money=nil`，补齐后十档翻页通过。
- 接入1201的VIP分支，避免落入其他玩法或“未实现”处理；先发背包／属性更新再执行原版领奖回调。
- 旅途、封神榜、渡劫、天缘、占星改用VIP对应额度，修正服务端显示与实际校验不一致。
- 本地充值适配器只在离线模式安装，可恢复原始回调；原版VIP页面、礼包预览和领奖逻辑保留。
- 编码所有奖励响应后才保存；奖励溢出或编码失败不会扣物品、消耗领取机会或记为已充值。
