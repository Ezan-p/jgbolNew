# 仙盟交互问题修复说明

日期：2026-10-25。适用客户端：金箍棒 OL 3.87；本仓库离线后端。

## 修复内容

### 秘境申请同意失败

原客户端 `secretAreaUI.showJoinTeamPage` 会遍历 `apply_list`，将表的键写回每条申请的 `id`。此前后端返回顺序列表，真实角色 ID 被覆盖成 1、2、3，导致点击同意后返回“申请不存在”。

查询申请（事件 50）和队伍信息内的 `apply_list` 现在统一使用数字角色 ID 作键；存档中的字符串键在发包时转换，旧存档无需迁移。单选/多选审核继续校验实际申请、队长权限、队伍容量；重复同意不会重复加人，拒绝和清空同步更新待审批表。

### 查看对阵失败、闪退

已在原客户端复现原生崩溃。模拟器日志显示加载 `v2/abyssUI/level/z-19.png` 失败，随后进程收到信号 11。

当前 `guildFightUI.showNewAgainst` 使用 `match_type - 20` 生成赛段图片编号；此前返回旧枚举值 1，会生成负数图片名。现代入口和对阵查询统一返回离线赛段 21（图片编号 1），报名状态继续由 `has_match_flag` 和后端状态控制。旧押注专用接口保留其旧协议枚举。

同时补齐对阵双方的 `leader_id`、`match_type`、`level` 和查询中的 `bet_list`、`bet_time_info`，保留分组 6、7 的对阵数组，供两个分组页及详情读取。详情页提交本方盟主角色 ID 时映射回本方仙盟 ID；已下注目标按盟主 ID 回显，开战/结算后关闭押注时段。离线赛段值是兼容当前 UI 的推测设置，不代表官方线上赛程。

### 神树不能捐赠

原客户端 `worldTreeUI.createDonateLayer` 直接计算 `数量 × donate_rate`；缺少该字段会中断捐赠窗口。神树信息和捐赠成功响应现在均返回配置中的 `donate_money_rate`。

默认每捐献 1 元宝增加 10 仙盟资金、1 贡献、1 人气，每日上限 100 元宝；校验和扣款仍由服务端完成。原客户端保留 36 级或 VIP 大于 0 的入口条件，低等级非 VIP 角色会收到条件提示。

### 取消创建次数限制

移除每日只能创建一次的校验。同一天解散后可以再次创建，旧存档中已有 `create_count` 不会阻止创建，该字段仅继续记录次数。仍须满足创建等级、名称规则、元宝费用和当前未加入仙盟等条件；申请、加入仙盟次数限制不变。

## 历史修复：秘境全选申请误报满员（人数判断已纠正）

2026-10-25 用户进一步反馈同意申请显示“队伍已满”。检查现场存档，队伍只有队长一人，申请表有三个 NPC；日志连续记录事件 28 被拒绝。上轮回归只验证单个申请，漏掉了多选数量大于空位的场景。

当时改为：所有申请先通过身份、重复 ID、队长权限等校验，再按本次提交顺序接纳剩余名额允许的人数。当时错误地保留了三人上限，仅接纳两人。此判断已被下节的“五人上限、三人起战”修复取代。不会扩大人数上限或扣除未接纳的申请。

满员时，队伍信息与申请查询都返回空的可审批名单；内部候补记录仍保存。移除一名成员后重新打开申请名单即可继续接纳候补。修复前已保存的三人申请表可以直接使用，无需解散队伍或修改存档。

新增回归覆盖三申请/两空位、满员隐藏、腾位后再审批、非法和重复 ID 的原子回滚。仙盟测试共 54 项通过；原客户端回放增加三名申请全选及满员后的队伍/申请表断言。

原客户端 74 步回归全部通过，已恢复原角色和配置引用。证据：`analysis/evidence/guild/team_capacity_validation.json`。本轮未重跑全量测试，以上 360 项为上一轮结果。

## 规则纠正：五人上限、三人起战（当前有效）

此前把三人作为队伍上限是不正确的，之前的测试也沿用了这个错误预期。现以用户确认的五人上限及原客户端的起战检查分别实现：

| 规则 | 证据与实现 |
|---|---|
| 上限为 5 人，包含队长 | 用户确认。原客户端 `getTeamsInfo`（约 195 行）、`onGetTeamsList`（约 871 行）读取服务端 `max_count`；队伍列表约 405 行显示 `count / max_member_count`。后端 `team_size` 改为 5，配置校验不再错误限制为最多 3。 |
| 至少 3 人才能开始 | 原客户端 `pressFight`（1147–1161 行）收集队员 ID 到 `fight_list`，不足 3 人时显示 `secretArea_figther_less_3` 并直接返回；3 人及以上发送事件 41。后端新增 `team_min_fighters=3` 独立校验，禁止 1、2 人绕过客户端发包开战。 |
| 3、4、5 人均可挑战 | 服务端校验实际队伍人数、出战名单完整性、重复/非本队 ID；通过后才模拟战斗、扣次数和发奖励。保存客户端提交的队员顺序，供后续查询使用。此修改不重写离线战斗算法。 |
| 只有 5 人才算满员 | 三名申请加队长是 4 人，全部接纳；第 5 人仍可加入。超过空位的批量申请按提交顺序接纳到 5 人，余者候补；满员隐藏可审批名单，腾位后恢复候补。 |

旧队伍和候补无需删除或重建，重新查询即使用五人上限。上述数字不改变 `team_daily`（每日挑战次数）或探宝次数，两者是不同规则。

验证新增 1/2 人拒绝、3/4/5 人允许、6 人拒绝、第五人接纳、满员候补、重复/伪造/缺失名单回滚。`test_nested_battles` 使用真实五人队执行离线模拟；原客户端回归检查三申请全选后四人、第五人接纳，以及原 `pressFight` 在 2/3/4/5 人时的实际请求行为。

本轮验证：57 项仙盟测试、437 项全量测试、原客户端 77 步回归全部通过，原角色和配置引用已恢复。证据：`analysis/evidence/guild/team_rules_validation.json`。
