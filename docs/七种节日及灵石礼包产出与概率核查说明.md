# 七种节日及灵石礼包：奖励池实现与概率明细

更新日期：2026-10-28。当前配置版本：`2026-10-28-seven-gifts-user-pools-2`。

**七种礼包已按用户提供的两张图实现：固定项全部必得，并在此基础上额外随机抽取一项奖励。** 奖励表中的数量表示一次中奖发放该数量，不是再从该数量中选1个。批量开启N包，固定项发N份，额外独立抽N次；没有空奖、保底计数或充值加概率。

本次更新替换此前的“银币10000＋蟠桃10”通用配置，以及上版文档中未实施的建议池。原包身份／历史附件属于原版证据；本次奖励范围、数量与灵石概率来自用户图片，银币数量及其他概率是离线设计值，均不冒充原服概率。

## 4. 概率与期望产量说明

设额外奖项概率为p，一次命中给n件，则每包的期望额外产量是 `p×n`。连续N包至少命中一次的概率为 `1−(1−p)^N`，不是 `N×p`；大金卡1%并不代表100包必出，100包至少1次约63.40%，仙缘果2%开100包至少1次约86.74%。

| 礼包 | 每100包固定产出 | 额外奖励示例的数学期望 |
| --- | --- | --- |
| 春节／新年，各自100包 | 银币1000万＋蟠桃10000 | 直接元宝18000；小卡54张；大卡1张；超级召唤符55；高级召唤符200 |

这些是长期期望，不是单批100包的保底结果；金卡尚未使用时，不能计入“直接元宝”。选择概率时使常用补给、低阶材料更常见，稀有卡和高阶材料更少；没有礼包售价、投放量等依据，因此不宣称完成原服付费价值还原。

## 5. 实现方式与兼容边界

- [item_reward_rules.json](../server_config/item_reward_rules.json)：七项切换为 `mode=fixed_random`，`prizes` 保存固定列表，`pool` 指向各自 `seasonal_ID` 额外池。其余礼包保持既有配置。
- [item_rewards.py](../network_redirect/item_rewards.py)：兼容原有 `fixed`／`random`，新增固定＋随机结算。每消耗1包独立调用1次抽样；相同对象、ID、等级汇总数量，不合并不同等级。
- 通用每批1～15包，仍只扣请求指定的实例，不自动跨堆叠取包。所有随机结果先确定、货币上限先校验，再扣包发奖；沿用后端副本结算、编码成功后保存及会话请求重放保护。
- 容器产出仅开放图片要求的单向许可：`1085→1249`、`1086→1031/1032/1033/1034`。其他来源仍不能利用共享池绕过许可，也不允许奖励本礼包或循环生成礼包。
- 等级2～4仅对`1205→1090/1091/1092`开放。其他奖品仍要求实例等级1，不放宽任意材料／装备等级。
- 沿用现有类型化发奖器：不可堆叠灵石每颗独立实例；1级固定石与1级额外石数量可在奖励摘要汇总，背包仍为独立实例。元宝、银币分别计入对应余额。
- 五法界魂箱、乾坤袋、金卡、仙缘果仅作为背包奖励，不自动触发二次开启、兑换或充值。
- 本次只调整开启规则，没有增加商城上架、免费领取或活动投放，没有补发历史已开启礼包。原版CSV和APK未修改。

Python开箱逻辑已更改，现有本地服务需重启后使用新实现；之后配置文件在开启时读取。无需重打APK。本次未主动中断用户正在运行的服务，也未宣称已验证正在运行的进程版本。
