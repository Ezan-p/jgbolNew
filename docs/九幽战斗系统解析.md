### 2.2 关键状态

| 字段 | 含义 | 说明 |
|---|---|---|
| `cur_layer` | 当前挂机层 | 玩家可更换；决定挂机掉落与主界面背景 |
| `boss_layer` | 当前挑战层／最高解锁层 | 战胜后 +1；第 81 层胜利后标记通关 |
| `crystal_count` | 魂晶 | 挂机与 Boss 奖励产出，九幽商店货币 |
| `fight_boss_times` | 当日已挑战冥仙次数 | 上限 `max_fight_count=5` |
| `max_fight_count` | 当日冥仙挑战上限 | 客户端兜底 5 |
| `event_count` | 当前排队随机事件数 | 上限 5 |
| `tool_rate` / `tool_end_time` | 双倍挂机倍率与结束时间 | 不影响 Boss 战斗本身 |
| `pills` / `use_pill_list` | 药槽 → 药品 ID | 1—4 普通，5—6 精魄 |
| `reductions` / `pill_list` | 普通药对四维的累计减益 | 攻击／防御／气血／灵力 |
| `complete` | 是否已通关九幽 | 第 81 层胜利后置位 |

【A】客户端的 `specter_data` 同时读取 `cur_layer`、`boss_layer`、`crystal_count`、`event_count`、`tool_rate`、`tool_end_time`、`fight_boss_times`、`max_fight_count`；Boss 界面用 `boss_layer` 取立绘，用 `cur_layer` 取主界面背景。参见 `abyssUI` 的 `showBossLayer` 与 `specter_info` 读取。

### 2.3 挂机层与挑战层的关系

- **【A】规则**：玩家可更换挂机层；每层都有冥仙守卫；战胜冥仙才能前往下一层。
- **【A】客户端**：`boss_layer` 用于 Boss 立绘与挑战层显示，`cur_layer` 用于当前挂机层背景；`change_area` 请求改变的是挂机层。
- **【B】本地实现**：`s['layer']` 是挂机层，`s['boss']` 是挑战层；`change_area` 只改 `s['layer']`，且要求目标层 ≤ `s['boss']`；Boss 战使用 `s['boss']`。
- **【待证／客户端怪癖】** `abyssUI` 在精魄面板里用 `boss_extSkill[cur_layer]` 取精魄，而 Boss 立绘用 `boss_layer`。当挂机层与挑战层不同时，精魄展示可能与实际挑战层不一致。当前本地在 Boss 响应中把 `specter_info.cur_layer` 设为 `boss_layer`，以便客户端取到挑战层精魄，但这会与“挂机层”字段语义冲突，属于【B】兼容处理。

### 2.4 每日重置与持久化

【B】当前本地规则：

- 每日零点重置 `boss_count`、商店购买次数、挂机统计、随机事件完成数。
- **药效不因每日重置而清除**：已上的普通药／精魄药会保留，直到胜利或替换。
- 挂机层、挑战层、魂晶、背包、宝图、事件队列持久化。
- 随机事件的答案、累计伤害与次数持久化。

这些重置边界在原包中只能看到客户端字段，不能证明原服一定如此；标为【B】。

### 3.4 冥仙有没有主动法术？【待证】

这是九幽战斗最关键、也最容易被误实现的一点。包内同时存在以下事实：

1. 【A】`specter_cortege_base.csv` 的 236 行 `chushijineng` **全部为 0**；而普通 `elite/elite_cortege_base.csv` 的 `chushijineng` 大量非 0（如 210、207 等）。
2. 【A】`specter_boss_config.csv` 的 `cortege_list` 第二列字段名是 `skill_level`，本表全部为 1；如果 Boss 完全没有技能，这一列在语义上是空转的。
3. 【A】`specter_cortege_base.base_type_id` 指向原角色；例如第 81 层 `908101 → 5046 元始天尊`，而 `cortege_base_0.csv` 的 5046 原生技能是 `206 千光斩`（强度 145 + 31×(等级−1)，触发率 15%）。
4. 【A】33 行冥仙的 `base_max_magic` 大于 1000，最高为第 81 层 36,000,100；如果这些灵力参与法术伤害，将形成极高爆发；如果不参与，则这些数值在当前战斗中没有用途。

由此有两种合理解释：

| 解释 | 含义 | 对战斗的影响 |
|---|---|---|
| A. `0 = 无主动技能` | 冥仙只使用普通攻击 + `ext_skill_list` 精魄 | 灵力列基本闲置；高灵力是历史／占位数据 |
| B. `0 = 继承 base_type_id 的原生技能` | `cortege_list` 的 `skill_level` 用于设置继承技能等级 | 冥仙会释放千光斩等法术，高灵力直接转化为高额法术伤害 |

**当前本地实现采用 A**：`activity_abyss.enemies()` 只在该行 `chushijineng` 属于 `skill_base` 时加入技能；由于全为 0，冥仙只有普攻。该选择标为【B】，不是已证实的原服行为。

**建议验证**：抓取高层（尤其 81 层）的 `1027.fight_result[].skill_type`。若出现 `206` 等主动技能 ID，则解释 B 成立；若始终只有 `1`（普攻），则解释 A 成立。同时观察 `damage_list` 是否与“高灵力 + 法术公式”吻合。

## 4. 冥仙精魄系统

### 4.1 配置格式

### 4.4 精魄的作用范围【待证】

`ext_skill_list` 是**层级**配置，不是单位级。包内能确定的是客户端按层展示一套精魄；不能确定的是服务端把它挂给谁：

| 解释 | 说明 | 本地实现 |
|---|---|---|
| A. 只挂给主冥仙（通常 order=1） | 随从只有基础四维与普攻 | 否 |
| B. 挂给该层所有敌方单位 | 4 个单位都获得破甲／格挡／复活等 | **是** |

当前 `activity_abyss_combat.battle()` 对 `side_index==2` 的每个单位都执行 `u['extras']=effect_values.copy()`，即解释 B。若原服只给主冥仙，4 单位层的实际难度会被本地高估。

**验证方法**：

1. 抓取 `121` 事件中 `who_use`、`src_order`、`des_order`；愈合／吸血／复活事件只从 order=1 出现，则支持 A。
2. 观察 `1027` 中随从的伤害是否出现破甲后的递增、格挡后的减伤；若随从也享受，则支持 B。
3. 对同一层反复挑战，比较主冥仙与随从的复活次数。

在证据出现前，文档不把 B 当作原版结论。

## 5. 药品削弱系统

### 5.1 六个药槽

【A】`abyssUI` 的 Boss 用药界面有 6 个槽，其中：

| 槽位 | 类型 | 可放药品 | 作用 |
|---|---|---|---|
| 1 | 普通 | 攻击药 | 降低冥仙全队攻击合计 |
| 2 | 普通 | 防御药 | 降低冥仙全队防御合计 |
| 3 | 普通 | 气血药 | 降低冥仙全队气血合计 |
| 4 | 普通 | 灵力药 | 降低冥仙全队灵力合计 |
| 5 | 精魄 | `specter_extr_skill_drug` | 降低指定精魄效果 |
| 6 | 精魄 | `specter_extr_skill_drug` | 降低指定精魄效果 |

【A】请求字段是 `index`（药槽 1—6）与 `type_id`（药品 ID），不是 `item_type`。客户端按 `isJp` 区分普通药与精魄药：普通药进入 1—4，精魄药进入 5—6。

### 5.2 普通药品

【A】`specter_pill_config.csv` 的 `decrease_list` 格式为 `属性|数值|是否百分比`：

- 属性：`1` 攻击、`2` 防御、`3` 气血、`4` 灵力。
- 本表 144 行全部 `israte=0`，即**固定值减益**，不是百分比。
- 四类各 36 档；ID 不是简单连续的 1—36，而是分段：

| 槽 | 属性 | 36 档 ID | 数值范围 | 规律 |
|---|---|---|---|---|
| 1 | 攻击 | 1501—1520、1581—1584、1601—1604、1621—1624、1641—1644 | 10,000—360,000 | 每档 +10,000 |
| 2 | 防御 | 1521—1540、1585—1588、1605—1608、1625—1628、1645—1648 | 3,500—126,000 | 每档 +3,500 |
| 3 | 气血 | 1541—1560、1589—1592、1609—1612、1629—1632、1649—1652 | 140,000—5,040,000 | 每档 +140,000 |
| 4 | 灵力 | 1561—1580、1593—1596、1613—1616、1633—1636、1653—1656 | 3,600—9,148,000 | 前 12 档 +3,600，之后非线性跃升 |

示例：

- `1501: 1|10000|0` = 攻击 −10,000。
- `1520: 1|200000|0` = 攻击 −200,000。
- `1644: 1|360000|0` = 攻击 −360,000。
- `1541: 3|140000|0` = 气血 −140,000。
- `1652: 3|5040000|0` = 气血 −5,040,000。
- `1656: 4|9148000|0` = 灵力 −9,148,000。

由于是固定值，低层冥仙的四维较低，高等药可能直接把某一项压到接近 1；高层冥仙的四维高，高等药仍然有意义。实际可用减益还受 5.4 的 `max_list` 限制。

| 1598 | 10105 吸血 −10 | 10107 连击 −20 | 10108 法抗 −30 |
| 1599 | 10103 反击 −10 | 10112 战意 −20 | 10113 强壮 −5 |
| 1600 | 10110 愈合 −5 | 10111 强袭 −30 | 10119 复活 −10 |
| 1617 | 10102 −50 | 10106 −50 | 10115 −50 |
| 1618 | 10105 −20 | 10107 −30 | 10108 −50 |
| 1619 | 10103 −20 | 10112 −30 | 10113 −10 |
| 1620 | 10110 −10 | 10111 −50 | 10119 −20 |
| 1637 | 10102 −70 | 10106 −70 | 10115 −70 |
| 1638 | 10105 −40 | 10107 −50 | 10108 −70 |
| 1639 | 10103 −40 | 10112 −80 | 10113 −20 |
| 1640 | 10110 −20 | 10111 −70 | 10119 −30 |
| 1657 | 10102 −90 | 10106 −90 | 10115 −90 |

【A】原表 `effect` 字段格式为 `精魄ID|触发类型|logic_type|参数1|参数2...`，最后一位是减益点数。例如：

```text
1597: 10102|3|101021|0|30 / 10106|5|101061|0|30 / 10115|6|101151|30|0
1657: 10102|3|101021|0|90 / 10106|5|101061|0|90 / 10115|6|101151|90|0
```

客户端会把 `effect_list` 解析成 `{type=精魄ID, reduce=点数}`，再用当前已上药品逐项扣减 `can_reduce`；当某个精魄的 `can_reduce` 降到 0，相关药品会被判为“不能再削弱”。

### 5.4 减益上限、分配与替换

#### 上限 `max_list`

【B】当前本地规则：每个属性的可减上限为“该属性原始合计 − 单位数”，即每个单位至少保留 1 点：

```text
max_list[attack] = Σ base_gongji - unit_count
max_list[defense] = Σ base_fangyu - unit_count
max_list[hp]      = Σ base_max_hp - unit_count
max_list[magic]   = Σ base_max_magic - unit_count
```

【A】客户端确实读取 `boss_data.pill_list`（已减益）与 `boss_data.max_list`（上限），并在药品效果超过上限时拒绝。上限的具体算法属于服务端，包内不能证明“减到 1”；本地选择标为【B】。

#### 分配

【B】普通药作用于“全队属性合计”，再按各单位可减容量（基础属性 − 1）比例分配；整数除法留下的余数按遍历顺序继续分配，并保证每个单位至少 1 点。示例（本地测试）：

```text
4 个单位，攻击合计 100,000，使用攻击 −10,000 的药
→ 每个单位约 −2,500；余数按 order 依次分配
→ 任何单位的攻击不会低于 1
```

【A】客户端只显示合计，无法看出服务端是“按比例分配”还是“只减主冥仙”；因此这是【B】。

#### 替换与重算

【B】当前本地规则：

1. 同一药槽再次用药，消耗新药，**旧药效果丢弃**。
2. 普通药：从“未减益的基础属性”重新汇总所有已上普通药，避免多次乘算或重复扣总。
3. 精魄药：从 `specter_jp_desc` 的基础可减值重新汇总所有已上精魄药，逐项 `max(0, base - Σreduce)`。
4. 如果新精魄药对当前冥仙的所有精魄都不能再降低，拒绝并回滚，不消耗药品。

【A】客户端会拒绝“效果超过上限”的普通药，以及“没有任何可减精魄”的精魄药；这与上述规则一致。

#### 清除时机

【B】当前本地规则：

- 胜利后清空 `pills` 与 `reductions`；下一层从零开始。
- 失败后保留药效，允许继续挑战同一层。
- 每日重置不清除药效。
- 更换挂机层不影响药效；药效只与 `boss_layer` 的冥仙有关。

原包只能证明客户端展示 `use_pill_list`；上述清除时机属于服务端行为，标为【B】。


## 6. 冥仙战斗流程与协议

### 6.1 请求与前置校验

【A】战斗请求是 `1329`（`msg_specter_event`）：

```text
serial_num=I, id=B, data=s
```

战斗相关 `id`：

| id | 客户端枚举 | 作用 | 请求 data |
|---:|---|---|---|
| 1 | `enter_specter` | 进入九幽 | `{}` |
| 2 | `change_area` | 更换挂机层 | `{des_area=层号}` |
| 4 | `rand_event_op` | 随机事件 | `{op_type=0/1/2,...}` |
| 6 | `fight_boss` | 挑战冥仙 | `{}`（空表） |
| 16 | `query_boss` | 查询当前冥仙 | `{}` |
| 17 | `use_pill` | 使用药品 | `{index=药槽, type_id=药品}` |
| 15 | `query_tips` | 轮询挂机消息 | `{}` |

【A】客户端在 `abyssUI` 中先调用 `getCharacterCSVConfig('specter_boss')`，再 `saveLastFightLevel()`，最后 `sendRequest(s_e_t.fight_boss, {})`；**不发送层号、阵容、伤害或胜负**。战斗目标层由服务端的 `boss_layer` 决定。

【B】本地服务端前置校验：

1. 角色等级 ≥70。
2. `boss_count < 5` 且未通关。
3. 至少一个神仙在 1—8 号位。
4. 使用 `boss_layer` 对应行的 `cortege_list` 构建敌方。
5. 无论胜负，`boss_count += 1`。

### 6.2 服务端结算步骤

【B】当前 `activity_abyss.settle()` 的 `id=6` 分支：

```text
1. 构建我方：journey.fighters(role, ...) → 1—8 号位、装备法术、精魄、星宿/觉醒、洞府修炼
2. 构建敌方：activity_abyss.enemies(s) → 1—4 个单位、基础四维、普通药减益
3. 计算精魄：activity_abyss_combat.effects(BOSSES[boss], pills) → 12 类精魄的当前数值
4. 若有精魄：activity_abyss_combat.battle(..., max_actions=80)
   否则：journey.battle(...)，复用通用引擎
5. result = 1—3 胜 / 4—6 负 / 0 平（按剩余血量比例）
6. win = 1 <= result <= 3
7. 胜利：发 prirze_list；若 boss==81 置 complete；boss+1；清空药效
8. fight_id += 1；发送 121 / 1028 / 1027 / 173 flag6 / 44
```

### 6.3 数据包顺序

【B】当前本地发送顺序：

| 顺序 | 消息 | 内容 | 客户端处理 |
|---:|---|---|---|

## 7. 伤害、回合与状态结算

### 7.1 伤害公式（V1.1 候选，【B】）

九幽与旅途共用 `network_redirect/combat.py`。当前公式来自用户提供的《普通攻击与主动法术伤害计算说明_V1.1》，原包只提供技能强度、等级成长、触发概率与精魄数值，**不提供原服公式**。

#### 普通攻击

```text
A = 基础攻击 * (1 + 攻击修炼%) + 攻击修炼固定
D = 基础防御 * (1 + 防御修炼%) + 防御修炼固定
D = 破甲后的当前防御
damage = max(0.05 * A, A - D)
```

即最低保底 5% 攻击力。

#### 主动法术

```text
A = 攻击者攻击
M = 攻击者灵力
D = 目标防御（含防御修炼与破甲后的当前防御）
S = 0.25 * A + 3 * M
S = S * (1 + 法术修炼%) + 法术修炼固定

raw = max(0.05 * S, S - D)

I = 技能基础强度 + 每级成长 * (技能等级 - 1)
I = I * (1 + 觉醒%)
I = I * (1 + 星宿法术%) + 星宿固定
K = 强度曲线(I)   # 30 → 1.2，450 → 1.8，中间线性
damage = raw * K * (2 / (目标数 + 1)) * (1 - 法抗 * (1 - 破法))
```

- 单体目标数 1，群体默认 8（`multi_target_limit`），可由 `skill_target_limits` 覆盖。
- 法抗 `R` 与破法 `ρ` 均限制在 0—1；`R=0.3, ρ=0` 时乘 0.7。
- 所有分数保留到最终一次向下取整，并限制在目标当前生命以内。
- 暴击／星宿等 `reborn_stars.combat_hit` 在最终取整前处理。

#### 文档算术校正示例

```text
A=10000, M=3000, D=5000, I=300
S = 0.25*10000 + 3*3000 = 11500
普攻 = max(500, 10000-5000) = 5000
法术 raw = max(0.05*11500, 11500-5000) = 6500
K(300) = 1.2 + (300-30)*(1.8-1.2)/(450-30) = 111/70 = 1.585714...
法术 = 6500 * 111/70 = 10307.14... → 10307
法抗 30% → 6500 * 111/70 * 0.7 = 7215
```

上例仅用于说明公式结构；实际九幽战斗的技能等级、目标数和法抗来自原表与单位状态。`docs/战斗伤害重建V1.1.md` 另有同样的算术校正，并指出文档旧值 7214 应为 7215。

### 7.2 技能选择与目标

【B】当前本地策略：

1. 按本地 `role['attachments']` 中该单位的技能顺序遍历主动技能（`attach_type=6`，`equip_pos>0`；通常与装备位顺序一致）。
2. 每个技能按 `use_probability` 逐项尝试；第一个成功者替代普攻。
3. 全部失败则使用普攻（`skill_type=1`）。
4. 单体技能取当前存活敌方中 order 最小者；群体技能取前 `target_count` 个存活目标。
5. 目标数不会随存活人数减少而提高单目标伤害；`2/(N+1)` 使用实际目标数。

【A】原包 `skill_base.csv` 提供 `use_mode`（1 主动／2 被动）、`effect_target`（1 单体／2 群体）、`use_probability`（单体 15、群体 10 等）与 `intensity/upgrade_plus`。选择顺序和“首个成功者替代普攻”属于【B】，不是已证实的原服行为。

### 7.3 回合顺序

【B】当前本地循环：

```text
round = 1, 2, 3, ...
for order in 1..8:
    我方 order 单位行动（若存活）
    敌方 order 单位行动（若存活）
    任一方的追加行动立即插入当前 action 之后
```

这意味着：

- 每个单位每回合最多一次主行动；死亡单位跳过。
- 敌方只有 1—4 个单位时，order 5—8 没有敌方行动；我方 8 个单位在行动经济上占优。
- 追加行动（连击、反击、斩杀）不消耗下一回合的行动，但会增加 `fight_round`（action 计数）。
- `first_hand` 字段由 1028 发送；本地固定为 1（我方先手），【B】。

### 7.4 精魄状态时序

| 精魄 | 本地结算时序 | 证据等级 |

### 7.5 星级与 `final_result`

【B】当前本地 `journey.stars(hp, max)`：


## 8. 魂仙随机事件战（`fight_type=25`）

### 8.1 触发与规则

【A】`abyss_rule_content2.csv` 的“遇魂仙”：

> 玩家可免费挑战魂仙 3 次，伤害累计，可使用道具或付费增加次数。

【A】客户端把魂仙作为五类随机事件之一（`event_type=3`），请求仍是 `1329 id=4`，内层 `op_type`：

| `op_type` | 含义 |
|---:|---|
| 0 | 查看当前事件（首次必须查看） |
| 1 | 执行挑战 |
| 2 | 放弃事件 |

### 8.2 客户端读取的字段

【A】`abyssUI` 的随机事件界面读取 `event_data.boss_info`：

| 字段 | 含义 |
|---|---|
| `is_dead` | 魂仙是否已被击杀 |
| `hp` / `max_hp` | 当前气血／上限 |
| `free_times` | 剩余免费次数 |
| `cortege_type` | 显示用的神仙类型（本地 3001） |
| `level` / `star` | 显示等级／星级 |

同时读取 `attach_list`（奖励预览）、`consume_item`（付费道具）、`cost_gold`（元宝费用）。

### 8.3 【B】本地结算规则

当前 `activity_abyss_random.py`：

```text
创建事件：hp = abyss_event_boss_hp（默认 50,000），attempts = 0
free_times = max(0, 3 - attempts)

op_type=1：
  若 attempts >= 3：
      有 1023 则消耗 1023×1
      否则消耗 20 元宝
  用 battle_npc（默认 1001）构建敌方，再把 hp/max_hp 覆盖为事件 hp
  跑一次 journey.battle
  damage = 本次战报总伤害
  hp = max(0, hp - damage)
  attempts += 1
  若 hp == 0：胜利，发随机奖励，事件出队
  否则：事件保留，可继续挑战
```

【B】以下数值是本地配置，不是原包证明：

- 魂仙气血 50,000（`abyss_event_boss_hp`）。
- 第 4 次起优先消耗 `1023×1`，否则 20 元宝（`abyss_event_fight_gold`）。
- 奖励池：`1001×10`、`1023×1`、`1330×5` 等概率。
- 敌方攻击／防御沿用 `battle_npc=1001` 的基础值，只把气血覆盖为事件气血；这不是魂仙的真实四维，属于【B】占位。

原包只能证明“3 次免费、伤害累计、可道具或付费”与客户端字段；魂仙的具体气血、四维、奖励与费用需要原服抓包。

### 8.4 战报与回放

【B】魂仙战斗发送：

```text
2998 id=121 { fight_extra_logic: 玩家精魄事件或空表, fight_id }
1028 { fight_id, first_hand=1, des_name='魂仙', lineup_count, lineup }
1027 { fight_id, fight_type=25, final_result, fight_round, fight_result }
2998 id=173 { flag=4, event_data={..., hp, max_hp, free_times, ...} }
2998 id=44 { fight_id, fight_type=25 }
```

- `fight_type=25` 是 `specter_spirit_fight`；客户端 `fightUI` / `bkg_mgr` 与 26 共用 `v2/abyssUI` 背景和标题。
- 魂仙**没有冥仙精魄**；但代码仍会发送 `121` 包（`journey.combat_engine.event_packets`），其中可能包含玩家精魄事件，或为空表用于清理客户端上一场的事件缓存。不要把它描述成“完全不发 121”。
- 回放结束后，客户端 `fight_type=25` 返回 `showRandomEvent`，而不是 `showBossLayer`。
- 伤害由服务端累计；客户端不提交伤害或胜负。

## 9. 客户端表现与战斗回放

### 9.1 Boss 界面读取的数据

【A】`abyssUI.showBossLayer()` 从 `g_data.boss` 读取：

|---|---|

| `boss_data.max_list` | 各属性可减上限 |
| `boss_data.use_pill_list` | 6 个药槽的药品 ID |
| `boss_data.drug_bag` / `drug_material` | 药包与材料，用于选药 |

1. 普通药：比较 `pill_list[i]` 与 `max_list[i]`，超过上限则灰掉或拒绝。
2. 精魄药：对每个 `effect_list` 项，按当前 `use_pill_list` 逐项扣减 `can_reduce`；当所有可减值都为 0 时拒绝该药。
3. 替换药槽：先移除旧药效果，再按未减益基础重算，防止重复叠乘。

### 9.5 `cur_layer` 与 `boss_layer` 的客户端用法

### 10.2 推荐的抓包与对照步骤

1. **低层基准**：第 1 层只有 1 个单位、无精魄，最适合反推普攻公式。记录双方四维、`damage_list`、`skill_type`。

3. **精魄范围**：第 33 层起 4 个单位；对比主冥仙与随从的破甲/格挡/复活表现（Q2）。
4. **药品上限**：在 4 单位层连续使用普通药，读取 `pill_list`/`max_list`，确认是否按单位保留 1 点（Q7）。

6. **失败与重试**：失败后不换药再战，确认药效是否保留；胜利后确认清空。
7. **每日次数**：第 5 次后客户端是否还发送 `id=6`；服务端是否返回错误。
8. **通关**：第 81 层胜利后 `boss_layer` 是否保持 81、是否出现 `wake6`。

### 10.4 当前工作树的 121 事件差异（重要）

这是本次审阅代码时发现的**实现层**差异，不影响原包证据，但会影响九幽战斗回放的正确性：

| 版本 | `activity_abyss.py` 的 121 构造 | 结果 |
|---|---|---|
| HEAD（git 提交） | `summon.event(121, dict({i:e for i,e in enumerate(fight_events,1)}, fight_id=fid))` | 把 `activity_abyss_combat.battle()` 生成的吸血／愈合／复活事件发给客户端 |
| 当前工作树 | `journey.combat_engine.event_packets(actions, fid)[0]` | `actions` 是 `combat.battle()` 返回的普通 list；`event_data` 用 `getattr(actions, 'events', [])` 取事件，普通 list 没有 `.events`，所以 121 包为空 |

影响：

1. 服务端内部仍按精魄回血／复活修改 HP，`1027` 的 `damage_list` 可能只体现伤害；客户端血条不会收到回复事件，可能出现“服务端活着、客户端血条空了”的视觉不同步。
2. `tests/test_activity.py` 中的精魄事件测试直接调用 `activity_abyss_combat.battle()`，检查返回的 `events`，不会覆盖 `activity_abyss.py` 的集成路径，因此测试通过并不代表 121 已正确发送。
3. 若 `fight_events` 为空（例如该层没有精魄），空 121 包反而可以清理客户端上一场的 `g_fight_events` 缓存；这是 `event_packets` 注释中提到的用途。但有精魄时不能丢事件。

修复选项（任选其一，均属【B】实现层）：

- 恢复 HEAD 的写法：直接使用 `fight_events` 构造 121。
- 让 `activity_abyss_combat.battle()` 返回带 `.events` 的 `Actions` 对象（或把 `fight_events` 挂到 `actions.events`），再调用 `event_packets`。
- 在 `activity_abyss.py` 中显式判断：有 `fight_events` 时用 `fight_events`，没有时用空表清理缓存。

在修复前，不应把“九幽精魄回放完整”作为已验证结论。

## 附录 C：结论摘要（给实现者）

1. **九幽是回放制**：服务端算，客户端播；不要相信客户端提交的伤害或胜负。
2. **冥仙是 1—4 个平铺单位**：基础四维来自 `specter_cortege_base`，`base_*_plus=0`、`chushijineng=0`；当前实现无主动技能。
3. **精魄从第 46 层开始**：12 种、1—4 级、触发概率 100%；第 46、64、73、81 层是明显的难度节点。
4. **药品是核心克制**：1—4 普通药削四维，5—6 精魄药削精魄；精魄药按绝对百分点扣减，最低到 0。
5. **每日 5 次，胜负都计数**：胜利进阶、发奖、清药；失败保层、留药。
6. **协议顺序不能错**：121 → 1028 → 1027 → 173 flag6 → 44；`fight_round` 是 action 条数。
7. **最大的未证实点**是“冥仙是否继承原生技能”和“精魄是否只挂主冥仙”；这两点会显著改变高层难度，必须用原服战报确认后再改实现。
