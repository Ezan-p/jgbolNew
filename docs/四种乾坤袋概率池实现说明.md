# 四种乾坤袋概率池实现说明

实现日期：2026-10-26。适用本仓库金箍棒3.87离线服务；配置版本`2026-10-26.1`。

## 1. 整体说明与设计依据

四种乾坤袋已经统一接入真实背包开袋接口1051。每个袋子消耗1个，必定获得**一个奖励结果**；该结果可能是若干货币、若干材料，或者1件装备／法术。批量开启N个就独立抽取N次，允许重复，没有空奖、保底、按等级改概率、VIP额外概率加成或每日概率衰减。

本实现采用用户提供图片的品质概率、物品范围和备注；类别权重、资源数量是本次离线版平衡设计【B】，并非恢复出的原服概率。原表的模板ID、名称、星级、物品类别、VIP1开袋门槛、1051请求／21结果事件属于已有客户端依据【A】。此前[原版获取方式与产出推测](四种乾坤袋原版获取方式与产出推测.md)仍用于记录历史证据，不能限制本次用户明确要求的全装备／全法术范围。

每袋有低／中／高3个品质池，共**12个品质池**。池内再按奖励类别划分组，组内同类别的具体模板等概率。品质档是奖励价值分层，不等于装备星级。例如VIP低档允许高级仙佛密卷，而VIP高档全是五星成品。

## 2. 数量与范围的明确约定

- 少量／中量／大量银两：2,000／10,000／30,000。VIP低档的“银两”采用30,000。客户端协议12对应银两、11对应元宝，与角色字段`silver_coin`、`gold_coin`一致。
- 少量／中量元宝：5／20。VIP低档5、中档20。货币ID统一为1，是协议占位ID，不是背包模板。
- 小包子、包子、仙丹、人参果、密卷、高级密卷、金刚钻、仙缘果、圣母蟠桃、精魄石、五法界魂箱：每次各1个。蟠桃：棉布中档5个、银绸低档10个。魂缘丹：银绸高档2个、金丝中档及VIP低档3个。
- 五星武器／防具／法宝／被动法术碎片，以及紫色精魄碎片：每次统一5个。同一组命中一种碎片，只给这种碎片5个。
- 装备、法术、高级召唤符、超级召唤符：每次1件／1张。装备与法术初始等级1，生成独立实例；材料按原物品是否可堆叠入库。
- “武器／防具／法术”按图中指定星级分别纳入全量模板；法术包括主动和被动。法宝只在图片明确写出法宝的池中投放，不混进普通武器／防具组。不加入二星法宝或一星战斗内部技能。
- 五星武器包含全部10种，五星防具全部8种，五星法宝全部9种，五星主动法术全部11种。普通五星被动8种，大乘经单列1种；因此9种五星被动都可获得，且大乘经不会重复进入两个组。VIP礼包专属、金箍棒等对应星级装备均未排除。
- 普通仙佛密卷、高级仙佛密卷各有20个不同ID，分别完整纳入；同名ID的经验值不同，组内等概率。附录列出每个ID及经验值。
- 五法界魂箱1249本次只发1个箱子，不自动选择界魂、不自动打开。自选流程于2026-10-29修正为1箱换1个所选界魂，每批1～99箱；仙缘果也只发道具，后续按既有仙缘果功能使用。

“池中数量”分三种口径：**奖励组数**、**具体候选结果数**、**命中后发放数量**。候选结果以`对象类型+模板ID+产出数量`区分；例如金丝低档10,000银两和30,000银两是两个结果，但同属一种货币。池子不是有限库存，抽取后不移除候选。

## 3. 概率机制与设计解释

单次抽取分三层：

1. 以整数票`0…99`抽品质档，按低／中／高顺序累加权重。
2. 在命中的品质档内，以整数票`0…99`按类别权重抽组。每个品质池的组权重合计100。
3. 从命中类别的全部N个候选模板中等概率选1个，按该组固定数量发放。

设品质概率为`Q/100`，组权重为`W`，组内模板数为`N`，则某一个具体奖励结果单袋概率为：

```text
P(具体结果) = Q/100 × W/100 × 1/N
P(某模板，不区分数量) = 所有可产出该模板路径的概率之和
E(某模板数量/袋) = Σ[路径概率 × 该路径发放数量]
```

概率乘算和文档展示与抽奖执行是分开的：执行只使用整数权重，不通过浮点数比较决定命中。文档显示的小数允许四舍五入，机器附件同时给出精确分数。

关键例子：

- 棉布低档2,000银两：`65%×70%=45.5%`；棉布中档10,000银两：`30%×25%=7.5%`。任意银两结果合计53%，银两期望为`0.455×2000+0.075×10000=1660`／袋。
- 金丝低档两个银两组占本档70%，符合图片“银两权重大”。它们占全部开袋的`40%×70%=28%`；不会挤占中档40%、高档20%的概率。
- VIP袋任意五星成品：5%；五星武器合计`5%×35%=1.75%`；每一种武器为`1.75%÷10=0.175%`。金箍棒与该组其他武器等概率。
- VIP五星法宝合计0.25%，每一种约0.02777778%；普通五星被动合计0.20%，每一种0.025%；大乘经单独0.05%。三类合计仅占VIP高档10%，其余90%留给五星武器、防具、主动法术。这里的“权重小”按类别总量定义。
- 金丝高档三星、四星法宝分别占该档1%；四类五星碎片分别占1%，均为低权重项目。紫色精魄碎片独立占该档8%，没有与四种五星碎片混淆。
- VIP高级召唤符每袋3%，超级召唤符每袋1.5%；一次命中各1张。批量开15袋不是把一次奖励乘15，而是15次独立试验。

此设计先固定类别占比，再分摊给同类模板。因此增加某类的合法候选时，只改变该类单件概率，不会把银两、元宝、材料的总概率稀释掉。若原表新增同类物品，重新启动服务并重新生成本说明的统计区，核对新增范围后再使用。

## 4. 离线版调用、入库与存档流程

```text
客户端背包选择实例并发送1051
  → Backend.respond校验登录状态
  → vip.handles把1031～1034统一路由到Backend.vips
  → 校验请求序号与相同请求的内存重放缓存
  → 从SQLite读取分离的角色副本
  → qiankun_bags.use读取并校验新配置
  → 校验VIP、物品实例、类型、等级、数量1～15、目标、锁定／占用状态
  → 每个袋子执行品质抽样→类别抽样→模板抽样
  → 预检本批累计货币奖励是否超出2147483647
  → 只扣所选堆叠；数量归零时删除该实例
  → item_rewards.grant → equipment_crafting.grant按类型发放
  → 生成2998/事件21及背包、货币、属性同步数据
  → 原成就系统记录111／112／113／114等开袋进度
  → 响应编码成功后保存角色，SQLite提交
  → 返回奖励结果、完成包1106，并缓存响应
```

本地Python服务使用`secrets.randbelow`产生无模偏差的整数票，组内使用`secrets.choice`均匀选取模板，底层随机性来自操作系统。整个过程不需要互联网或原服，也不使用系统时间、账号ID、开袋次数作为固定种子。断网不影响概率抽取；相邻袋子和不同批次之间没有人为补偿或关联。

背包响应保留每个袋子一条奖励记录，15个袋子产生15条。相同材料可在背包中堆叠，装备／法术仍各自分配实例ID；法术协议`object_type=6`，道具协议`object_type=5`。法术实例内的`count=0`是现有实例存储约定，领奖事件中仍明确`attach_count=1`，不表示发放0件。

校验、发奖、编码出错时不会保存这次角色副本，因此不会发生“扣了袋子但没拿到奖励”的部分结算。重复的相同报文在同一Backend实例的缓存范围内直接返回旧响应，不重抽、不重扣；相同或过期序号的不同报文拒绝。缓存最多256条、属于内存状态；**完整服务进程重启后不承诺旧请求的跨进程幂等重放**。角色已提交的袋子数量和奖励会持久化，重新登录后按存档展示；不要把手动回滚存档描述成概率保证。

此次未增加新的网络协议或客户端弹框。沿用原开袋展示入口，不需要重打APK；实际可见动画和全部图标本轮未做模拟器逐项目视验收。

权重和数量修改后每次开袋会读取新配置；但本次新增路由与Python代码需重启本地重定向服务后生效。无需修改历史角色、无需清空背包，也不会追溯补发已经打开的袋子。原包与`analysis/configs`中的CSV未改动。

配置要求：四袋齐全，每袋低中高三个池齐全，品质权重合计100、各档组权重合计100，权重为正整数、组不可为空、类别存在、同档具体奖励结果不可重复。装备／法术／召唤符数量必须1，五种碎片数量必须5，VIP门槛固定为1031需VIP1、其他袋无需VIP。非法配置在启动或使用时拒绝，不会静默退回旧池。
