# 体力和精力恢复机制检查与修复

检查日期：2026-10-28（Asia/Shanghai）

## 1. 检查结论

原项目已经实现自然恢复，位于 `network_redirect/journey.py::prepare`，登录快照、旅途操作和在线心跳会调用它，并不是完全没有实现。本次修复以下问题：

1. 配置中的体力恢复周期为 360 秒、精力为 900 秒，与原版说明和客户端倒计时不一致。
2. 已有角色的 `Backend.profile()` 不统一结算恢复。仅依赖特定玩法或心跳，可能使其他玩法在心跳前读到过期数值。
3. 旧逻辑以角色上次结算时间为相对起点；客户端却根据 `renew_time1/renew_time2` 指定的每小时分钟数倒计时，两者恢复时刻不同。
4. 缺少周期临界点、缺失时间戳迁移、时钟回拨，以及恢复后直接挑战等专项回归验证。

现已统一为服务端固定时点结算，保留现有 SQLite 存档、心跳同步、道具补充和超额资源。

当前配置按 UTC+8 使用，体力在每小时 `:00`、`:30` 恢复，精力在 `:00` 恢复。新建或缺少恢复记录的角色从首次初始化后遇到的下一个时点开始，不要求先等待完整的 30／60 分钟。例如 10:29:50 初始化后，10:30:00 可获得 1 点体力。

## 3. 结算与存档机制

### 自然恢复

`journey.recover_resources(role, now, rules)` 只处理资源，不重置关卡、活动或其他每日进度。

```text
经过时点数 = max(0, 当前服务端时间 // 周期 - 上次结算时间 // 周期)
如果当前值低于上限：新值 = min(上限, 当前值 + 经过时点数)
若经过了新时点：保存最近已处理时点
```

两项资源分别保存到角色的 `journey.strength_recovery_at`、`journey.energy_recovery_at`，并随角色 JSON 写入 SQLite。无需后台逐秒写盘：在线由已有心跳和角色读取触发，离线由下一次读取或登录补算。

- **在线等待：**2999 心跳结算，1032 属性包同步体力属性 101 和精力属性 102。画面数值以收到同步包为准，因此可能比理论时点晚一个心跳间隔。
- **离线、退出及重启：**从已保存时点补算，最多恢复至自然上限；多次读取和重连不会重复发放同一时点的资源。
- **操作前恢复：**已有角色的 `Backend.profile()` 先结算并保存，封神榜等玩法可以立即使用刚恢复的精力，无需先打开旅途或等待心跳。
- **满额或超额：**不增加，也不扣减；仍推进已处理时点，避免把满额期间的恢复次数存起来，消耗后瞬间补回。
- **消耗后继续恢复：**等待下一个固定时点，消耗和使用道具不会重新安排恢复分钟。
- **跨日：**零点正常结算一个时点，不额外补满；每日次数重置仍由原有旅途、活动模块处理。
- **时钟回拨：**保留已处理的较新时间戳，不重复发奖，待服务端时间超过它后继续恢复。若人为将服务器时钟调到未来再调回，恢复会等到该记录之后才继续。

### 老存档兼容

有旧恢复时间戳的存档继续使用它，按新周期计算之后经过的固定时点；已有资源不会按旧周期倒扣或重算。没有时间戳时以当前服务端时间初始化，不根据账号年龄凭空补发资源。角色等级、道具、关卡、领取记录均保留。

### 道具及活动补充

现有补充逻辑继续生效：小包子 1020 每个增加 5 体力、包子 1022 每个增加 10 体力、仙丹 1023 每个增加 10 精力；喂八戒按活动奖励增加体力。这些补充允许超过自然上限。

本次不调整库存道具的使用次数、快捷购买额度或价格，具体见[小包子与贡献令使用机制及调试说明](小包子与贡献令使用机制及调试说明.md)、[旅途与释厄实现说明](旅途与释厄实现说明.md)。

## 6. 生效与界面验收

重启本地游戏服务后加载新代码及配置，重新登录可获取最新恢复字段。旧存档会自动迁移，无需删除数据库或重建角色。本次检查未主动重启当前玩家会话。

人工验收可在测试账号中将资源消耗到上限以下，打开人物信息查看倒计时：半点仅体力增加 1，整点体力和精力各增加 1；离线跨过这些时点再登录，应补足对应次数。满额时停止自然增长，使用道具超过上限后，重登和心跳均不应将其裁回 30／15。
