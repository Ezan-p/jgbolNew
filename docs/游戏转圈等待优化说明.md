# 游戏转圈等待优化说明

更新：2026-11-05。

## 第一轮范围

先补齐请求链路耗时记录，再将成就事件改为先筛选、后解析。没有更改奖励、战斗结算、存档事务、响应顺序或原客户端等待超时策略。当前工作区中已有的通天塔相关修改不属于本轮修改。

原客户端发送需要等待的请求后，收到 `1106`（`req_serial_num`）才清除等待状态。服务端请求完成前的多余解析会直接推迟完成通知；但网络传输、客户端消息队列和 UI 回调也会增加等待，因此不能仅凭服务端耗时认定转圈问题已彻底解决。

## 耗时记录

### 服务端

`network_redirect/server.py` 为每次完整接收的请求输出 `game_request_timing`，请求内的 `game_response` 带相同 `request_id`。关联键为 `connection_id:连接内递增编号`，同时记录协议 `message_id`、业务 `serial_num`、`event_id`（存在时）。不记录载荷、账号凭据或角色数据。

| 字段 | 含义 |
| --- | --- |
| `receive_ms` | 收到前 5 字节后，读取剩余包头和包体的时间 |
| `respond_ms` / `backend_ms` | 生成响应列表的时间 / Backend.respond 内部时间，两者重叠 |
| `save_ms` | 本请求内所有 save 调用累计时间，包含状态计算、成就刷新、序列化和数据库提交 |
| `achievement_parse_ms` | 被白名单接纳的 Lua 载荷解析累计时间 |
| `achievement_packets` | 成就处理遍历包数，包含递归构造的嵌套事件 |
| `achievement_parsed` / `achievement_skipped` | 解析次数 / 2998、1301 中被白名单排除的次数 |
| `write_ms` | 将响应交给输出流及逐包日志的时间 |
| `drain_ms` | 等待输出流 drain 的时间 |
| `total_ms` | 上述服务端接收起点至 drain 返回或处理异常的时间 |
| `status` | `ok` 或 `error`；响应数量、字节数同时输出 |

使用 `perf_counter` 单调时钟和 ContextVar 隔离请求；阶段异常时仍累积耗时，并在 finally 清理上下文。未执行的阶段字段可以缺省。阶段有包含关系，不能把所有字段相加。完整收包前的异常沿用连接结束日志。

这不是客户端 RTT：不包含前 5 字节到齐前的时间、事件循环调度前等待，也不能用 drain 返回证明客户端已经收包或完成渲染。

安卓离线版 `offline_android/backend.py` 已允许上述字段进入 `files/logs/backend.jsonl`，沿用 512 KiB 轮转及写日志失败不影响事务的策略。桌面服务沿用现有 session 日志。

### 客户端

新增 `network_redirect/request_timing_client.lua`，由 `summon.client_source` 的补丁链装载。包装实际 `main_server.send_msg` 和 `msg_process_done_1106`（包括已注册分发表），输出 `[request_timing]` 日志：

- `stage=installed`：确认补丁实际安装，并标识时钟精度。
- `stage=send`：带正请求序号的实际发送；重发同一序号保留首次时间。
- `stage=ack`：收到匹配的 1106；`elapsed_ms` 包含传输、服务端处理及此前客户端队列处理。
- `stage=done`：原生 1106 回调返回；另记 `dispatch_ms`。该回调清除等待，也可能处理缓存消息并发送下一个请求，因此它不是下一帧画面呈现时刻。

优先使用 LuaSocket `gettime` 墙钟；缺失时退化为 `os.time`，明确标记 `wall_seconds`，不可用来判断毫秒级改善。墙钟调整会影响客户端差值；不使用 `os.clock`，因为 CPU 时间不能测网络等待。不跨客户端和服务端直接相减时间戳。

原生客户端只维护一个等待请求，补丁相应只保留当前序号，避免无确认请求无限积累。没有确认时只留下 send，不伪造完成。跨重连分析需结合日志会话、消息号和请求顺序，不能单靠可能重复的 serial_num。

## 成就事件先筛选、后解析

原实现对 2998、1301 事件几乎都调用 `login_fields`，仅提前排除 2998/121。该解析器会构建 Lua AST，即使事件最终没有对应成就分支，也承担解析成本。

新增 `ACHIEVEMENT_EVENTS`，在读取协议事件 ID 后、解析 `data` 字符串前筛选：

| 协议 | 允许解析的事件 ID |
| --- | --- |
| 2998 | 23、41、43、77、112、114、116 |
| 1301 | 40、69 |

白名单按协议区分。例如 2998/40 和 1301/41 都不解析。1027 的战斗权威结果仍照常处理；114 批量事件仍递归处理其中的 41 事件；`finalize` 保留原有调用语义。外层协议解码仍保留，本轮优化的是昂贵的内部 Lua 表解析。以后新增成就事件分支时必须同步白名单和测试。

## 实机验收和后续定位

1. 更新服务端并重新登录装载客户端补丁；安卓内嵌版需重打包安装。确认出现 `stage=installed`，精度是 `socket_wall`。
2. 对同一存档、同一操作重复采样，收集客户端 send/ack/done 与服务端 timing，按会话和请求序号配对，比较中位数和 P95。未收到 ack 的请求单独计为未完成，不计入成功耗时。
3. 优先检查 `achievement_parsed`、`achievement_parse_ms` 是否下降；若 `save_ms` 高，再拆分状态重算、JSON 与 SQLite；若服务端快而客户端 ack 慢，继续排查传输、消息队列和前序 UI 处理。
4. 若 `dispatch_ms` 高，检查 1106 回调内的缓存包处理及 UI 刷新；如果 done 后仍有可见等待，补测实际帧呈现和动画结束，不提前发送确认来掩盖问题。

第一轮只删除无效解析。第二轮实现和验证情况见下文。

## 第二轮：按变化同步、无变化不写库、按需准备

本轮在第一轮观测和事件筛选基础上，调整活动请求公共处理路径。

### 查询、移动、领奖分别同步

`Backend.activity_changes` 依据读取存档前的持久化状态与结算后的实际状态生成同步，而不是只看操作名称。这样查询恰好触发资源恢复、跨周奖励、移动获得物品等情况也不会漏发。缺失或旧版基线回退到完整快照。

| 操作与结果 | 同步行为 |
| --- | --- |
| 无变化查询 | 保留该活动查询结果和原有 1106 完成通知，不发送无变化的背包、阵容、魂魄和图鉴 |
| 普通移动 | 保留地图位置、行动力等活动原有事件；真实消耗的公共资源通过属性差量发送 |
| 移动获得奖励、使用道具、领奖 | 按变化发送物品或神仙快照、魂魄、图鉴及属性；属性变为零同样发送 |
| 跨日、跨周结算 | 保留活动自身结算和邮件同步，真实状态变化仍保存 |

背包和神仙列表仍按各自的完整快照分块协议发送，仅在对应列表发生变化时发送，避免破坏原客户端 `first_send` 和删除条目语义。神仙、物品属性差量仍位于快照之前。属性按 `(unit_type, id, type)` 去重，减少 activity、power、journey 三组重复的角色属性；不会提前发送 1106。序号校验、重放缓存和无序号轮询的原协议行为保持。

### 无变化不写库

`save` 仍先执行迁移、状态规范化、成就与任务跟踪，再比较最终序列化状态和数据库原值。完全相同才跳过角色 INSERT 和无事务时的 commit；若调用方已更新其他表，仍提交待完成事务，保留原事务边界。有真实变化照常提交。比较保留整数键经过 JSON 后变为字符串键的兼容性。

这里没有根据“查询请求”直接跳过保存，因为查询可能触发资源恢复或跨日结算。活动的防时钟回退字段、结算时间等发生变化时仍需要写库；不能期待不同时间的所有查询都零写入。

新增日志字段：`save_serialize_ms`、`save_commit_ms`、`save_unchanged`、`save_writes`，安卓离线日志白名单同步更新。

### 避免重复重算

在单次 `Backend.respond` 内启用有界缓存。只有同一个角色对象、完整角色状态、完整规则及当前秒都与上次重算后的状态相同，才跳过 `formation.recalculate`。任何字段变更、规则变更或跨秒都会重新计算；请求退出时清理缓存，异常也清理。

采用保守的完整状态比较，不维护容易漏掉的战力依赖字段清单。代价是一次状态复制和比较，大存档上仍应结合日志验证净收益。没有跨请求缓存，也没有忽略称号时间等有效期。

新增日志字段：`recalculate_ms`、`recalculate_calls`、`recalculate_skipped`。

### 按需活动准备的覆盖范围

通天塔 `1353` 在功能等级校验后直接调用自身处理器，不再先执行包含其他活动的 `activity.prepare`，也不加载无关的天命玩家列表。通天塔自己的 `state` 继续负责旧存档迁移、共享战斗编号初始化、行动力恢复、商店每日刷新、周排行结算和时钟回退保护。

登录、心跳及其他尚未拆分的活动仍保留全量准备。尤其没有把有跨活动依赖的结算统一删除。当前“按需准备”的专门分流仅覆盖通天塔；其他活动继续利用公共差量同步和无变化写库优化。

### 本机检查样本

以固定时间的测试存档连续查询通天塔信息为例，旧公共同步部分单独产生 **19 包 / 7461 字节**；修改后的整次响应（包含查询结果和 1106）为 **2 包 / 1739 字节**。本次新路径日志记录 `recalculate_calls=1`、`recalculate_skipped=2`、`save_unchanged=1`。

这是协议包体样本，旧值仅计公共同步部分、新值包含整次响应，不能作为等口径的总流量百分比。开发机计时亦不代表实机转圈时长。尚未重新打包或安装 APK。

新增 `tests/test_activity_performance.py` 覆盖重复查询无写库、移动保存及重放、列表清空与属性清零同步、实际修改必须写库、重算在状态变更和跨秒时失效。

## 第三轮：异常与重连出口、等待交互

### 请求身份和服务端防重放

新增会话级 `request_receipts`，覆盖已经认证且带正 `serial_num` 的业务请求；登录、重连、重放查询和心跳走各自控制路径。

- 同一请求序号、同一协议和载荷：返回原响应，不再执行业务。重连改变包头连接编号不视为新操作。
- 同一序号但协议或参数不同：明确拒绝，不覆盖原请求结果。
- 响应收据超过 256 条被淘汰：会话内仍保留最高已接收序号；旧序号不会重新执行。
- 执行业务前预留序号。若业务异常，回滚尚未提交的事务，返回错误提示和匹配的 1106；已提交部分不会假称已回滚，提示核对结果。相同请求重试复用该错误响应，避免提交后编码异常引发二次扣费。
- `1016` 重连保留收据；成功的新登录开启新序列。控制请求 `1105` 只查询响应历史，不执行扣费或发奖。

收据仍是服务端进程内、登录会话内保护，不是跨服务端重启的持久化事务日志。重启或新登录后，客户端不会自动重发旧会话未确认的操作，而是要求核对存档结果。本轮没有承诺跨进程的“恰好执行一次”。

### 缓存失效不再返回空列表

原 `1105` 找不到历史范围时只返回 `[]`，客户端缺少结束或恢复信号。现在返回不带响应序列号的 `local_request_reset` 控制事件，再发送完整权威快照：

1. 清理客户端未完成的等待计时及部分响应队列。
2. 对齐服务端响应序列水位，推进客户端请求序号下限。
3. 接收完整快照并提示重新打开活动查看结果，不自动重做原经济操作。

控制事件使用已有 2998/80 配置通道。无序号保证它能越过丢失的响应序列；服务端和客户端补丁需要一起更新。

### 等待状态和交互时序

`request_wait_client.lua` 包装业务请求入口、实际传输、1106 和已注册的消息回调，与第一轮耗时记录共存。

| 时间或状态 | 行为 |
| --- | --- |
| 实际发送时 | 立即保存请求序号和参数副本，并锁住重复业务提交；请求本身不延迟 |
| 前 200 ms | 不显示转圈；收到确认就取消计时，不再补显示 |
| 约 200 ms 后 | 显示原生转圈；使用调度器累计时间，不依赖秒级墙钟 |
| 超过 3 秒 | 提示“正在处理，请稍候；无需再次点击” |
| 超过 10 秒 | 停止普通转圈，提示正在确认原请求结果，并发送 1105 查询原响应 |
| 再等待 10 秒仍无确认 | 停止计时和转圈，明确提示结果尚未确认，进入待核对状态 |
| 待核对时再次点击完全相同的原操作 | 使用保存的原序号和原参数副本重试，不分配新请求标识 |
| 待核对时点击其他业务操作 | 阻止提交并提示先重连核对；导航和登录控制不依赖转圈遮罩锁定 |

按钮防连点由业务提交入口和实际发送入口共同保护，不依赖转圈是否可见，也不将连续点击排队为下一次扣费。这里没有给所有按钮统一增加灰色样式；其核心保证是立即阻止重复业务提交。

### 异常、重连和迟到确认

- 发送异常：保留原意图，进入待核对状态并关闭转圈，不假定请求没有到达服务端。
- 业务回调异常：明确提示界面更新失败，避免异常被静默吞掉；原 1106 仍负责确认业务。
- 1106 回调自身异常：清理等待标志、计时器及未处理的部分队列，推进已确认序号，提示重新打开界面核对。
- 不匹配的迟到 1106 不完成当前请求；重复确认不会重复推进序号。
- `req_serial_num=0` 仅表示重放控制完成，不证明原业务成功。有待确认业务时进入待核对状态；无业务等待时清理并处理重放队列，不消耗新的业务序号。
- 重连成功先查询响应历史，保留原业务请求；重连失败明确提示重新登录。新登录成功丢弃旧意图，不自动重做。
- 原生 `packageTimeOut` 在本状态机接管的请求上转入响应确认流程，避免显示超时后留下仍在等待的标志。

新增 `[request_wait]` 状态日志；安卓离线后端允许 `game_request_failed`、`game_replay_unavailable` 和异常类型落盘，不记录业务载荷或凭据。

### 验证方式与限制

新增 `tests/test_request_wait.py`，以真实 Lua 5.1 运行时和可控调度器验证快速确认不闪圈、防连点、慢请求提示、超时查询、原标识重试、迟到与零序号确认、回调异常、缓存重置和重连状态。新增 `tests/test_request_recovery.py` 验证响应复用、连接编号改变、收据淘汰、冲突参数、提交后异常及重连后的防重放。

完整客户端补丁已通过 Lua 5.1 编译检查。Lua 动态测试需要 `lupa.lua51`；本轮测试依赖安装于临时目录，未写入产品依赖。尚未重新打包安装或进行真机触摸与弱网验收，因此 200 ms 显示时机和原生提示的视觉效果仍需实机验证。
