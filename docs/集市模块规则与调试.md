### 3. 普通购买与限购显示

`shopUI.getGoodsList`（L120–124）发送：

```text
1057: serial_num=I,index=B,type_id=I,count=I,first_send=B,page_id=B
查询：first_send=1, index=0, type_id=0, count=0, page_id=1
购买：first_send=0，page_id=1/2/3 分别为特惠/全部/独立限时
```

响应是 `2998/id=24`。`first_send=1` 时携带完整商品列表，客户端加载后执行刷新回调；普通购买成功值是 `result=1`。其它原版结果码：2 商品不存在、3 已下架、4 时间未到、5 VIP 限制、6 钱不足、7 已购买/次数用完。

`buyShopItem`（L948–976）按 `buy_price × 购买份数` 检查余额。币种枚举 `11=元宝、12=银两`。特惠/独立限时默认一次购买一份；全部页支持批量，窗口按余额除以价格计算可购买数量。成功后特惠的原版回调会自行减一次剩余次数，因此服务端不能先发一个已经扣减的新列表、再让成功回调减第二次。

`is_day_limit` 决定特惠限购文案；`buy_limit_times=0` 禁用购买。客户端还支持服务端 VIP 配置的乾坤袋每日上限，并在本地按角色保存购买历史。原包未提供完整的该项服务端数值，本次不冒充已恢复这套 VIP 上限。

### 4. 抢购规则与原版时间文案

原版 `v2/String.plist` 的文案：

- `sales1`：每周二、四开启。
- `sales2`：午市 12:00–13:00。
- `sales3`：晚市 18:00–19:00。
- `sales8`：每十分钟进行一次打折，限量供应。

这些文本由 `shopUI/salesUI` 原版 UI 显示，`common.hz` 从 plist 加载。服务端排期遵守这组周几和小时；时区见【B】。

`salesUI.getStatus/getCurrentPrice/buyItem` 中可直接验证：

1. 活动判断为 `sale_time < 当前时间 <= sale_time + 3600`。开场整秒仍为未开启，结束整秒仍可购买；实现保留原版边界。
2. 第一件剩余库存大于 0 时处于第一阶段；售罄后进入第二阶段。第二件在第一件售罄前不可购买。
3. 第一阶段价格为 `floor(原价 × panic_discount[ceil((当前时间-sale_time)/600)])`。例如第 600 秒仍用第一档，第 601 秒进入第二档，最多六档。
4. 第一件两次购买至少间隔 10 秒；第二件按 `per_buy_limit - has_buy_item2` 限购。
5. 第一件售罄后显示服务端 `item1_sale_price`；第二件使用固定 `panic_price`，两个购买分支均检查元宝。
6. 活动状态查询走 `1242(sale_time=I)`，没有请求流水，不等待 `1106`；返回事件 `138`。购买走 `1241(serial_num=I,buy_index=B)`，返回事件 `139`。
7. 抢购与普通商店成功码不同：抢购 `result=0` 才成功；1 失败、2 元宝不足、3 限购、4 活动关闭、5 售罄。
8. 查询和购买回包必须含 `activity_data`、`role_data`；成功还含 `attach_list`。奖励条目使用 `object_type/attach_type/attach_count/attach_level`，与背包协议的 `attach_type/type_id/count` 命名不同。

## 三、【B】缺失服务端配置的推测与落地

| 项目 | 本地采用值 / 行为 | 依据与限制 |
|---|---|---|
| 时间解释 | UTC+8；每日 00:00 重置特惠 | 与中文运营时段一致，但客户端文案没有时区声明 |
| 常驻选品 | 启用原表 begin_time=end_time=0 的 15 项；不复活 2013 活动 | 原版旧表的保守使用方式；不宣称是最后运营服全量商品 |
| 常驻币种 | 元宝 `money_type=11` | 原表没有币种列，原 UI 支持元宝/银两 |
| 特惠次数 | 每角色每商品每天 1 份，`is_day_limit=1` | 原 UI 有每日限购分支，原表没有具体次数 |
| 特惠原价 | 同品全部页单价 × 每份数量；无对应商品则等于实际售价 | 蟠桃显示原价 5、VIP乾坤袋显示原价 30；未虚构更高划线价 |
| 全部页上限 | 无额外 VIP 袋子日限购；每单最多 999 份 | 原版有配置入口，但具体服务端值缺失；999 为本地请求保护上限 |
| 抢购第一件 | 高级召唤符 1006 ×1；原价 150 | 商品存在于原版；选品与价格均为推测 |
| 六档折扣 | 0.9 / 0.8 / 0.7 / 0.6 / 0.5 / 0.4 | 对应成交价 135 / 120 / 105 / 90 / 75 / 60 元宝；折扣数值为推测 |
| 每场第一件库存 | 10 份 | 本地单账号服务持久化，只有真实购买会减少，不模拟其它玩家抢购 |
| 抢购第二件 | 超级召唤符 1007 ×1；展示价 300，成交价 180；每场限购 3 份 | 选品、价格与次数均为推测 |
| 最低成交价 | 每次成功购买记录成交价，售罄后展示最后一次成交价 | 折扣单调下降，因此此值是本场最低实际成交价；官方结算代码缺失 |
| 非活动时段 | 下发下一场完整商品预览及未来 sale_time；禁止购买 | 遵循客户端预告显示，下一场重置库存/个人次数 |
| 结算与保存 | 服务端查表计价、校验 VIP/数量/库存/阶段；先编码响应，再一次性保存角色 | 客户端不能作为扣款或限购的信任边界 |
| 重发与过期请求 | 同一登录会话同一流水原包返回原响应；旧流水或同流水不同内容拒绝 | 本地防止重复消费策略；缓存 256 组，完整重新登录重建会话 |
| 抢购跨场点击 | 购买绑定该连接最近收到的登录/查询活动时间 | 原版1241没有活动ID，避免旧点击在新一场误扣款 |

上述配置是本地离线恢复方案，不是“官方运营服配置”。历史版本曾固定校验原版周二/四、12/18点；当前按用户要求校验周二/四/六、12/18点，并由客户端补丁同步开启及刷新文案。

配置修改后重启本地离线服务生效。购买所得商品进入原背包；开袋、聊天、更名等关联功能是否可用，取决于各自子系统，本次没有把“买到物品”冒充为已完成所有道具使用逻辑。
