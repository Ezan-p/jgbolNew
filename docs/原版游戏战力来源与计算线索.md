# 金箍棒 3.87：原版战力来源与计算线索

分析日期：2026-10-24。对象：本项目 `jgbol3.87` 中的原版客户端资源、LuaJIT 字节码、协议和 CSV；不把本地模拟服务端的推测规则当作官方规则。

## 1. 结论与证据边界

**单神仙战力、角色总战力都是原版协议中的独立数值。当前材料可以还原大量属性来源及部分局部计算，但尚不能还原完整官方战力公式，也不能证明总战力恒等于上阵神仙战力之和。**

已经确认：

- 神仙战力字段为 `combat_power`，神仙属性编号 **58**。
- 角色当前总战力为 `role_combat_power`，角色属性编号 **30**。
- 另有角色属性 `max_combat_power = 39`。名称提示最高战力记录，但更新时机、用途和是否历史峰值仍未确认，不能替代当前战力。
- 单神仙存在基础、培养、装备、法术、三类仙缘、角色加成、助威相关、收集、转生装备、灵兽、称号、觉醒、星宿、洞府等属性入口；还有只在战斗中起效的触发效果。
- 客户端定义了 `client_config_type.combat_power = 25`。这是值得追踪的专门配置类别，**尚未获得其内容，也未证明它一定保存战力权重**。
- 本地 `network_redirect/formation.py` 的默认“四属性等权相加，再合计上阵者”属于本地推测，不能用于证明原版公式。

证据标记：

| 标记 | 含义 |
|---|---|
| 【实证】 | 原包字段、表值、协议或可直接读出的字节码行为 |
| 【线索】 | 字段或配置存在，具体适用对象、顺序、计分方式尚缺直接证明 |
| 【假设】 | 为验证或未来实现设计的候选公式，不能当作官方结算 |

本文“全部可能来源”指当前 3.87 原包可见来源的尽量完整清单，包含未证实计入评分的入口；不意味着已经证明所有入口都会涨面板战力。服务器独有规则、旧服热更新和未下发配置不在可穷尽范围内。

## 2. 战力从哪里来：协议与显示链路

### 2.1 单神仙战力

【实证】公共结构 `type_cortege_data = 114` 同时携带：

```text
id, order, cheer_order, type, level,
hp, magic, gongji, fangyu, combat_power,
culture_point, hp_plus, magic_plus, gongji_plus, fangyu_plus,
evolve_level, equiped_ext_skill_limit, equiped_ext_star_limit,
reborn_layer, reborn_vein_level, reborn_plus_type ...
```

`1034` 用 `cortege_list=$114{255}` 下发神仙列表；`1032` 用 `unit_type、id、attr_list` 更新对象属性。因此可以分别更新四属性和战力，协议本身没有要求客户端根据四属性现算战力。

原版 `charPositionUI` 原源码行 **1502** 读取 `character.combat_power`；原源码行 **3494–3502** 遍历 1–8 阵位，把 `g_usedCharacters[i].character.combat_power` 保存到 `g_lastCombat[i]`。这段是单体旧值缓存，**不是总战力求和公式**。

### 2.2 总战力

【实证】`1017` 登录角色信息包含 `role_combat_power=I`。`mainUI` 原源码行 **1025** 显示此字段，**2857–2868** 比较新旧 `role_combat_power` 后调用 `showCombatAnim`；阵容页原源码行 **4242** 也读取总战力字段。

由这些调用可以确认显示数据来自服务端，但不能仅凭 UI 推导服务端的汇总算法。

### 2.3 三套容易混淆的属性

| 神仙属性编号 | 字段组 | 可确认含义与限制 |
|---|---|---|
| 53–54 | `hp`, `magic` | 神仙属性枚举中的生命、法力字段；不可仅凭同名断定等于面板最大值 |
| 61–64 | `max_hp_show`, `max_magic_show`, `wuligongji_show`, `wulifangyu_show` | 显示属性入口 |
| 65–68 | `max_hp_calc`, `max_magic_calc`, `wuligongji_calc`, `wulifangyu_calc` | 计算属性入口；与显示值是否一致需要验证 |
| 71–74 | `base_max_hp`, `base_max_magic`, `base_wuligongji`, `base_wulifangyu` | 基础属性入口 |
| 58 | `combat_power` | 单体评分，不是上述任一属性的别名 |

注意：`1034` 结构中也用 `hp/magic/gongji/fangyu` 作为传输字段名。不能把传输结构与内部属性枚举仅靠字段拼写机械等同。

证据：[协议结构](../analysis/evidence/protocol_tables.json)、[原版属性定义](../analysis/evidence/lua_named/lua/common/common_def.lua.txt)、[单体界面](../analysis/evidence/lua_named/lua/ui/charPositionUI.lua.txt)、[主界面](../analysis/evidence/lua_named/lua/ui/mainUI.lua.txt)。文中“原源码行”指反汇编的 `[L...]`，不是 `.txt` 文件行号。

### 3.1 精魄、阵法和临时增益不能漏查

`skill_ext_base.csv` 有外部技能等级和 `spell_rate`；公共枚举 `FIG_OR_LINE` 区分 `FIGHT=1` 与 `LINEUP=2`。`ext_star_config.csv` 明确存在 `LINEUP` 类型四维加成，另有战斗触发效果。精魄所带破甲、反击、吸血、格挡、连击、法抗、愈合、强袭、战意、强壮、斩杀、复活等应按具体条目判断。

`rune.csv` 描述例如“随机增加我方一人攻击”“增加我方全体攻击”。这证明阵纹有战斗作用，**不证明 `runeUI` 显示的角色战力是把阵纹重新折算后的值**；该 UI 直接读取 `role_combat_power`。

九幽药品削弱、关卡附加规则、活动临时增益也应独立记账。它们可能显著改变战斗结果，却不改变常驻战力字段。

### 3.2 全局加成的证据字段

角色属性枚举保留正向八方 `heaven/earth/shake/sunda/water/fire/hill/pool` 的四维与 `_plus`，以及 `unheaven/.../unpool` 逆向对应字段、助威等级、效果、技能等级。

角色 `goss_*` 不止四维：还分神仙、装备、法术通道，以及威慑、招架、吸血、清心、复活、法抗、破甲、祝福、强壮、战意等效果字段。追踪灵石时要保留这些分层，避免只扫描 `hp/gongji` 而漏掉有效来源。

完整角色和神仙字段可见 [本次枚举与审计结果](../analysis/evidence/combat_power_audit.json)；神仙 161 个字段另附在文末。

## 4. 总战力有哪些可能来源

【实证】总战力有独立的服务端结果字段；当前静态材料尚未发现完整的官方汇总实现。

| 可能组成／变化原因 | 证据与判断 |
|---|---|
| 上阵神仙自身战力 | 最基本的汇总候选；客户端有 1–8 阵位单体缓存，但不能由缓存循环证明求和 |
| 可上阵人数和实际阵容 | 会改变参战集合；必须明确 `order`、主角是否占位以及各玩法阵容规则 |
| 助威者属性传递 | 助威表和角色字段确实存在；可能已进入受益神仙战力，不应再重复加助威战力 |
| 伙伴组合产生的仙缘 | 换一个神仙可能同时改变多人的属性，因此总变化不一定等于新旧两名单体战力差 |
| 全局收集、灵兽、称号、灵石、洞府等 | 若已体现在每名单体战力中，汇总后无需额外加一次；是否另设团队评分待验证 |
| 阵纹／法术／精魄的非四维效果 | 有战斗效果，但是否存在单独团队评分尚无实证 |
| 非上阵、非助威神仙 | 可能通过收集等间接影响；没有证据支持“背包里所有神仙战力直接相加” |
| `max_combat_power` | 与当前总战力并列的字段，不能拿最高记录参与当前汇总 |
| 其他玩法 `fight_power` | 洞天、挑战、敌方信息里的类似名称要按协议上下文区分，不能当作角色总战力的额外加项 |

### 4.1 推荐的验证式，而非已确认公式

```text
P_i = 官方给第 i 位神仙的 combat_power
T   = 官方 role_combat_power
S   = 当前待验证的计入集合
R   = T - Σ(P_i, i ∈ S)
```

先对“仅上阵”“上阵＋助威”“主角与伙伴分开”等集合计算残差 `R`，再做单变量变更：

- 多个状态下 `R=0`：支持该范围内的求和模型，仍需高阶系统样本验证。
- `R` 随助威变化：检查受益神仙刷新是否完整，再判断是否有额外评分。
- `R` 恒定：检查漏掉的主角／固定项；不能立即把它定成官方常数。
- `R` 随称号、阵纹或精魄变化：检查是否存在非四维评分或不同汇总范围。

应等一组属性更新完成后比较，避免 `1032` 分包到达时把“总战力已刷新、单体尚未刷新”的过渡状态误认为公式。

## 5. 可以落地的局部计算线索

### 5.1 基础与升级

`cortege_base_0.csv` 中 5001 的基础攻／防／命／法为 `218 / 124 / 522 / 137`，成长字段为 `15.7 / 9.28 / 39 / 10.29`。

【假设】首先检验的裸属性模型：

```text
Base_s(L) = template_base_s + growth_s × (L - 1)
```

按这个模型，2 级、没有任何加成时的未取整结果是 `233.7 / 133.28 / 561 / 147.29`。**这是配表推导例子，不是已获得的原服观测值，更不是战力。** 服务端可能在成长、倍率或最终输出阶段取整；转生后的模板和等级也会改变结果。

### 5.2 装备强化的直接公式

【实证】`equipmentUpgradeUI` 原源码行 539、543 及相邻生命分支按下面结构生成属性显示：

```text
装备属性显示值 = 基础属性加成 + (装备等级 - 1) × effect_plus
```

攻击分支读 `base_gongji_plus`，防御分支读 `base_fangyu_plus`。这能证明该 UI 的基础强化展示算法，不能据此断言升阶、转生、灵石后的最终装备加成仍然只有这一项。

`equip_advance_worth.csv` 有诸如 `0|6`、`0.04|42|0`、`0.18|147|0.05` 的复合值，且存在重复列名。解析应保留列序，不能用普通字典读表后把同名列覆盖，也不能把 `worth/cost` 一律当作“战力点”。

### 5.3 法术、仙缘和百分比单位

【实证】`fate_config.csv` 例如：照妖镜缘给 4064 法力 `15%`；四大天王缘描述与指定伙伴一起上阵、生命提升 `35%`。

【实证】`ext_star_config.csv`：

- 10301，1 级 `1|0.3|0`，说明为攻击增加 `0.3%`。
- 10302，1 级 `1|0|50`，说明为攻击增加 `50`。

因此不同表的比例不能统一用同一种单位：星宿 `0.3` 是 0.3%，不是 30%；助威表却有 `0.026` 这类原值，其应用仍须对照实际运算。不得看到小数就自动乘 100 或除 100。

法术的 `upgrade_plus` 需要结合 `effect_field`、基础值和 `formula` 读取。最常见候选是“基础效果＋增量×(等级−1)”，但不能脱离具体法术分支推广到所有主动／被动效果。

### 5.5 单体战力候选式

仅供拟合的最简模型：

```text
P_i = Q(wH × H_i + wM × M_i + wA × A_i + wD × D_i + E_i)
```

`Q` 是未知的取整或量化规则；`w*` 是未知权重；`E_i` 代表主动法术、精魄、星宿强度等可能的额外评分。

需要分别尝试 `show`、`calc` 及其他独立属性作为输入。若四属性保持不变而原服战力改变，最简纯四维模型就被否定；不能靠随意修改权重掩盖遗漏的来源。

**目前没有足够证据填写这些权重，也没有证据确认 `E_i=0`。本地默认 `wH=wM=wA=wD=1` 是实现选择。**

## 6. 为什么不能把所有加成一次相加

推荐保留以下概念层级进行逆向分析，但此图示顺序不是已经还原的官方计算顺序：

```text
模板／等级／培养
   ├─ 装备自身基础、强化、升阶、转生
   ├─ 法术属性、觉醒、仙缘
   ├─ 收集、称号、灵兽、助威等共享来源
   ├─ 灵石：分别作用于神仙、装备、法术的通道
   └─ 星宿、转生、洞府与特殊倍率
              ↓ 未知的基数、叠加与取整规则
          显示属性／计算属性
              ↓ 未知的评分函数
           单神仙 combat_power
              ↓ 未知的计入集合与团队附加项
           role_combat_power
```

必须解决的叠加问题：

1. 多个百分比是相加后乘一次，还是逐项相乘？
2. 装备仙缘乘装备本身、基础属性还是最终属性？
3. 助威依据助威者裸属性、面板属性还是专用传递值？
4. 灵石的装备／法术加成在相应子系统内部结算，还是对总面板结算？
5. 星宿固定值、称号、收集等是否被其他倍率放大？
6. 每个阶段取整，还是最后统一取整？
7. `plus_rate`、`max_hp_rate` 等是来源值还是已汇总的缓存？
8. 特殊场景改变的是 `calc`、临时战斗状态，还是常驻评分？

这些问题未解决时，直接叠加所有字段容易重复计算：例如角色收集与神仙收集入口、角色宠物属性与神仙宠物加成、装备总加成与装备转生子项，都可能是同一效果的不同阶段。

## 7. 最重要的缺失线索：配置类别 25

【实证】`common_def.lua` 的 `client_config_type` 包含：

```text
cheer_data=14, stone_config=11, equip_advance=23,
common_config=24, combat_power=25,
reborn_config=31, awaken_star_config=32
```

本次扫描原资源索引及解出的 CSV，没有找到名为 `combat_power.csv` 的战力系数表。枚举存在只能证明预留／使用过这个配置类别，不能证明当前版本仍使用，也不能证明配置里一定有完整公式。

后续优先事项：找到原服或可信旧客户端缓存中的类别 25 内容，确认它的实际接收／解析路径；同时取 11、14、23、24、31、32 类别辅助解释其他加成。

公共协议还定义 `msg_query_config=955`、`msg_update_config=956`，后者有 `common_config/world_config/arena_config/fixed_config` 字符串块。但**目前未证实类别 25 必经此协议**，不能直接把 956 宣称为战力配置下发包。

本次完整扫描了资源索引中的 **323 个原版 Lua 脚本**，按 `combat_power/combatPower/CombatPower` 检索命中 11 个脚本。相关命中主要是字段定义、协议、复制和界面读取；没有从这些命中中还原出完整评分公式。这个检索结论也不能排除另有不使用这些字段名的 native 实现或服务器实现。

## 8. 如何用原服样本把公式补齐

仅使用可信原服响应／历史抓包做验证；本地后端产生的数值只会重复当前的推测公式，不能证明原版。

每个快照至少保留：版本、时间、角色 ID、上阵和助威列表、各神仙类型／等级／飞升／转生、四维、单体战力、角色总战力、所有装备法术精魄星宿、共享加成和当前玩法状态。能采集时同时记录 `show/calc/base` 及 `1032` 原始增量。

| 实验 | 保持不变的条件 | 用途 |
|---|---|---|
| 裸神仙连续升级 | 不装备、不培养、无新增共享效果 | 验证成长、取整、基础评分 |
| 只增加攻击／防御／生命／法力 | 使用单属性来源，暂避仙缘触发 | 分别估计四种边际权重，验证是否线性 |
| 同四维更换主动法术／精魄 | 四维不变、只改变触发能力 | 判断是否有额外评分项 |
| 同比例使用不同属性底数 | 不改其他系统 | 确定倍率作用的基数 |
| 两种增益分别启用及同时启用 | 同一个神仙、同等级 | 区分加算、乘算和固定值顺序 |
| 助威上下阵 | 主阵不动，完整采完受益者属性 | 确定传递关系、避免重复汇总 |
| 单独换将及增减阵位 | 全局加成固定、检查仙缘变化 | 确认总战力计入集合 |
| 称号／收集／灵兽等全局开关 | 所有单体同步记录 | 检查团队评分是否独立存在 |
| 进入／退出有增益的玩法 | 记录进入前、战斗中、退出后 | 区分常驻和临时效果 |
| 接近取整边界的多组样本 | 小额单属性增量 | 识别逐层取整、截断、四舍五入 |

至少使用线性无关的属性变化求解四个权重，并用额外样本反证。一个裸神仙、一个等级或一个总战力值不能唯一决定公式。

## 9. 与当前本地实现的关系

当前 [formation.py](../network_redirect/formation.py) 采用配置权重计算四维加权和，并对 `order` 非零者求和。现有 [阵容规则说明](阵容模块规则与调试.md) 已将它标为推测规则。

- 分开存储属性来源、中间量、面板值和评分结果。
