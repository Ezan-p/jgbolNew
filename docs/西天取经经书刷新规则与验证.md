# 西天取经经书刷新规则与验证

更新日期：2026-11-09。

本次修复运送经书的刷新逻辑：移除“当前档次加1～2、最高为5”的算法，改为每次成功刷新直接从高四档抽取。第4档可以刷成第2档，第2档可以连续出现五次；最后一次刷新也没有额外保底。

## 规则与证据

- 用户确认的玩法：刷新只出现第2、3、4、5档，四档概率不同，可降档、可重复，无保底。
- 原版客户端证据：`analysis/evidence/guild/ui_escortUI.txt`，原源码行1395在档次5时直接提示并停止刷新；行687～690直接接收服务端的档次、已刷新次数和贡献，没有只升不降的限制。行1205用服务端上限减已刷新次数显示剩余次数。
- 原包未找到服务端刷新概率表，因此以下概率属于暂定本地数值，不能宣称是原服精确概率。
- 原包字符串 `book_tip28` 确实写有“再刷新%d次必得紫书”，`book_tip282` 提示未刷到紫书联系客服。这与本次用户明确要求的“无保底”冲突，因此按用户规则实现，并在 `guild_activity_client.lua` 中仅替换取经模块的提示为剩余刷新次数、品质随机和次数耗尽。没有将原包文案作为新增保底的依据。

| 经书档次 | 每次有效刷新概率 |
|---|---:|
| 1 | 0% |
| 2 | 60% |
| 3 | 25% |
| 4 | 12% |
| 5 | 3% |

概率配置位于 `server_config/guild_rules.json` 的 `escort_refresh.grade_weights`，与残卷合成的 `escort_compose.bag_weights` 分开管理。虽然暂定比例相同，两者没有共享奖池或概率联动。刷新使用现有 `summon.weighted_choice` 的整数权重抽样，每次仅抽一次，概率不依赖当前档次、已刷新次数或历史结果。

最高档停止刷新沿用原客户端规则：这表示已经获得最高档后无需继续刷新，不是经过若干次后强制抽到最高档。后端也拒绝最高档的刷新请求，不扣费、不计次。

## 次数、费用与存档

沿用已有本地数值：初始第1档，每趟最多刷新5次，首次免费、后续每次10元宝；每日最多运送3次、拦截3次，运送时长一小时。次数和费用没有新的原服数值证据，本次不将其标为已还原的官方数值。

查询、切换路线和重启不重新抽取；旧存档直接保留当前经书档次及已刷新次数。出发时检查请求档次等于存档档次，保存本趟经书；下一趟初始档次和刷新次数恢复为1和0。运送中或尚未领奖不能刷新。每日重置逻辑沿用现有实现。

元宝不足、次数耗尽或最高档刷新请求均不扣费、不计次；同一会话重复发送同序号请求返回已保存响应，不重复抽奖或扣费。完成奖励根据最终出发档次结算，现有拦截、护送、残卷合成和经书袋奖励机制继续使用各自规则。
