# 等级卡道具实现与使用说明

更新日期：2026-11-13。本文对应源码新增道具，不代表已发布到现有APK。

## 1. 道具用途与设计范围

新增“等级卡”，每消耗1张，使**当前主角等级提高1级**。这里的等级指账号主角等级，不是神仙等级、宠物等级、装备等级或洞府规模。

按本次需求新增的等级卡及其使用规则属于【B：离线自定义规则】；沿用的主角1～99级经验表、阵位表和使用道具协议属于现有原版客户端结构。等级卡不是原版已存在道具的改名，不覆盖传世金卡、仙佛密卷或天仙令。

## 2. 基础定义

| 项目 | 配置 |
|---|---|
| 道具名称 | 等级卡 |
| 道具模板ID | `1901` |
| 奖励对象类型 | `5`：普通道具 |
| 物品自身等级 | `1`，与主角等级无关 |
| 可堆叠 | 是 |
| 单次消耗 | 1张 |
| 使用对象 | 当前账号主角 |
| 使用效果 | 主角等级+1 |
| 主角适用等级 | 1～98级 |
| 当前等级上限 | 99级，运行时取主角等级表的最大等级 |
| 原有修为 | 保留绝对数值，不清零、不按百分比换算 |
| 升级奖励 | 按到达等级正常发放 |
| 批量使用 | 不支持，每次请求只能使用1张 |
| 出售 | 未配置出售价格，不可通过普通道具出售接口卖出 |
| 获取途径 | 仅激活码礼包，10／20／50张三档 |
| 每日次数 | 没有为等级卡新增每日使用次数限制 |
| 图标 | 复用现有金卡资源`217`，没有新增图片文件 |
| 分类 | 背包道具页；技术上沿用卡片的`main_type=6`，结算不进入随机宝箱池 |

背包说明文案：

> 使用后主角等级提高1级，保留已有修为，并获得正常升级奖励。主角达到99级后不可使用。每次使用1张。

## 3. 玩家操作与结果

1. 获得等级卡后，打开背包道具页。
2. 选择“等级卡”，查看说明并点击使用。
3. 成功后扣除1张，主角升1级，背包和角色属性同步更新，触发现有升级奖励弹窗。
4. 剩余数量大于0时继续保留该堆叠；最后1张使用后移除背包实例。

即使持有100张，点击一次也只提交1张，不出现批量数量选择框。达到99级后客户端提示“主角已达等级上限，等级卡未消耗”；服务端也会独立校验上限。

### 3.1 修为如何保留

设使用前等级为`L`、当前修为为`E`、从`L`升到`L+1`所需修为为`T(L)`：

```text
使用前：等级 L，当前修为 E
等级卡：通过现有升级入口增加 T(L) 修为
升级扣除：T(L)
使用后：等级 L+1，当前修为仍为 E
```

因此卡片的价值随当前等级变化，不是固定经验道具。保留的是修为数值；下一级所需修为改变后，经验条百分比可能下降。

| 使用前 | 使用后 | 道具变化 |
|---|---|---|
| 19级、37修为、2张卡 | 20级、37修为 | 剩1张 |
| 20级、0修为、1张卡 | 21级、0修为 | 卡片移除 |
| 98级、37修为、2张卡 | 99级、37修为 | 剩1张 |
| 99级、任意合法修为、1张卡 | 请求被拒绝，等级和资源不变 | 仍为1张 |

服务端要求使用前修为处于当前等级的合法区间，且该修为小于下一级阈值。这样即使未来修改经验表，也不会因为一次用卡而意外连升多级。异常存档会被拒绝使用，不通过吞掉修为或多扣卡来修正。

### 3.2 升级奖励与功能开放

等级卡共用`progression.add_exp()`，不会另建一套升级奖励。当前奖励规则详见[主角升级系统与升级奖励实现说明](主角升级系统与升级奖励实现说明.md)。例如：

| 升级过程 | 小包子1020 | 元宝 | 大传世金卡1152 |
|---|---:|---:|---:|
| 9→10 | 2 | 100 | 0 |
| 19→20 | 3 | 100 | 1 |
| 20→21 | 3 | 20 | 0 |
| 69→70 | 8 | 100 | 2 |
| 98→99 | 10 | 20 | 3 |

这些奖励随`server_config/progression_rules.json`变化，不在等级卡模块内重复硬编码。奖励自动入账，并沿用已有领取水位防止重复发奖；旧档历史等级不补发。

角色等级、剩余修为、下级所需修为、阵位数及背包通过现有同步流程更新。依赖主角等级的玩法继续读取更新后的等级；其他解锁条件仍需满足。等级卡不替代任务、旅途通关或新手引导，也不直接提高神仙、宠物和装备等级。

## 4. 唯一获取途径：激活码礼包

**等级卡只能通过激活码礼包获取。** 商城购买、九幽及九重天兑换、活动奖励、战斗掉落、宝箱、合成、签到、升级奖励、邮件附件和测试版自动福利均不作为等级卡来源。本次没有向真实账号自动发放等级卡，已有库存保留，后续新增库存必须通过激活码兑换。

### 4.1 三档礼包与激活码

| 礼包 | 激活码 | 奖励 | 领取限制 |
|---|---|---|---|
| 等级卡礼包·10张 | `7KIEGUOTCKQN` | 等级卡×10 | 每账号一次 |
| 等级卡礼包·20张 | `K1MJI3166RT4` | 等级卡×20 | 每账号一次 |
| 等级卡礼包·50张 | `CUTWP96BZCKY` | 等级卡×50 | 每账号一次 |

三档均已写入`server_config/gift_code_rules.json`，启用且可兑换，永久有效，不绑定指定账号／角色／服务器，沿用本地激活码系统。同一账号每档只能领取一次，三档领取组独立，可以分别领取，共获得80张。`max_uses=0`表示没有跨账号总领取次数限制，不代表同一账号可重复领取。

这些激活码属于本地离线版本，不是官方兑换码。代码固定保存在配置中，重启不会重新生成；大小写不敏感，首尾空格会被去除。礼包只有等级卡，没有附送其他材料、元宝或银两。

领取路径：重启本地服务并重新登录 →「其他功能 → 兑换码」→ 输入激活码 → 奖励进入背包。99级主角仍可兑换礼包，已领取的卡片保留在背包，但无法突破99级上限。礼包领取不会自动使用卡片，每张仍需单独点击使用。

### 4.2 发放约束

三档奖励配置分别为`[5,1901,10,1]`、`[5,1901,20,1]`、`[5,1901,50,1]`；四项依次为对象类型、道具模板ID、数量、物品等级。上述条目仅用于激活码礼包，不能复制到游戏内其他奖励配置。

服务端采用两层约束：

1. 普通发奖入口`summon.add_item`、`journey.grant`、`equipment_crafting.grant`对1901执行来源检查，普通宝箱、活动、商店等调用会被拒绝。仅激活码模块完成资格校验后，通过专用入口临时授权该角色领取；授权在发奖结束或异常时立即解除。
2. `Backend.save`在最终保存前核对等级卡总量。默认不允许增加；成功激活码兑换才从本次兑换账本提取可发放数量，并与库存一起提交。即使某条业务绕过普通发奖函数直接追加背包，也不能保存新增等级卡。

这也适用于将1901误填入未来活动／邮件／商店配置的情况：错误发放会被拒绝，不会成为新的获得渠道。内部专用函数与保存授权参数只能由服务端代码调用，网络请求不能传入这些授权。该限制针对正常游戏结算，不宣称防止直接修改离线数据库或程序源码。

### 4.3 防重复、失败与旧档

沿用激活码系统的账号＋兑换码、账号＋领取组唯一约束。重复请求不重复发卡，重启后已领取记录仍然有效；兑换编码或保存失败时，库存和兑换账本一起回滚，可以重新兑换。旧77码及其领取组、奖励保持不变，当前配置共80码。

更新不会删除已有等级卡，也不会重新发放历史已领取礼包。桌面服务端重启生效；独立离线APK需重新打包安装，本次尚未发布新APK。

## 5. 请求校验与存档

### 5.1 使用协议

沿用`1051 / msg_use_item`，请求字段如下：

| 字段 | 要求 |
|---|---|
| `serial_num` | 由原客户端请求系统生成 |
| `item_type` | `1901` |
| `item_id` | 当前账号背包中的等级卡实例ID |
| `item_count` | 整数`1` |
| `des_type` | `1`：主角 |
| `des_id` | `0`或当前主角ID |

服务端拒绝库存不足、实例不存在、冒用其他道具、锁定或装备关联状态、异常物品等级、错误使用对象、批量数量及满级使用。服务端不依赖客户端按钮限制。

成功时返回现有事件`21`（道具使用结果），并由升级框架生成事件`2`（升级及奖励列表）。属性、物品增减和背包同步先于事件2发送，事件2先于事件21发送。原客户端处理事件2时只记录待升级标记和奖励，不会在背包中主动打开升级面板；因此客户端在1901的事件21成功回调中刷新背包，并在存在待升级信息时调用原版`playerLevelUp`，将升级面板挂到当前场景上，显示本次等级变化与正常升级奖励。该入口会清除待升级标记，避免返回主界面或重复成功回调时再次弹出。使用失败或没有待升级事件时不打开面板，也不套用要求`attach_list`的普通礼包回调，避免出现空奖励窗口。

### 5.2 扣卡、奖励与防重复

使用逻辑在现有Backend提供的角色副本上完成；响应生成成功后才保存。校验或响应编码失败时，不提交本次等级、奖励或道具消耗。

沿用现有请求串号防重机制：同一会话内重发同一个请求返回缓存响应，不重复升级或扣卡。新的合法请求是一次新的使用操作，持有剩余卡且未满级时可以继续升级。不能把会话缓存理解为跨重启永久保存的请求ID。

无需增加存档字段：等级卡放在`attachments`中；等级与修为使用`level`、`cur_exp`、`next_exp`；阵位使用`cortege_count`；升级奖励水位仍使用`progression.rewarded_level`。更新不会清空原有背包，也不重置升级奖励记录。
