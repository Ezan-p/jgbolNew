# 阵容与包裹修复：配置补齐与协议说明

记录日期：2026-10-24。适用范围：本项目当前 3.87 游戏内容、360 渠道登录桥接及本地离线后端。

本文依据当前 [backend.py](../network_redirect/backend.py)、[protocol.py](../network_redirect/protocol.py) 与客户端 Lua 静态分析记录整理。配置值属于本地最小初始化方案，不能当作恢复出的官方服务器配置或完整玩法参数。

## 1. 本次究竟补了什么

本次修改包括公共配置、角色存档字段及响应协议三部分。包裹问题并非仅靠增加一个配置开关解决。

| 类别 | 修复前 | 修复后 |
|---|---|---|
| 公共配置结束标记 | `config_end=false` | `config_end=true`，执行客户端最终初始化 |
| 公共配置节 | 只有 `[24]` 的最小内容 | 新增 `[4]`、`[5]`、`[10]`、`[11]`、`[14]`、`[15]`；保留 `[24]` |
| 角色阵容容量 | 存档缺少 `cortege_count`，编码后为 0 | 根据角色等级读取 CSV，一级为 2 |
| 包裹存档 | 缺少明确的物品列表初始化 | 缺字段时写入 `attachments=[]` |
| 包裹数据下发 | 只有 `1034` 伙伴列表 | 增加 `1035` 物品列表，空列表也下发 |
| 查询完成 | 没有完整的界面通知与结束消息 | 补充 `2998/event 1` 与 `1106` |
| 响应序号 | 直接使用请求编号，多包可能编号重复 | 独立、连续的服务端编号及重传缓存 |

原有沙悟净伙伴记录不是本次新增的配置。本次保留它，并让阵容页面能够完成初始化和显示。

## 2. 为什么需要把 config_end 改成 true

配置通过 `2998` 消息、事件号 `80` 发送，客户端接收路径为：

```text
Backend.bootstrap()
  → 2998 / event 80
  → data.callback_update_config
  → 合并到 g_new_config
  → config_end == true
  → data.set_g_new_config()
  → 各界面初始化公共状态
```

修复前仅下发：

```lua
{
    [24] = {vip_shop={had_gift=false}, buff_data={buff_type=0}},
    config_end = false
}
```

这能提供主界面部分需要的数据，但一直不执行最终配置初始化。阵容页面创建头像栏时调用 `cheerSquadUI.canJoin()`；其 `g_self.Lv` 尚未赋值，于是访问 `Lv[1]` 报错，后续界面创建中断。

对应链路是 `mainUI → charPositionUI.show/create/createHeader → cheerSquadUI.canJoin`。日志中的直接错误为 `attempt to index field 'Lv' (a nil value)`。

`Lv` 由 `cheerSquadUI.initCost()` 从 `[14].cheer_level_limit` 取得；`isOpen` 从 `[14].is_open` 取得。`canJoin()` 只有在 `isOpen == false` 时才提前返回，未初始化的 `nil` 不能替代 `false`。

因此必须同时补齐初始化所需的配置节，并将 `config_end` 置为 `true`。只增加 `[14]` 却继续发送 `false`，不会执行这一步初始化；只改结束标记而不补齐其它必需节，又会在统一初始化过程中访问其它缺失字段。

## 3. 修复后的完整公共配置

以下内容与 `CLIENT_CONFIG` 一致：

```lua
{
    [4]={party_top_list={},pay_consume_gold=0},
    [5]={},
    [10]={panic_buy_list={},cheap_item_list={},rich_item_list={},limit_item_list={},
          item_begin_time=0,item_end_time=0,server_time=0},
    [11]={open_flag=false,min_role_level=60},
    [14]={cost_item_count={},cost_gold_count={},is_open=false,cheer_level_limit={},
          is_open_ni=false,open_cheer_item={}},
    [15]={adaptive_visible=false},
    [24]={vip_shop={had_gift=false},buff_data={buff_type=0}},
    config_end=true
}
```

这里的 `[10].server_time=0` 是代码模板占位值。`bootstrap()` 在发送前将它替换成 `int(time.time())`，实际发送的是当前 Unix 秒时间戳；`item_begin_time` 和 `item_end_time` 仍为 0。

数字配置编号来自客户端 `client_config_type`。它们是事件载荷内的配置分类编号，不是网络消息号。

### 3.1 `[4] party_fight`：公共初始化所需的战斗活动配置容器

| 字段 | 当前值 | 用途 |
|---|---|---|
| `party_top_list` | `{}` | 提供空排行榜容器，供 `worldBossUI.g_topList` 初始化 |
| `pay_consume_gold` | `0` | 为 `getGoldConfig()` 所读取的消耗参数提供明确数值 |

虽然本次修复目标是阵容，统一配置初始化仍会读取该节，因此需要提供。这里的 0 是本地初始化值，不表示相关活动已实现或可以免费参与。

### 3.2 `[5] order_config`：订单／充值价格配置容器

当前值为 `{}`。配置初始化末尾处理充值 CSV 时会索引服务器价格配置表，空表使“没有提供价格覆盖项”成为可处理状态，而不是对 `nil` 进行索引。

本次没有新增商品、支付渠道或充值处理逻辑。

### 3.3 `[10] shop_items`：商城列表初始化

| 字段 | 当前值 | 用途 |
|---|---|---|
| `panic_buy_list` | `{}` | 空抢购列表 |
| `cheap_item_list` | `{}` | 空优惠商品列表 |
| `rich_item_list` | `{}` | 空商品分类列表，保留客户端原字段名 |
| `limit_item_list` | `{}` | 空限时商品列表 |
| `item_begin_time` | `0` | 本地初始化的时间字段 |
| `item_end_time` | `0` | 本地初始化的时间字段 |
| `server_time` | 发送时的当前时间戳 | 提供服务器时间参考 |

`set_g_new_config()` 会调用 `shopUI.loadGoods()`，该函数需要可遍历的列表。这里提供空列表是为了完成初始化，没有恢复商城货品，也没有实现购买与扣费。

### 3.4 `[11] stone_config`：灵石功能状态

| 字段 | 当前值 | 客户端状态 |
|---|---|---|
| `open_flag` | `false` | 初始化 `stoneUI.g_self.isOpen`，明确关闭 |
| `min_role_level` | `60` | 初始化 `stoneUI.g_self.Lvlimit` |

`60` 是当前本地方案提供的占位门槛，不是此次考证得到的官方解锁等级。在 `open_flag=false` 的配置下，不代表到达 60 级会自动开启功能。

### 3.5 `[14] cheer_data`：直接解决阵容崩溃的助威配置

| 字段 | 当前值 | 作用 |
|---|---|---|
| `cost_item_count` | `{}` | 助威物品消耗配置容器 |
| `cost_gold_count` | `{}` | 助威金币消耗配置容器 |
| `is_open` | `false` | 初始化 `isOpen`，让 `canJoin()` 在功能关闭时直接返回 |
| `cheer_level_limit` | `{}` | 初始化 `Lv`，避免它完全不存在 |
| `is_open_ni` | `false` | 明确关闭该配置中的另一助威功能分支 |
| `open_cheer_item` | `{}` | 提供助威开启物品配置容器 |

关键不是单独把 `Lv` 填成空表：空表的第一个元素仍是 `nil`。当前方案依赖 `is_open=false` 先关闭该分支，从而不读取等级阈值。以后若要开放助威，需要补齐真实的等级与消耗规则，不能只把布尔值改成 `true`。

### 3.6 `[15] adaptive_spirtit`：万能魂魄相关初始化

客户端枚举原名为 `adaptive_spirtit`，这里保留其拼写。当前发送 `{adaptive_visible=false}`，为 `soulExchangeUI.initData()` 提供一个可遍历的配置表，并携带关闭可见性的标志。

这里记录的是实际载荷和初始化目的，不代表已经验证了魂魄兑换全流程。客户端枚举中另有编号 `[16]`、名称 `adaptive_visible`；本次代码没有新增 `[16]`，不要将其与 `[15]` 表内的同名字段混为一谈。

### 3.7 `[24] common_config`：保留既有主界面配置

| 字段 | 当前值 | 说明 |
|---|---|---|
| `vip_shop.had_gift` | `false` | 保留此前的 VIP 商店礼物状态初值 |
| `buff_data.buff_type` | `0` | 保留此前的 buff 类型初值 |

这两个字段修复前已经存在，不应计入本次新增字段。它们在最终配置中继续保留。

## 4. 角色存档补齐规则

### 4.1 `cortege_count` 是阵容容量，不是伙伴总数

后端加载 [role_level_config.csv](../analysis/configs/role_level_config.csv)，构建 `FORMATION_SLOTS[level]`。

新角色默认等级为 1，因此角色快照 `1017.cortege_count=2`。旧存档只有在缺少该字段时才按其当前等级补齐，并写回 SQLite；已有字段不会被此次迁移覆盖。

两个同名协议字段必须区分：

| 字段位置 | 含义 | 当前本地角色 |
|---|---|---|
| `1017.cortege_count` | 角色可上阵槽位数量 | 2 |
| `1034.cortege_count` | 此次伙伴列表的记录数量 | 1 |

当前初始伙伴沙悟净仍为 `id=1`、`type=5004`、`order=1`。它占用第一个阵位；第二个阵位为空，不是伙伴丢失。点击空位时出现“暂无可用神仙”，表示没有未上阵的候补伙伴。

此迁移不等于已经实现角色升级。未来实现升级时，还需要在等级变化后更新阵容容量；当前迁移只处理字段缺失。

### 4.2 `attachments`：包裹物品列表

新角色写入 `attachments=[]`；旧角色仅在字段不存在时补为空列表。已有物品列表、伙伴、名字、等级、货币及其它存档字段均保留。

数据位于 `.runtime/offline/game.sqlite3` 的 `roles.data` JSON 内，没有新增独立的物品数据库表。`attachments()` 从该列表生成 `1035` 消息。

当前存档确实没有物品，所以包裹显示分类和空列表。本次没有为了让界面看起来有内容而添加演示装备。

迁移前备份：`.runtime/offline/backups/before-formation-bag-fix.sqlite3`。

## 5. 包裹还补齐了哪些协议行为

### 5.1 空包裹也必须发送快照

新增 `1035` 物品快照：

```text
serial_num = 0（登录初始化时）
first_send = true
attach_count = 0
attach_list = []
```

客户端通过这条消息初始化 `g_packageItemsInfo` 及物品分类。“没有物品”和“尚未收到物品数据”是两种不同状态，因此不能省略空列表响应。

协议定义使用 `attach_count=b`，此前数组编码、解码只允许大写 `B` 作为前导计数。本次让两处检查同时接受 `B` 和 `b`，保持原有单字节数值编码规则。

### 5.2 登录与重连的初始化顺序

```text
2998 / event 80：公共配置，config_end=true
1017：角色快照，包含阵容容量
1034：伙伴列表
1035：包裹物品列表
```

登录成功的 `1002`、重连成功的 `2996` 分别位于各自初始化序列之前。初始化消息不主动打开包裹页面。

### 5.3 查询不仅需要列表，还需要完成通知

对于带正请求序号的 `1033` 查询：

```text
1034：伙伴列表
1035：物品列表
2998 / event 1：界面更新通知
1106：本次请求处理结束
```

当前后端将查询的 `flag` 放入事件数据 `{flag=...}`；此次实测包裹查询为 `flag=1`，对应打开包裹。不要把 `1033.flag` 理解成能唯一识别所有点击入口的页面编号：客户端多个入口也会使用 1。

`1106` 触发客户端释放等待、处理缓存响应，并允许发送后续请求。只收到列表而没有结束通知，仍可能在约 10 秒后超时。

## 6. 响应编号与重传修正

请求序号与响应序号具有不同含义。服务端计数从 200000 初始化，第一条编号响应为 200001；每条响应独立递增，包括界面事件和 `1106`。

例如请求编号为 100001：

| 响应 | 服务端 `serial_num` | 关联请求 |
|---|---|---|
| 1034 | 200001 | 本次查询数据 |
| 1035 | 200002 | 本次查询数据 |
| 2998 | 200003 | 本次查询的界面通知 |
| 1106 | 200004 | `req_serial_num=100001` |

之前多条响应复用请求编号，会被客户端判断为重复包。请求序号为 0 的查询继续使用零序号响应，不追加 `1106`，也不消耗服务端编号。

`1105.req_serial_num` 表示客户端最后接收的服务端序号。后端缓存最近 256 条编号响应，重传时保留原始字节和原序号，不重复编号或额外追加完成消息。若没有遗漏，发送新的 `1106(req_serial_num=0)` 结束重传等待。客户端一个编号包也未收到、最后接收序号仍为 0 时，只要缓存仍保留从 200001 开始的完整内容，也能整批重放。

计数及缓存跨 TCP 重连保留，新登录重置；缓存范围外的请求记录 `game_replay_unavailable`。这仍是单个本地账号的有限缓存实现。

## 7. 验证结果与实现边界

本次修复完成时，36 项回归测试通过，覆盖配置初始化、存档迁移、空及非空物品编解码、连续序号、请求结束、重连重传、TLS 和服务端生命周期。

原客户端实测结果：阵容可显示沙悟净头像、立绘及属性；包裹可打开并切换分类；重连后再次查询成功，最终等待标记为 `false`。
