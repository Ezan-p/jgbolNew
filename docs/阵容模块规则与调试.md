# 阵容模块规则与调试

初次记录日期：2026-10-24；接入状态复核：2026-10-26。适用版本：原版 3.87 游戏资源、当前 360 登录桥接、本地离线后端。

本次解决了“换将请求无结算”和“伙伴没有自带法术实例”两个直接问题，并接入阵位调整、装备／法术穿卸、强化、装备注灵／升阶、培养、经验升级、传承、魂魄合成、飞升和飞升回收。没有改写这些玩法的原版客户端 Lua。

本文不是官方服务器规则还原声明。客户端不包含完整服务端程序，不能从界面反推出所有概率、属性合成公式和返还规则。每项依据分别标记：

- **【A】原版客户端规则**：能在原始 APK 的协议、Lua 字节码或 CSV 中直接复核的内容。客户端显示值不自动等于已验证的官方服务端结算。
- **【B】推测规则／本地实现选择**：缺少官方服务端证据，按用户授权实现的结算、配置、容错或迁移行为。

代码：[formation.py](../network_redirect/formation.py)、[backend.py](../network_redirect/backend.py)、[summon.py](../network_redirect/summon.py)。推测配置：[formation_rules.json](../server_config/formation_rules.json)。专项测试：[test_formation.py](../tests/test_formation.py)。

## 1. 故障原因与修复

| 问题 | 原因 | 本次处理 |
|---|---|---|
| 点击上阵／换将没有结果 | 后端没有处理 `1024`，客户端一直等业务完成 | 校验阵位、原子更新伙伴、下发列表与原版事件，最后发 `1106` |
| 神仙缺自带法术 | 伙伴 CSV 虽有 `chushijineng`，旧存档没有对应的 `attach_type=6` 实例 | 登录、召唤、合成后补齐；保存法术 ID、等级和固有归属 |
| 换将后法术留在旧阵位 | 自带法术需与持有者一起迁移 | 自带法术根据神仙 ID 绑定，换将／调序后同步位置 |
| 召唤后法术可能再次消失 | 原扣材料清理按 `count>0` 保留物品，误删数量为 0 的法术 | 清理只删除耗尽的物品栈，保留法术实例 |
| 升级／培养后面板可能仍持有旧值 | 原版窗口保留旧伙伴对象，全量列表替换不能更新这些引用 | 先发 `1032` 伙伴属性变化，再发完整列表，最后触发界面回调 |
| 背包／伙伴过多无法编码 | 把单包 255 条限制当成账号容量；新增自带法术加速触发 | 按 128 条分包，首包清空、后续包追加 |
| 重发造成重复消费 | 原业务缺少请求幂等保护 | 同一请求序号及内容重放原响应；冲突、过期请求拒绝 |
| 非法操作可能扣一半材料 | 多项扣除、校验、编码未形成一个结算边界 | 在脱离数据库的角色副本上结算，业务响应全部编码成功后才保存 |

【B】存档迁移会重算当前已实现的基础属性及战力，并按原表刷新可上阵数量；并非逐字节保留旧角色 JSON。姓名、货币、伙伴 ID、等级、已有自带法术等级、魂魄等进度保留。未知类型伙伴保留原记录。测试操作结束后，已将实际存档阵位恢复到调试前的“沙悟净在一号位”。

## 2. 原版规则与推测规则对照

### 2.1 换将、上阵与调序

**【A】** `1024` 字段为 `serial_num, flag, count, change_info[{id,new_order}]`，数组上限 8。`charPositionUI` 的换将使用 `flag=4,count=1`，调序使用 `flag=5`；旧 `formationUI` 还使用 `flag=0`。完成事件为 `2998/event 1`，保留原 flag，分别进入原版换将／换位回调。

**【A】** 阵位开放数量来自 [role_level_config.csv](../analysis/configs/role_level_config.csv) 的 `cortege_count`；它与 `1034.cortege_count`（当前包记录数）不同。

**【B】** 单人换将：新伙伴进入目标阵位，原目标伙伴退到新伙伴此前位置；候补位置为 0。普通装备及可替换法术留在该阵位；自带法术跟随神仙。调序则让普通装备及法术随原阵位持有者一起移动。

**【B】** 服务端拒绝不存在的神仙、重复神仙、重复阵位、未开放阵位、助威与上阵冲突；调序后至少保留一名上阵神仙。整批请求同时验证、同时提交。

### 2.2 自带法术与穿卸

**【A】** [cortege_base_0.csv](../analysis/configs/cortege/cortege_base_0.csv) 的 `chushijineng` 指向 [skill_base.csv](../analysis/configs/skill_base.csv)。自带法术使用 `attach_type=6,protogenic=1,equip_pos=1`；另两个法术槽为 2、3。沙悟净 `5004` 对应 `209` 六魂幡；阎罗王 `5001` 对应 `207` 天罗地网。

**【A】** 法术起始等级、最高等级、效果字段和每级增量来自 `skill_base.csv`。原版法术升级界面把法术记录的 `count` 读作失败补偿，不是堆叠数量；因此 `count=0` 是合法法术记录。

**【A】** 穿卸请求 `1037` 包含 `obj_type,src_id,src_order,des_order,des_equip_pos,flag`。原版阵容页使用 `flag=3`。装备主类型 1、2、3 分别为武器、防具、法宝；槽位按 `item_base.csv.equip_pos`。

**【B】** 为所有已拥有神仙建立唯一的自带法术，包括候补；内部字段 `innate_owner_id` 固定归属，不写入原协议。迁移优先复用已有自带法术 ID 和等级，避免每次登录创建一份。自带法术不可卸下、替换、转交或作为升级材料。

**【B】** 普通法术同一神仙不允许重复类型；同槽替换会自动卸下旧物品。请求中的旧阵位必须与存档一致，防止旧页面误操作。

### 2.3 装备强化

**【A】** `1052` 请求单次或批量强化，结果走事件 2 的 `obj_type=5,upgrade_list`；每个结果含旧等级、新等级、装备 ID、效果值。银币费用按 [equip_enhance_cost.csv](../analysis/configs/equip_enhance_cost.csv) 的当前等级和品质读取。

**【A】** 原版强化上限是角色等级的 **2 倍**，并受物品 `top_level` 限制；`equipmentUpgradeUI` 对应乘法常数池为 `[2,0.5]`。批量按钮要求 VIP3。

**【A】** [equip_enhance_weight.csv](../analysis/configs/equip_enhance_weight.csv) 包含升级 1／2／3／4／5 级及权重 70／15／7／5／3。

**【B】** 本地按该权重抽取每次增加等级，触顶截断；一次批量最多尝试 10 次。银币不足或达到上限后停止后续尝试，保留本批已完成结果；一项也不能完成则拒绝，不扣款。批量次数及权重的服务端实际采用方式缺少官方运行证据。

### 2.3.1 装备注灵与升阶

**【A】** `1073.flag=1` 是注灵，`flag=2` 是升阶；包含 `equip_id,equip_order,is_one_key`，完成事件为 `115`，载荷 `flag,result=1`。物品进度字段是 `advance_level,star_count,cur_spirit_count`。四／五星装备的每星注灵量取 `equip_star_cost.csv`，升阶材料取 `equip_advance_cost.csv`，增益取 `equip_advance_worth.csv`。

**【A】** 武器／防具／法宝注灵材料分别为 `1310/1311/1312`；客户端初始化默认每次 5 个，服务端配置 `[23]` 可覆盖。原增益 CSV 重复使用 `star1_worlth` 等列名，必须按列位置解析，不能用同名键覆盖。

**【B】** 缺少原服务端开关及门槛，当前配置开放，角色 60 级可用，10 阶封顶，每阶先注满 7 星。一个材料增加一点注灵进度，普通点击最多消耗 5 个，一键补满下一星；尾数按实际所需扣除。注满后才能扣除下一阶材料，升阶后星数和进度归零。装备加成按基础强化效果乘 `(1+percent)` 再加 `plus`；关键阶的 `extra` 作为对应神仙属性的额外百分比，取已达到阶数中的最高值，属于推测叠加顺序。

**【B】** 强化／注灵／升阶使用原版 `1032` 增量更新，不替换当前装备表对象，确保在同一窗口连续点击时进度刷新。材料耗尽也以原版数量更新删除。登录及主动刷新仍下发完整物品快照。

### 2.4 法术升级

**【A】** `1071.data` 是 Lua 字面量表，字段为 `des_skill_id,src_skill_list`。客户端升级率显示逻辑为：

```text
min(100, floor(材料总价值 × 100 / 当前等级升级成本) + count补偿)
```

材料价值取 [skill_enhance_worth.csv](../analysis/configs/skill_enhance_worth.csv)，成本取 [skill_enhance_cost.csv](../analysis/configs/skill_enhance_cost.csv)。品质及等级上限来自 `skill_base.csv`。结果事件 2 使用 `obj_type=6,obj_id,old_level,new_level`。

**【B】** 本地将显示率用作成功概率：成功升 1 级并清零补偿；失败不升级、补偿加 1（最多 100）；两者都消耗提交的合法材料。只接受未装备、未锁定、非自带的其他法术，禁止重复 ID、自吞及空材料列表。最大 500 个材料 ID 是本地输入限制。

**【B】** 只解析字面量，不执行收到的 Lua。客户端不能用表达式调用系统命令，也不能自行指定成功或结算属性。

### 2.5 培养、十次培养、精心培养与定向培养

**【A】** 角色 5 级开放培养；请求 `1081`、确认／放弃 `1082`，回调事件 4。普通单次 5 蟠桃、1 潜力，精心单次额外 1 元宝、使用 3 潜力；十次对应 50 蟠桃和 10／30 潜力，精心十次另需 10 元宝。

**【A】** 预览不是最终属性。原回调字段为 `train_result,increase_field,decrease_field,train_point`；结果号 1 预览、2 保存、3 放弃。培养属性编号为生命 86、法力 87、攻击 88、防御 89、潜力 90。

**【B】** 缺少随机分布和负向洗点配置，本地均匀随机选择生命／攻击／防御／法力之一，将本次潜力等量转为该属性，不扣其他已培养属性。十次合成一次预览。发起时扣蟠桃和元宝，确认时才扣潜力、增加属性；放弃不返还消耗品。未确认结果持久化，重连后仍可保存或放弃，不能覆盖旧预览。

**【A】** 定向培养使用 `1089`，`train_field=1/2/3/4` 对应生命／攻击／防御／法力。原版道具 ID 为 `1343`，`direct_rate=5`，结果事件 176。

**【B】** 每个定向培养道具转换 5 潜力，神仙等级须高于 1；点数必须为正的 5 倍数，且不能超过潜力。待确认普通培养存在时禁止定向培养。

### 2.6 经验书、经验丹与神仙升级

**【A】** `1059` 使用 `first_send=true,flag,cortege_id,roll_list[{type_id,count}]`，结果事件 65。经验书页 `flag=1`，物品 `sub_type=99`；经验丹页 `flag=2,sub_type=100`，角色 65 级开放。物品经验取 `item_base.csv.experience_plus`；不能以 `use_target=4` 判断是否经验书，原表这些书的值为 0。

**【A】** 按 [cortege_experience.csv](../analysis/configs/cortege_experience.csv) 的品质和当前等级逐级结算。原版 `expbookUI.getExpResult`：角色低于 80 级时，神仙等级达到 `floor(角色等级×2.5)` 后经验效率为 20%，达到角色等级 3 倍后为 0；角色达到 80 级后采用全额经验。基础上限 200，洞府主建筑配置提供附加上限。

**【B】** 本地默认洞府附加上限 0，可由存档 `cortege_limit_plus` 提供；每升一级增加 5 潜力。整个请求的材料先验证并一次结算，错误不扣书；升到上限的溢出经验不保留。经验效率逐级判断，可在一次请求中跨过降效阈值。

**当前边界（2026-10-26）：** `1059/flag=3` 属于药神殿药灵丹，已由 `Backend.respond` 分发给活动模块，并由 `activity_drug.use_exp` 校验70级门槛、目标、数量和药品类型后结算炼药经验；它不走普通神仙经验书分支。详见[活动模块规则与调试](活动模块规则与调试.md)。

### 2.7 传承

**【A】** `1025` 使用神仙实例 `src_id,des_id`，完成事件 8。原版计算为接收方已有经验加上传出方自 1 级累计的全部经验；接收方选择门槛是等级低于角色等级 **2 倍**（`inheritUI` proto21 常数池 `[2,1,0]`），最高 200 级。两名神仙不能相同，等级 1 且经验 0 的神仙不能作为传出方。

**【A】** 原版预览包含传承道具 `1002` 和已培养属性的蟠桃返还显示；返还算式 `floor(培养属性总和/5×10×0.5)` 等于培养属性总和。

**【B】** 本地扣 1 个传承道具，转移全部经验。传出方回到 1 级、0 经验、清除培养加点，保留自身 ID、阵位、自带法术等级和飞升等级；剩余潜力仅保留飞升所得。接收方升级每级增加 5 潜力。传出方是否应被销毁、各类高级养成返还方式缺少官方服务端依据，本地采用可继续使用神仙的重置方案。达到 200 级后不保留溢出经验。

### 2.9 属性、仙缘与战力

**【A】** 基础属性、等级成长系数、装备基础加成与强化增量、法术效果来自原表；仙缘触发目标和百分比来自 [fate_config.csv](../analysis/configs/fate_config.csv)。原版仙缘区会展示这些配置。

**【B】** 当前属性由 `combat_power.recalculate` 统一重建，已纳入成长／培养、飞升、装备与灵石、被动法术、转生／经脉、觉醒／命星、仙缘、收集、称号、洞府、宠物、八卦助阵和灵阵。早期仅累加基础装备的简化顺序不再代表现状。伙伴仙缘要求相关神仙在上阵／助威集合中，装备／法术仙缘要求该神仙所在阵位持有目标物品；各系统叠加与取整的本地策略见[单神仙与总战力实现说明](单神仙与总战力实现说明.md)、[灵阵说明](灵阵系统原版规则与修复说明.md)。

**【B】** 当前采用V1.1评分：`floor(3×攻击 + 2.5×防御 + 1.5×法力 + 0.2×生命 + 有效精魄分E)`；角色当前总战力为1—8号上阵神仙评分之和，历史峰值另存。已接入的宠物、转生、命星、灵石及灵阵会通过属性或战斗效果参与结算，不再列为未接入。评分权重、组合规则及部分属性叠加仍是本地推测，不能据此认证原服公式。

### 2.10 锁定、事务和重连

**【A】** `1343.flag=1` 锁定、`flag=2` 解锁，`des_id` 是物品 ID，结果事件 193。不是 `0/1`。

**【B】** 本地锁定物品不可被当作强化／培养材料消费；明确选择的强化目标仍可强化。锁定状态持久化。

**【A】** 原协议以独立服务端序号连续编号；`1106.req_serial_num` 结束对应请求；`1105` 请求重传。原数组计数是单包限制，`first_send` 区分清空和追加。

**【B】** 当前单账号后端保存最近 256 个业务响应组的请求幂等记录；响应重传缓存为最近 256 个包。同进程断线重连保留，进程重启后旧登录随机密钥失效，需重新登录。不宣称跨进程“恰好一次”。
