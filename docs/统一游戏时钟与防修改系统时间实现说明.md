# 统一游戏时钟与防修改系统时间实现说明

> **2026-11-09 后续实现：联网北京时间与防改时间处罚（工作区，尚未打入APK）。** 本节为当前生产入口策略。后面的“纯离线策略”和v110记录属于历史版本；已发布v111仍使用前一轮纯离线补时规则。

## 当前：可信联网校时，统一北京时间

### 时间来源与触发

- Android启动与桌面离线服务启动默认创建 `network_time.TimeService`，在打开玩家时钟前尝试一次联网校时。启动最多等待约5.5秒，不因断网无限阻塞。
- 恢复前台时，Lua在已登录连接的2999心跳中携带保留标记 `delay_time=2147483646`。后端只将该值解释为“请求校时”，不接受客户端传来的日期作为时间来源。字段仍是原协议无符号32位整数，没有新增协议号。6秒后再发一次普通心跳取得异步校时结果；再次退到后台或重装补丁时取消旧回调。
- 普通游戏请求会检查是否到了15分钟复核周期；发现系统日期跳变会请求提前核查。前台恢复、失败重试与异常核查均至少间隔60秒，同一时刻只有一轮联网请求。
- 固定向 `https://www.baidu.com/`、`https://www.qq.com/`、`https://www.cloudflare.com/` 发送带随机查询参数的HTTPS HEAD请求，读取响应Date。仅发送通用User-Agent和防缓存头，不上传账号、密码、角色或存档。不会跟随重定向。
- 默认校验证书链和主机名，最低TLS1.2。Android内嵌Python加载系统CA目录，不使用游戏自签的回环CA、不添加用户证书目录，也不关闭验证。系统日期错误到无法验证证书时，校时失败并沿用离线规则；不会用不安全连接强行校时。
- 三个不同来源中至少两个时间在5秒内一致才接受；拒绝缺失／重复Date、带非零Age的缓存响应、错误状态、超过4秒的往返延迟和过期采样。每轮约5秒，网络线程不访问SQLite，每个来源至多保留一个未结束线程。

HTTPS Date代表响应生成时间，依据 [RFC 9110 §6.6.1](https://www.rfc-editor.org/rfc/rfc9110.html#name-date)。证书校验使用 [Python ssl 默认安全上下文](https://docs.python.org/3/library/ssl.html#ssl.create_default_context)。**这是经过TLS验证的多源网页时间校准，不是国家授时中心接口，也不是毫秒精度或带签名的专用授时服务**；来源可能不可用，Date只有秒级精度，接受结果记录误差估计。不能宣称绝对零误差或对Root、Hook和整套存档回滚有效。

### 游戏时间、显示与结算

网络返回UTC时间戳，游戏日历统一采用UTC+8。所有现有后端 `timezone_offset_hours`／`reset_utc_offset_hours` 配置均为8，按原玩法各自的刷新时刻执行；无需修改设备时区。

- 正常校时后，登录 `server_time`、2999心跳以及客户端时钟均使用校准时间；客户端在同步之间使用连续计时，不用系统日期差估算。
- 虚拟机挂起导致连续计时停止时，下一次成功联网校时修正整段偏差；不再受纯离线30天接受上限限制。
- 客户端北京时间小时、分钟、星期／周末判断及 `getShowTime` 日历格式化不受手机时区影响。保留原登录／心跳／生命周期回调与事件表，退出／重进支持重装补丁。
- 断网但仍在同次设备启动内：最后保存的时间＋连续计时增量继续推进。断网且设备重启／计时倒退：不信任系统日期来补发跨重启收益，沿用保存时间并提示待联网校准；恢复联网后自动校正。
- 首次安装且始终无法联网时，没有可信北京时间可用；临时初始值仍来自现有初始化逻辑并明确提示未校准，不将它标为已验证时间。

**未来存档有特殊保护**：网络北京时间可以向前或向后修正显示，已经经过的业务结算时间不回退。`clock.sqlite3` 的 `settlement_floor` 保留最高结算时间；业务 `game_clock.now()` 取它与当前校准时间的较大值，协议显示使用 `game_clock.display_now()`。正常存档两者相同。旧档曾结算到未来时，界面立即显示正确北京时间，相关额度／恢复在北京时间追上之前不会因回拨重新发放，并显示提示；不删除历史领奖键或邮件记录。玩家仍可能看到对应冷却／活动进度暂处未来，这属于保存既有结算历史的明确边界。

### 防改时间与处罚

完整性检查和原有 `TIME-001` 持久化限制继续生效，联网成功不会解封：

1. 角色受保护时间快照与签名记录不一致、时钟主记录被篡改，继续采用原隔离机制；签名损坏或密钥丢失继续停止处理。
2. 首次可信校时建立系统日期与可信UTC的偏差基线，不凭迁移前已有日期错误或未来存档直接认定作弊。
3. 有可信基线后，检测到系统日期偏离连续计时轨迹，并由新一轮双源HTTPS时间确认日期偏差比基线恶化超过300秒，持久化 `network_confirmed_wall_change`，进入原角色 `*` 时间功能限制。连续小幅修改按基线累计；跨重启也核对已有可信基线。
4. 只有本地计时差、网络失败、来源不一致，不新增永久处罚，也不据此发放系统日期带来的收益。正常虚拟机挂起而系统日期与网络一致、自动校时向真实UTC纠正、可信时间修正历史游戏偏差，均不直接处罚。
5. 恢复系统日期、登录、联网成功、跨日跨周与设备重启不会解除已保存处罚。旧版处罚和人工复核限制保留，未提供自动解封接口。

检测的是时间记录异常，并不证明玩家主观作弊；系统自动校时若错误地把日期改得更偏离网络UTC，也可能满足处罚条件。首次联网前改时、两次核查之间改时又恢复、Root／Hook等仍不能可靠识别，但已经接入可信时钟后不能靠普通系统日期前跳推进游戏收益。

## 0. 历史纯离线策略（2026-11-09）

### 0.1 正常退出、关机与补时

- 同一次设备启动：继续使用包含休眠的连续计时，正常退出／强退后重开也按连续计时补算。该路径不受30天上限限制。
- 启动身份变化、身份不可确认或连续计时倒退：比较当前系统时间与上一次持久化观察时间。间隔为0～30天（含30天）且上次没有尚未恢复的系统时间异常时，完整推进游戏时钟。
- 游戏日期推进与各玩法收益上限分离。时钟不将30天内的正常间隔截成几小时；资源、恢复次数与奖励沿用各玩法原有规则和上限。
- 补时仍先提交到 `clock.sqlite3`，再进行角色结算。同目录多账号、再次登录、重复重开或后续业务失败，都不能重新计入已提交的同一间隔。领奖和邮件仍由业务存档的幂等记录保护。
- 游戏时间不倒退，不用当前系统日期直接覆盖已有游戏日期；升级前已经累积的日期偏差不会被自动抹平。

30天是纯离线自动接受间隔的策略边界，常量为 `game_clock.MAX_OFFLINE_GAP`。纯离线无法证明系统日期真实；修改日期后重启并落在接受范围内仍可能获得补算。本版不将此机制描述为可靠联网反作弊。

### 0.2 系统校时、虚拟机挂起与存档异常分开处理

| 情况 | 当前处理 |
|---|---|
| 同次启动的系统日期与连续计时累计偏差超过300秒 | 暂不接受异常日期差，连续计时照常推进，不新增 `TIME-001` 封锁 |
| 虚拟机挂起后系统日期补进时间、连续计时冻结 | 同上；无法证明的挂起间隔暂不补算，恢复后的正常经过时间仍有效 |
| 跨重启系统日期倒退超过300秒，或离线超过30天 | 不补该次间隔，保存原因并重新建立观察基线，后续正常计时／重启可继续 |
| 系统日期在300秒容差内倒退 | 不倒退游戏时间，跨重启按0秒补算 |
| 系统时间异常仍未恢复时发生重启 | 该次跨重启间隔也不自动补算，防止将已暂缓的日期调整转成收益；重建基线后正常运行 |
| 同次启动系统日期恢复到连续计时预测值的容差内 | 清除“当前日期不可信”状态，保留异常记录；不追补曾拒绝的间隔 |
| 时钟主记录被改、签名损坏、密钥丢失、角色时间快照不一致 | 保留原有存档完整性保护，隔离或停止处理 |
| 旧版已经保存的封锁 | 不自动清除。旧记录不能充分排除并存的篡改或人工限制，需要另行复核 |

系统日期异常保存在签名时钟记录的 `deferred_gap`（最近一条）与 `deferred_history`（最近16条）中，包含编号、原因、观察时间、游戏时间和未计入的差值。`wall_untrusted` 表示当前连续计时观察期是否仍有未恢复的偏差。`policy_version=2` 标记新策略，旧时钟数据和密钥原地兼容。

登录、重连与心跳使用原客户端提示事件显示：

> 检测到时间校准或异常离线间隔，该间隔暂未补算；游戏可继续，请检查系统日期。

同一连接对同一异常编号不重复弹窗。保存的未补算记录不会因恢复日期自动发奖，也没有客户端一键补发入口；“暂未补算”表示保留记录待核查，不承诺稍后自动补发。新的系统校时事件不写入角色永久封锁。已有封锁与存档完整性异常继续显示原 `TIME-001`。

## 1. 采用的策略

采用“统一游戏时钟＋同次开机可靠计时＋纯离线严格重启策略”。首次建立时间锚点后，系统日期不再参与玩家收益结算。游戏时间只能通过可信的开机连续计时推进。

```text
同一次设备启动：游戏时间 = 已保存游戏时间 + 连续计时增量
设备重启／启动身份无法连续确认：沿用已保存游戏时间，重新锚定连续计时
```

这里的“可信”指普通用户调整系统日期无法修改计时源，不表示能抵抗 Root、Hook、修改 APK 或恢复整个旧存档。

| 场景 | 当前行为 |
|---|---|
| 把系统时间前调一天、一周、一年 | 不提前恢复资源、不提前刷新日／周额度 |
| 回退系统日期 | 游戏时间继续推进，不倒退，也不等待手机日期追上未来日期 |
| 反复小幅前调 | 所有系统时间差均不计入，不存在阈值内累积套利 |
| 锁屏、后台休眠 | 计入真实经过时间 |
| 关闭、强退游戏后重开，设备未重启 | 启动身份可确认时，按连续计时补算 |
| 设备重启，包括新开机时长大于旧开机时长 | 以启动身份辨别重启，不补算无法确认的间隔 |
| 同一存档目录切换／创建账号 | 共用一个时间锚点，不能重新采信改过的系统日期 |
| 改变系统时区 | 不改变活动时区；沿用现有各业务配置（通常 UTC+8） |
| 时钟记录无效或数据库损坏 | 报错停止相关处理，不自动回退到系统时间或清空时钟 |

**代价：跨设备重启的离线间隔不发收益，游戏日期可能落后现实日期。** 本实现没有联网校准服务，也未增加恢复未知间隔的按钮。首次安装时的日期仍是未验证的初始基准，纯离线无法证明它是真实日期。

## 2. 时钟源与 Android 兼容

实现：[game_clock.py](../network_redirect/game_clock.py)。

- Android/Linux：使用 `CLOCK_BOOTTIME`，包含休眠时间。Python 未公开该常量时，通过 libc `clock_gettime(7)` 读取；读取失败报错，不偷换为墙钟。
- Android 壳每次进程启动、Python 服务启动前写入 `files/clock_boot_id`。优先组合本应用可读的设备标识与系统 `boot_count`（仅本地保存，避免不同设备启动次数相同）；不可用时读内核 `boot_id`；均不可用则生成进程随机身份。
- 为兼容项目保留的旧 Android SDK，`Settings.Global.getInt` 使用反射调用。旧系统没有该 API 时走回退分支。
- Python 内嵌运行时在创建 Backend 前读取启动身份；同一次开机重启应用仍能沿用计时锚点。旧 Java 壳没有桥接标记时，仍可通过内核身份或进程身份保守降级运行；标记存在但内容无效则报错。
- macOS 开发服务使用 `mach_continuous_time`，启动身份取 `kern.bootsessionuuid`。受权限限制读不到身份时降级为进程身份。
- 其他平台使用进程范围单调计时，不承诺跨进程／休眠补算能力。

**保守降级：读不到设备启动身份时，应用重启也会丢弃无法确认的离线间隔；应用仍可运行，不因读取失败改用手机日期。** 本次开发沙箱限制了 macOS 启动身份读取，跨进程连续性由可控时钟源测试覆盖。

平台依据：[Android BOOT_COUNT](https://developer.android.com/reference/android/provider/Settings.Global#BOOT_COUNT)、[Linux CLOCK_BOOTTIME](https://www.man7.org/linux/man-pages/man2/clock_gettime.2.html)。

对应接入文件：[OfflineRuntime.java](../offline_android/java/com/jgbol/offline/OfflineRuntime.java)、[offline_android/backend.py](../offline_android/backend.py)。

## 3. 全局覆盖方式

[Backend](../network_redirect/backend.py) 通过 `@game_clock.bind_backend` 包装业务方法。一次最外层调用只取一个时间快照；嵌套的 profile、save、奖励计算、属性计算共用该值，并在 finally 中恢复上下文。不同存档目录不会串用时间。

原有显式 `now` 参数保持不变，Backend 统一传入 `game_clock.now()`。原来隐藏在底层函数中的直接系统时间读取也已替换。

| 覆盖层 | 业务范围 |
|---|---|
| Backend 所有原 `time.time()` 入口 | 登录、重连、心跳、活动、日常、福利、帮派、VIP、充值、集市、仙灵、旅程、兑换码、成就等 |
| `progression.py` | 新手期、每日体力额度、经验结算中的默认时间 |
| `formation.py`、`combat_power.py`、`role_profile.py` | 战力缓存时间、限时称号及其属性有效期 |
| `equipment_crafting.py` | 周锻造状态、返回的下次重置时间 |
| `reborn_stars.py` | 默认时间路径 |
| `journey.py` | 奖励发放进入家园／灵兽逻辑时的默认时间 |
| `system_mail.py` | 游戏业务上下文内调用的默认时间；人工运营 CLI 的显式时间接口仍保留 |
| 测试版固定账号初始化 | v106／v108 壳使用统一时钟上下文初始化，生成临时种子角色的 Backend 也借用原时钟，不重新读取系统日期 |

登录快照的 `server_time` 和 2999 心跳返回的时间同样来自游戏时钟，已通过真实协议编码验证。原客户端在两次同步之间仍用本地墙钟差值估算显示时间，改系统日期可能造成短暂倒计时偏差，下一次心跳会重新同步；收益始终由后端游戏时间决定。本次未替换原客户端全局时间函数，也未修改客户端日志计时和非收益用途的订单随机标识。

通天塔的每日生命恢复、半小时仙力恢复、商店及限购、周一地图重置、周四榜奖、首次到层时间均沿用原业务规则，但时间来源统一。其他活动原有日／周编号和邮件去重键继续保留。

以下时间不属于游戏收益，保留原用途：账号记住登录凭据的有效期、日志时间、备份文件名，以及单调时钟测量的网络超时、登录票据和性能指标。

单独调用底层纯函数做分析时，仍可传入显式 `now`；无 Backend 上下文时默认时间兼容原分析工具。新增生产入口应通过 Backend 或 `game_clock.scope(clock)` 执行，不能直接绕开统一时钟调用收益函数。

## 4. 存档、事务与性能

每个游戏存档目录新增 `clock.sqlite3`，与 `game.sqlite3` 并列，权限设为 0600。账号共享该文件，程序载荷升级不能覆盖它。

单行时钟记录包含：版本、设备启动身份、连续计时锚点、游戏时间锚点、状态和旧存档时间下限。不写入密码或令牌。

采用独立 SQLite 事务：

1. 最外层业务调用先锁定时钟记录，计算本次游戏时间。
2. 在任何资源结算前提交时钟进度。
3. 业务按既有 `game.sqlite3` 事务保存资源、恢复 tick、日／周状态与奖励领取记录。

独立记录不是跨库原子事务，而是有意采用“时钟先提交、业务后提交”：非法请求或业务回滚不会把时间退回；若时钟提交后进程崩溃，最多丢失无法证明的离线间隔，不会因这份时钟记录重复发奖。奖励本身仍依赖现有业务状态与幂等机制，不把时钟表当作领奖表。

正常推进时，同一游戏秒内只读时钟记录，不重复写入。跨秒或启动身份变化时写入；保留小数计时余量，避免频繁请求丢失累计秒数。SQLite 的写锁协调多账号连接，采样在锁内完成。

没有增加后台轮询、常驻唤醒或联网请求。新增持久化有磁盘开销；本次未做 Android 真机延迟基准，不能宣称零性能影响。

## 5. 旧存档迁移与边界

第一次建立时钟记录时，取系统日期与已识别的旧业务时间下限的较大值。扫描全部角色，识别 `clock`、`*_clock`、`*_recovery_at`，以及现有 UTC+8 的日状态字段（含召唤的 ISO 日期）。不把活动结束时间、称号过期时间当作已经经过的时间。

目的在于保留既有结算历史，避免迁移时退回过去并重置额度。**迁移不能判定旧存档中已经保存的未来时间是否作弊，也不撤回此前收益。** 本次补充时间活动封锁机制：正常／疑似旧档保留；人工复核确认获利后按活动限制；升级后受保护记录不一致则自动限制，详见第8节。 有未来历史的存档会保留相应游戏日期；新时钟建立后不再继续随手机日期前跳。若将来引入可信网络校准，需要另行设计未来历史的修复，不能清空领奖键。

不能通过本机制防止：

- 删除整个应用数据后重新安装并指定初始日期；
- 修改数据库、恢复时钟和角色的整套旧备份；
- 修改 APK、Hook 计时函数、Root 修改系统启动标识；
- 旧版 APK 忽略新时钟记录继续结算。

备份／迁移游戏时应将 `game.sqlite3`、`clock.sqlite3` 与新增的 `time_guard.key`、`clock_integrity.key` 作为同一份停服备份保存；不要只还原其中一份（旧版尚未生成的文件除外，详见第8节）。新设备无法继承旧设备连续计时，按严格重启策略重新建立锚点。

## 8. 污染旧档与时间活动封锁（2026-11-06）

实现：[`time_guard.py`](../network_redirect/time_guard.py)、[`time_guard_admin.py`](../network_redirect/time_guard_admin.py)。仅修改工作区，未操作真实存档、未打包／安装 APK。

### 8.1 判定与处罚

| 情况 | 行为 |
|---|---|
| 正常、未来日期、无法证明获利的旧档 | 统一标记 `legacy_unverified`，保留养成与库存，不处罚；首次登记时间状态基线 |
| 已复核确认异常获利 | 管理入口保存证据说明与活动范围，封锁指定活动；不扣资源、不删角色 |
| 升级后角色时间字段与校验记录不一致 | 视为受保护数据异常，自动封锁该角色已接入的时间功能 `*` |
| 共享时钟数值被直接修改，签名副本仍有效 | 恢复签名副本的游戏时间锚点，持久化隔离标记；目录内角色下次加载时限制时间功能 |
| 仅修改手机日期、正常设备重启（原交付策略） | 原版本沿用统一时钟规则，不因此封锁；工作区新增跳变检测见第9节 |
| 时钟格式损坏、签名副本损坏、已有记录但密钥缺失 | 停止处理并要求恢复完整备份，不能伪造安全锚点继续游戏 |

旧版本没有可信的完整发奖流水，因此**没有实现“凭未来时间自动认定旧档已获利”**。已获利旧档必须提供人工复核依据；没有证据仍归疑似。异常校验表示文件状态不一致，也可能来自只恢复一个文件、外部编辑工具未同步登记，不等于证明玩家主观作弊。

处罚永久保存，不随日／周刷新、登录、进程或设备重启解除。没有客户端解封接口，也没有自动到期解封。不累积可领取的封锁期奖励；当前没有解封功能，如未来增加，必须先重建结算起点并处理去重记录，禁止直接删除封锁字段。

### 8.2 后端覆盖

活动模块通过显式的 `protect(globals())` 接入公共限制层，覆盖角色参数入口；活动主路由额外检查请求所属玩法。封锁活动的操作入口抛出 `formation.Rejected`，客户端复用事件55显示 `TIME-001`；登录时也显示异常提示。

自动准备、恢复、排行、跨周期结算、查询在角色深拷贝上按封锁时刻运行，结果仅用于维持原客户端查询结构，**不写回角色，不实际恢复、刷新、回收或发奖**。预览内调用不会再次复制或处罚；整个预览结束后恢复上下文。查询视图可能展示冻结时点计算出的状态，不代表可领取，实际操作仍被后端拒绝。

覆盖活动总路由及 `activity_*` 角色入口，以及每日、福利、仙盟、集市、召唤、仙灵和周锻造入口。召唤的通用加物品函数、集市通用物品发放及锻造通用材料函数不受展示隔离影响，避免正常主线奖励被吞掉。`*` 表示这些已接入功能，不表示禁止所有角色操作；主线与基础体力计时仍按可信游戏时间运行。

共享计数的旧活动（排行、喂养、拜访、祈福、蟠桃、试炼、天命等）归并为 `activity` 组；月饼／粽子归并 `activity_seasonal`，财神／唐王归并 `activity_spring`，子模块归并所属玩法。这样不会出现封锁一个入口、共享入口仍刷新同一额度的绕过。管理结果会返回归并后的实际范围。

本版以玩法模块或共享组为限制粒度：例如封锁通天塔会同时拒绝塔内移动、购买、恢复、领取等操作；不会只关闭免费领取按钮。新增时间玩法必须显式接入公共限制层并补充请求／邮件来源映射。

邮件按持久化批次键映射来源。封锁通天塔时，其阶段奖、补给、周榜邮件都不能领取；正常运营邮件继续允许领取并保存真实领取标记。已有奖励不删除、不回收。新增自动发奖邮件必须补充来源映射，运营批次不要使用活动保留前缀。

### 8.3 校验、事务与备份

`game.sqlite3` 增加 `time_guard` 表，保存账号绑定的时间字段快照、限制范围、原因、版本、起始游戏时间和 HMAC；密钥为存档目录内 `time_guard.key`，0600权限。校验仅覆盖明确的日／周字段、`clock`、`*_clock`、`*_recovery_at` 等，不对未知字段猜测语义。首次登记不将旧数据异常当作证据。

角色加载在任何资源准备之前验证；判定出的封锁先独立保存，后续请求回滚不会撤销处罚。正常角色保存与时间快照更新位于同一个业务数据库事务，避免进程中断造成双库不同步。限制记录独立于角色JSON，清除角色JSON中的 `time_guard` 不能解除已记录限制。已登记角色缺失对应校验行时按异常处理。

`clock.sqlite3` 增加 `clock_integrity` 签名副本，与主时钟在同一事务提交；密钥为 `clock_integrity.key`。原时钟首次升级只建立基线，不推断作弊。校验副本可识别普通的单独编辑主时钟；签名副本本身不可验证时继续采用停止处理策略。

备份须停服后同时保存 `game.sqlite3`、`clock.sqlite3`、`time_guard.key`、`clock_integrity.key`。不可只恢复角色或只恢复时钟；外部存档工具必须同步维护保护记录。首次升级前的备份可能没有新增文件，恢复应使用完整的同一代备份。

本机制不抵抗 Root、Hook、读取密钥后重签、删除全部保护记录和标记、整套备份回滚、旧版APK忽略规则。不能称作联网反作弊。每次最外层请求增加时钟签名校验，角色加载增加时间快照比较；正常未改变的记录不重复落盘，无后台轮询。尚无Android真机性能数据。

## 9. 系统时间跳变自动封锁（工作区后续变更）

系统时间只用于异常检测，收益仍完全由连续计时推进。首次运行或旧版时钟升级时，在原有签名记录中增加系统时间、连续计时观察基线及最近观察时间；不根据旧档已有未来日期推断作弊。

- 同一次设备启动，比较系统时间与“该次启动观察基线＋实际连续计时增量”。前调或后调累计偏差**超过300秒**，立即持久化隔离；基线不随每次采样重置，反复小幅修改也会累积触发。
- 杀进程再开仍读取已保存的观察基线。正常锁屏、休眠及同次开机离线经过时间不触发；修改时区不改变 Unix 时间戳。
- 设备启动身份变化后，系统时间早于最近已保存观察时间超过300秒时也封锁。正常设备重启重新建立观察基线，仍不补发无法验证的离线收益。
- **跨设备重启的前调无法与正常关机间隔可靠区分**，不凭这一项封锁；首次安装前改时、在两次请求之间改时后恢复、Root／Hook／整套备份回滚仍不在可靠检测范围内。
- 5分钟容差内的修改也不会增加收益。时间跳变不证明主观作弊；系统自动校时超过容差同样会触发此严格策略。
