# 仙盟模块 NPC 离线实现与调试说明

更新日期：2026-10-26（UTC+8）。客户端：金箍棒 OL 3.87。配置修订：`guild-players-2026-10-26`。

本文记录本轮对原版入口、NPC 替代、商店与盟主管理的修复。仙盟仍存于各角色的本地 SQLite 存档；所有模拟玩家均来自 `analysis/npc_design/players/catalog.json`，完整阵容通过其 `source_file` 引用 v1/v2 阵容库。原版客户端可证规则标【A】，官方服务端缺失而采用的本地规则标【B】。不会将离线模拟称为真实联机或官方服务端复原。

## 本轮已实现内容

## 【A】原版证据与修复依据

证据来自 APK 内未修改的 LuaJIT 字节码、协议、CSV。执行 `analysis/tools/audit_guild_rules.py` 可重新提取 14 个原版模块，资源哈希见 `analysis/evidence/guild/audit.json`。

### 商店持续刷新

`ui_guildStoreUI.txt` 对应原 Lua 约 L370 的定时回调每秒比较 `g_playerInfo.union_store_flush_time` 与当前时间；到期即再次请求 38。旧后端初始值为 0，付费刷新又写为当前时刻，因此每次重绘后仍然到期。

修复后，属性 147 在商店响应之前下发未来自动刷新截止时间。普通查询返回数值 `flush_flag=0`，付费刷新返回 `1`；不再用布尔值代替原客户端数值判断。自动刷新在本地零点执行，是下节【B】的时间规则，不能据此认定官方商店也在零点刷新。

### 申请及禁言管理

`ui_xianmengUI.txt` 原 Lua 约 L916/L938 的拒绝/同意按钮发送 `role_list`，并非仅 `role_id`。解除禁言也可批量发送。旧后端测试手工构造单人字段，未覆盖真实按钮。现在两种请求均有校验和原子结算。

原生禅让由 `ui_xianmengUI` proto65、L1339—1342 发送 `11/new_rank=1`，此前只允许12会让按钮失败；现在两种方式统一校验仅盟主可禅让，同时降原盟主为盟员，确保仅一个盟主。

职位编号、申请通知事件 82/7、成员信息字段、原版管理入口沿用原协议。权限分配、职位限额、招募频率属于【B】。

### 秘境与战报

原客户端读取服务端 `max_count`，出战检查至少三人，并提交完整 `fight_list`；申请界面会将申请表的数字键复制为角色 ID。因此必须使用真实角色 ID 作键、保留出战顺序，并校验重复、缺员和非本队成员。当前上限五人沿用项目已确认规则。

秘境及灵兽使用嵌套 `line_up_msg` / `fight_result_msg`，固定八格伤害数组；单个 Lua 文本消息有长度上限。战报回放恢复数值键，保留完整可装入包的最新记录，避免持久化后的 JSON 键类型导致回放失效。

### 捕获历史 94 与本地小游戏

- `ui_petHomeUI.txt` proto26、原 Lua L798—803 的 `sendMsgGetLuckyPetHistory` 主动发送 94；proto2、L244 的页签调用它。**94 同时有客户端查询与服务端更新用途**。旧文档“93/94 都只是推送”对 94 的结论有误，现已修复该可达入口。
- `ui_pethuntUI.txt` proto28、L836 的 `checkDeviceFit` 通过后，L841 才发送 `task_type=1`；拼图 proto34、L922—969 先 `checkPuzzleFit`，成功回调 proto33、L964 提交相同结算字段。
- 原请求没有上传棋盘步骤或答案。后端校验任务、支付方式、次数、完成状态并发奖；原版客户端负责小游戏操作。旧文档将其描述为“用付资源代替小游戏”不准确。本地信任原客户端成功提交属于【B】的服务端边界。

### 试炼、捕获与取经限制

- `pethunt_guide1` 明确任务周一至周五刷新、周末不出现；`pethome_guide1/2` 明确周末盟主开启试炼、按周声望确定宠物抽取次数。默认恢复这些日程，测试使用隔离时钟。
- `petHomeUI` L817/L1160 以栖息数 **至少240** 发送开启请求；文案写“>240”，实现遵循可执行的 `>=240`。L843 与 `pethome_shilian_info3` 限盟主指定成员。
- `petHomeUI` L638 只有结果58（has_prize）绘制领奖按钮，旧54（had_closed）会使奖励虽可后端领取、界面却无入口。现按未领奖阶段、完成、过期等状态返回正确值。
- `pethuntUI` L1373 发送玩家选定的 `catch_type`；现严格消耗所选1338/1339/1340/1341道具，缺货拒绝，不替换成别的符或悄悄扣元宝。
- `escortUI` L84 的 `max_stopable` 为品质1—4最多3次、品质5最多1次，替换旧后端统一5次限制。

宴席三档价格、体力、精力、倍率和奖励沿用原 `union_feast_award.csv`；盟战奖励继续读取 `union_match_prize.csv`；取经一小时沿用原客户端倒计时。其他既有【A】协议清单见 [仙盟模块规则与调试](仙盟模块规则与调试.md)。

## 【B】NPC 安排与战斗规则

### 成员、申请与旧存档

- 同一角色的仙盟世界中，NPC 成员和申请身份不重复；按玩家等级附近的候选池随机选择，随机序列随存档保存。
- `npc_recruit_daily=4`：盟主每日首次触发仙盟请求时最多收到四名申请，受剩余成员容量及待审批数量约束。创建响应即生成第一批，无须改正式存档或人工写入成员。
- 申请需要玩家按原版管理入口批准；拒绝/清空后当天不立即补回，次日继续招募。批准、拒绝、重连不会反复加入同一 NPC。
- 旧临时成员迁移时保留贡献、职位、入盟时间，并同步队伍、禁言、试炼指定成员与护送引用。只修改本地社交状态，不改阵容库和玩家养成资源。
- 原版角色 ID 通过 int32 表示；players 的大 ID 不能再被旧的“一百万”通用参数上限拒绝。资源数量继续受各业务上限限制。

### 秘境联合阵容

当前离线实现将 3—5 名队员的原始阵容按 `fight_list` 顺序轮流抽取神仙，拼成最多八格联合阵容；每名队员至少提供一位，其余格子继续轮流补齐。保存来源角色 ID、原位置和新位置，避免不同角色神仙实例 ID 重号而错误关联装备。

原先“每名 NPC 给玩家增加 10% 属性”的替代逻辑已经移除。NPC 现在实际出战；兽栏成长和宴席已配置的加成仍生效。这种八格联合方式是【B】，不是已证明的官方多人分场轮战。

敌人选取目标战力为联合阵容基础战力的 `75% + min(100%, 层数×8%)`，在附近候选中随机选择合法可播放的 NPC 配置。只选择现有阵容，不为胜负修改 NPC 属性；同层失败重试、查询、重连不重选，胜利推进下一层。难度公式和选取范围属于【B】。

### 栖息池与周末试炼

原版240门槛保留。每名已入盟的 NPC 一次性向仙盟共享栖息池带来60只灵宠，按合法类型保存数量；四名NPC合计240只。这一数量及补充方式属【B】，与玩家个人兽栏、独立宠物背包分开，不把NPC的栖息数量伪造为玩家捕获所得。幸运抽取从共享池扣一只，发给玩家真实宠物实体并写捕获历史。

【B】每10点周声望获得一次基础抽取额度，基础上限3次；每档试炼奖励额外增加1次；本周已用次数持久化。试炼每次活动保留剩余生命和结束时间，指定挑战最多3次、援助最多3次，不通过反复查询或继续挑战延长倒计时。具体数值均在 `guild_rules.json` 中。

### 其他互动

- 盟战与跨服各自保存当日六名对手，等级邻近、身份不同；旧 90001—90006 是兼容别名，新列表显示 players 的真实 ID。生命、行动力、功勋、连胜、下注与排行结算保留既有离线积分杯规则。
- NPC 盟主、护送成员和取经对手均可解析回同一 players 身份。取经的劫掠概率、品质成长及收益公式沿用既有【B】配置，不因改用真实阵容而伪称官方数值。
- 宴席 NPC 每场只赠礼一次，最多三份。模拟赠礼记录进入福气排行；玩家抢礼仍校验到期、剩余数量、重复领取和每日次数。
- 神树守护和灵兽试炼的 Boss 是玩法目标，保留既有 Boss 配置；不把所有怪物强行替换成玩家身份。真人参与者和玩家型敌人使用 players。

## 如何体验

1. 重启本地离线后端并重新登录，旧存档自动兼容；不用重装 APK 或删档。
2. 达到创建条件后创建仙盟，打开申请列表，多选四名 NPC 并同意。成员资料、任命、禁言、踢人和禅让均走原版入口。
3. 新盟先捐献获取 50 威望，再种树、培育；领取贡献后打开贡献商店，界面应保持稳定。刷新和购买后检查元宝、贡献、商品数量。
4. 创建秘境队伍，批准本盟 NPC 的组队申请；满五人或至少三人后出战。也可加入 NPC 队伍，由 NPC 自动补齐队友。
5. 工作日完成灵兽任务获得周声望；周末在240只栖息灵宠前提下，由盟主指定 NPC 并开启试炼，检查其姓名、伤害排行与领奖按钮。幸运捕获按周额度发放宠物；兽栏历史页应能正常打开。
6. 宴席、灵兽任务、游历捕捉、盟战、跨服和取经按原版入口操作。已批准 NPC 可参与护送，宴席出现其赠礼。
7. 仙盟灵兽额外养成继续使用既有聊天命令 `/灵兽`、`/喂养`、`/合成`、`/升星`；这是【B】扩展入口，不宣称原 APK 新增了养成按钮。

## 验证与覆盖

自动验证使用临时 SQLite 和本地 NPC 阵容。原客户端验证拦截网络发送，运行后恢复玩家、配置、发送函数、取时函数等引用，不向正式存档写入测试奖励。回放使用2026-10-23周五和10-24周六的隔离时钟；真实80战斗和领奖UI分别覆盖，领奖分支通过临时存档设置Boss生命为0触发，不将其宣称为实战击杀证据。

```sh
.runtime/venv/bin/python analysis/tools/audit_guild_rules.py
.runtime/venv/bin/python -m unittest discover -s tests -p 'test_guild*.py' -v
.runtime/venv/bin/python -m unittest discover -s tests -q
.runtime/venv/bin/python analysis/tools/verify_guild_client.py
```

最终本轮结果记录在 `analysis/evidence/guild/current_validation.json`、`current_client_validation.json` 与 `current_tests.log` / `current_full_tests.log`。具体通过数以这些新记录为准，旧文档中的 47/57/77 步等数字不是本轮验收结果。

验证涵盖商店定时行为、原按钮字段、真实 NPC 身份、盟主管理、申请批准后五人组队、阵容来源、队伍人数与非法名单、重复请求、跨日、重连持久化、试炼伤害和历史查询，以及既有神树/探宝/宴席/捕捉/盟战/取经回归。原客户端回放说明所列回调和定时检查可运行，不等于每一种点击组合、每段动画都完成人工穷尽测试。

## 实现边界

原版玩家可达的仙盟入口以本地离线行为实现，真实多人由 players NPC 替代。官方隐藏 AI、随机种子、原服赛季和淘汰赛调度、实时跨服通信没有可验证服务端资料；目前沿用明确的【B】离线积分杯及请求时推进。未知保留请求 10/17/49 不伪造成功，合服补偿 77 因没有合服活动明确拒绝；这几项不应算成已确认可达入口，也不能当作“官方服务端全部还原”的依据。

主要实现文件：`guild.py`、`guild_npcs.py`、`guild_offline.py`、`guild_combat.py`、`guild_instances.py`、`guild_hunt.py`、`guild_match.py`、`guild_escort.py`、`guild_activities.py`，均位于 `network_redirect/`。本轮之外的历史补全见 [仙盟模块离线补全说明](仙盟模块离线补全说明.md)；有冲突时以本文及本轮代码、证据为准。
