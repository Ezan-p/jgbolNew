## 4. 推测规则 B：逆天改命判定与防重复

### 4.1 单神仙独立判断

以神仙实例`cortege.id`为身份，`fate_rebullding_state == 1`才参与新增成就。两只同类型但不同ID的神仙分别计次；同一个ID改变属性、刷新、换阵位、重登，不重复计次。24是每项成就的全角色上限，不是按神仙类型计数的种类上限。

三魂层数采用：

```text
spirit_heaven_level + spirit_fortune_level + spirit_earth_level
```

七魄层数采用七个`physic_*_level`之和：`tc/lh/qp/lp/zs/jp/yp`。

**层数口径属于B。** 使用已完整点亮的层，不加入未满一层的星点；也不套用七魄界面解锁检查中的“当前层索引之和+7”，三魂也不额外加3。原条件写的是“总点亮层数”，完整层口径更能避免尚未完成一层就提前领奖。三魂每层9点、七魄每层7点沿用既有培养逻辑。

例如：同一神仙天魂10、命魂10、地魂9，即使地魂已有8颗星，也未达到30层；完成最后一点、地魂升到10层后才完成581。两名神仙各有15层，不合并为一名30层神仙。

### 4.2 完成记忆与重置

每个`成就ID:神仙ID`保存0→1的历史最高达成记录。首次达标才加一次；高档达标可同时补齐全部低档。重置三魂、移出阵容、回收神仙后，已得次数和道行保留；同一实例再次培养到相同门槛不能刷取。新生成的不同实例可以另记一次，直到24次封顶。

这沿用已有养成成就按实例去重的本地方式；未发现官方服务器的重置退还／重领规则，因此不能把此策略宣称为原服源码还原。

### 4.3 结算与道行

仅检查成功保存后的角色事实。材料不足、前置不足、参数错误不增加成就，不扣资源；同一序列号重放由现有协议缓存返回原应答，不能重复结算。

新增固定道行加入既有成就基础总和，沿用本地公式：

```text
道行 = min(2147483647, floor(固定道行总和 × (100 + 百分比成就加成总和) / 100))
```

公式及百分比叠加方式是既有B规则，本次未改。完成后1032同步道行属性27，1066同步变化的成就；新达成通知沿用原客户端。登录／全量查询使用`new=0`，正常业务结算使用`new=1`。

## 5. 推测规则 B：提炼计次与旧存档迁移

### 5.1 新操作怎样计次

已有实现通过“同一物品首次达到至少12级”补记一次563～565，本次保留该兼容行为。原逻辑只覆盖首次12级，导致同一颗石头12→13、13→14成功时不再计次；现已按“提炼一次”的原描述补齐：

| 变化 | 本次成就结算 |
|---|---|
| 10→11 | 只适用既有封神成就，不加提炼成就 |
| 11→12 | 该物品首次12级事实记一次提炼 |
| 12→13 | 1054／flag=5成功后，目标等级实际增加1，记一次 |
| 13→14 | 同上，再记一次 |
| 14级继续请求、材料不足、非法材料 | 拒绝操作，不记次 |
| 镶嵌、卸下、查包、重连 | 不作为提炼操作 |

12→13、13→14的事件判定采用成功交易前后的同ID物品差异，不相信客户端宣称的“成功”。原版未公开服务端计次代码，因此这一触发细节仍标B。

旧版本可能把高阶石头保存成数量大于1的堆叠。拆分时，余下物品继承已有成就观察标记，避免仅生成新ID就再次补记“首次达到12级”；随后各石头真实提炼仍按成功操作记次。

### 5.2 可证明历史的补记范围

- 已激活、已有魂魄层数的神仙：首次读取／保存就按当前事实补齐对应新增成就，不重新收材料。
- 神石旧总次数200：直接保留，后续成功提炼继续累计到400，不清零、不先翻倍。
- 旧`observed`中超过200条的提炼成就实例记录：旧代码虽截断总数但保留了这些记录；本次一次性将其恢复为可证明的次数下限，最高400。通过`stone_cap_revision=2`标记避免重复迁移，也避免后来继承的拆堆标记被再次当作历史奖项。
- 旧14级石头但没有操作流水：只保留／补记已有兼容逻辑的一次“至少12级”事实，不凭当前等级虚构另外两次历史提炼。更新后发生的12→13和13→14正常计次。
- 已回收且没有记录的神仙、旧版上限外且没有观察记录的提炼：没有可验证依据，不自动发放。

迁移只增加可证明的达成记录，不删除已有道行来源或模拟凭据。记录放在既有角色JSON中，无数据库表结构变更；重复读取和进程重启保持次数。

## 6. 推测规则 B：258条列表与客户端显示

原服1263的1066定义仍然是：

```text
serial_num=I,new=B,role_id=d,tao_point=I,achievement_count=B,achievements=$123{255}
```

直接把258装进条数字节会失败；简单分两包也不够，因为原客户端他人成就处理会在每包开始时重建对比表，最后只剩3条。此次保留原二进制协议，增加本地桥接：

1. 超过255条时，先发事件80的`local_achievement_batch`，说明角色ID、new标志和总条数。
2. 再发原1066分包，目前全量为255+3；小增量仍走原单包。
3. 客户端适配器按成就ID收齐、去重，最后一次性调用原`onGetAchieves`，本人和他人共用原界面处理。新的批次替换未完成旧批次，重新登录配置清除未完成批次。
4. 合并后的258仅是Lua内存表条数，不编码到原1字节线协议。

同时按原`data.getAchievementsCSVConfig`字段格式补入11条目录并修改三项400上限；已有1263客户端和仍使用旧表的客户端都取得相同内容，名称、条件、奖励和排序来自专表。不会把未知ID丢给旧界面，也不通过关闭三条原成就来规避容量限制。

该本地分包桥接属于B，不声称是原服的传输方案。代码沿用现有可靠、有序的客户端消息分发；没有新增跨连接通用消息重组协议。
