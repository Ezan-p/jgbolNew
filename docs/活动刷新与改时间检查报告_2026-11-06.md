## 2. 当前源码的刷新规则

下表日期均指统一游戏时间的 UTC+8 日期，手机系统时区不改变这些边界。

| 活动／功能 | 日刷新 | 周或其他周期 |
|---|---|---|
| 九重天 | 00:00 重置每日免费额度、商店与限购；已有奖励骰子按规则保留 | 周一 00:00 重置周进度，剩余天星按 2:1 向上取整生成蟠桃邮件 |
| 通天塔 | 00:00 生命回满、商店商品／限购／付费刷新次数重置；仙力另按半小时恢复 | 周一 00:00 重置普通塔地图／进度；周四 00:00 冻结榜单，结算榜奖、阶段奖和补给 |
| 捕魂达人 | 00:00 重置日额度／日榜；商店限购在 06:00 重置 | 周一更新周榜周期 |
| 东海寻宝、财神贺岁、唐王集卡 | 按各自规则更新每日次数或赠礼领取资格 | 周一更新周状态，按规则回收旧活动物品 |
| 救悟空、如来大转盘 | 只有各玩法明确规定的日额度刷新 | 当前配置为七天周期，周一边界 |
| 梦境、天机阁、两周年／元始活动 | 不把整个活动进度每天清零 | 当前配置为十四天周期，并非每周清零 |
| 天工制物阁 | 按每日任务／商品规则更新；周一营业规则单独处理 | 周二 00:00 开始新周期，下一周一为兑换日 |
| 太虚血战、洞府修炼周榜 | 按各自玩法规则处理 | 周一开始新周 |

通天塔旧说明保留过“周一发榜奖”的历史描述；当前以 `activity_babel_npc.settle_week` 和《通天塔热更新与命星产出合成链规则A及推测B》第3节的“周四结算、周一重置”为准。

## 3. “按时刷新”的实际触发方式

后端采用请求触发的结算，没有一个常驻定时任务在零点同时修改所有角色。登录／重连、活动请求及部分心跳维护会比较已存日期与当前游戏日期，跨界后先结算再处理操作。九重天和通天塔的日／周界限已通过心跳协议验证。

活动专属节点可能等到对应请求才落库，例如捕魂商店 06:00 的重置由读取其活动状态触发。关闭游戏期间不需要运行后台任务；同一次开机重开后，能够确认启动身份时按实际连续计时补算。重复请求不会因为再次检查边界而重复刷新同一日额度或重复生成相同周期邮件。

客户端是否立即重绘还取决于页面自身的查询、回包和定时器；本次没有逐个原版 UI 做真机验收。

## 4. 当前源码对前调／回拨时间的处理

- 已建立时间锚点后，前调一天、一周、一年、反复小幅前调及回拨系统日期，均不推进或倒退后端游戏时间，也不会因此封锁正常角色。
- 同一次设备启动中，游戏时间按包含休眠的连续计时推进；关闭／重开应用在启动身份可确认时继续补算。
- 设备重启或启动身份无法确认时，沿用已保存游戏时间，丢弃无法验证的间隔。此后继续正常计时，**游戏的零点／周一可能落后现实日历**。
- 首次建立锚点仍需采用未验证的系统日期与已识别旧档时间下限；已有未来时间历史不会自动回到现实日期。纯离线没有可信网络校准。
- 原客户端 `common/time.lua` 用本地 `os.time()` 与同步偏移估算时间。修改日期会影响同步间隔内的倒计时、过期判断及部分刷新请求；下一次时间同步会纠正偏移。后端收益仍由统一游戏时间决定，不能承诺客户端表现完全不受影响。
- 已被时间异常限制的角色或玩法按限制规则冻结刷新／恢复／领奖，这是有意行为，不能按普通角色验收。

## 5. 验证及交付范围

新增 [tests/test_activity_clock_boundaries.py](../tests/test_activity_clock_boundaries.py)，使用真实时钟 SQLite、可控操作系统时间输入和二进制协议，不替换 `game_clock.now()`，5 项全部通过：

1. 改系统日期不刷新；真实经过一秒跨零点后恢复日额度，重复心跳不重复刷新。
2. 周日 23:59:59 不提前刷新，周一 00:00 重置并只生成一次天星回收邮件。

4. 同次开机关闭后跨周重开能补算，回拨系统日期不改变结果。
5. 设备重启不虚构离线日期，重建锚点后继续前进并正常跨零点。
