# 天工制物阁离线活动实现说明

更新：2026-10-26，原版基准3.87。**本活动为菜单32、mondayUI、玉圭兑换；不是菜单47、destinyUI、金砖礼包的天机阁。** 原文误把天机阁写在本路径，现已移至[天机阁说明](天机阁离线活动实现说明.md)。

【A】表示可从原包资源、Lua字节码、协议或CSV直接证明的规则；【B】表示原服数据缺失时的离线补全。实现保留原生四格界面、任务、换货、开业赠玉、兑换及回收流程；商品池、售价、赠玉数量等不能冒称原服数值。

## 2. 玩家完整流程

1. 在活动／奇闻中进入“天工制物阁”。周二至周日歇业，可查看四格预告及今日目标。
2. 完成当天的一项实际玩法目标，点击领取玉圭。四格预告每天分别可免费换货一次。
3. 周一开业，平日确定的商品进入兑换状态；领取开业赠玉，有VIP时开业赠玉翻倍。
4. 按每格标价消耗玉圭领取物品，物品真实进入背包，可按既有道具机制使用或合成。
5. 周二歇业，将剩余已领取玉圭按界面显示的比例折成银两邮件；随后开始下一轮预告与任务。

活动不要求修改APK、替换天机阁入口，也不新增充值依赖。入口原生 `canJoin` 恒为真，未额外编造等级门槛；具体任务仍受其所属玩法的原有解锁条件限制。

## 3. 原版可确认规则【A】

- 原界面 `MaxShowCount=4`，不是九个礼包；歇业和开业分别使用 `show_list` 与 `prize_list`。
- 原 `String.plist` monday16～22、`String2.plist` monday1～15明确：周一开业；玉圭只能在开业当天使用；歇业回收剩余玉圭；歇业期间每件不满意的商品每天可以更换一次。
- 原UI显示回收物品及数量，使用服务端 `exchange_item`；没有在客户端写死回收比例。
- 周一有开业赠玉，VIP图标配“可获赠双倍～”；具体VIP门槛与赠玉基数不在原包配置中。
- `week_task_def` 有九种目标。原文案均要求一次对应行为：消耗体力、消耗精力、大闹天宫、夺宝、刷新夺宝列表、培养神仙、拜访三星、天缘召唤、旅途战斗。
- `today_task` 用 `cur_task / finish_time / recv_time`；另有 `can_take_count`，原生领取按钮同时判断未领取数量、已完成未领任务，以及周一开业赠玉。
- 原刷新回包带新商品及 `random_time`，原UI按是否跨日控制各格的换货按钮。
- 原包成就125“天工制物”条件是通过天工制物阁兑换任意物品，奖励10道行。由本活动成功兑换触发一次；天机阁不再误触发，旧存档已经获得的成就不追溯扣除。

## 4. 缺失规则与明确补全【B】

原包没有找到天工的服务端商品池、价格表、各日赠玉数、回收单价或完整日历。以下值集中配置在[monday_rules.json](../server_config/monday_rules.json)，明确标注 `mode=inferred`，没有挪用天机阁的 pavilion CSV。

| 项目 | 当前补全 |
|---|---|
| 时区／周期 | UTC+8；周二00:00开始新期，下一周一全天开业，随后周二00:00歇业 |
| 平日赠玉 | 完成今日目标领取10玉圭，每日一次 |
| 周一赠玉 | 非VIP20；VIP等级大于0为40，周一无需额外做任务 |
| 平日VIP加成 | 不翻倍，避免把开业文案扩大到整周 |
| 目标选取 | 本地历日序号对九项轮转取模，每日一项；不自动补做未上线／未完成的目标 |
| 随机商品 | 每格从自己的三个候选中等概率抽一个；换货排除当前商品，另外两个各50% |
| 商品保存 | 当期预告与换货结果保存至周一；周一不能换货，新期重新抽取 |
| 兑换限制 | 仅受玉圭余额限制，同一商品可重复兑换；原包未给出兑换次数上限，不另加限购 |
| 跨日未领取 | 当期已完成未领取目标累积到待领数量；未完成不累积；跨期未领取资格作废 |
| 歇业回收 | 每1玉圭换1000银两；仅回收已领取余额，通过永久系统邮件送达 |
| 结算时机 | 歇业后下一次登录、活动请求或成功玩法存档时补结算；不依赖进程持续在线 |
| 时钟回退 | 保留时间高水位，回退期间拒绝本活动领取／换货／购买，防止刷日与重复回收 |

商品全部为已存在的原版道具；**在此活动中的候选组合、数量、概率及售价都属于【B】**：

| 格位 | 玉圭售价 | 三个候选（每次显示其中一个） |
|---|---:|---|
| 1 | 10 | 蟠桃1001×10；破障丹1421×5；魂缘丹1024×5 |
| 2 | 20 | 补天石1333×3；精华礼包1327×5；太古水晶1323×10 |
| 3 | 30 | 金丝乾坤袋1032×5；银绸乾坤袋1033×3；紫色精魄碎片10001×5 |
| 4 | 40 | 五星被动碎片6005×5；五星武器碎片6002×5；五星防具碎片6003×5 |

设计理由：六个歇业日全部完成可得60玉圭，叠加普通开业赠玉共80，VIP共100；四格价格合计100，平日换货提供选择空间。低价补充日常消耗，高价提供装备／神术碎片。这是可运行的离线经济方案，不是原服掉落表复原。

任务完成口径同样明确为【B】：以成功落库的实际状态变化为准。体力／精力以消耗及实际消耗型战斗记录确认，兼容同一请求发生自然恢复或升级；大闹天宫／夺宝／旅途参加一次战斗即可，不强制胜利；刷新夺宝列表必须实际增加刷新次数，单纯查看不算；神仙培养成功生成一次培养结果即算，之后保留或放弃不影响；拜访三星只计实际拜访；天缘召唤只计实际召唤次数增加。失败、查询、重复网络包不完成目标。

## 5. 原版协议与实现

| 请求 | 参数 | 原生返回 |
|---|---|---|
| 1219 | op_type=0，flag=1，level=0 | 112：入口、活动数据、今日赠玉、回收比例、倒计时 |
| 1219 | op_type=0，flag=2，level=0 | 112：领取成功，add_count及更新后的activity_data |
| 1219 | op_type=0，flag=3，level=1～4 | 112：购买成功，left_count、attach_data、can_rece |
| 1243 | index=1～4 | 142：新商品、random_time |

兼容细节：**112成功码为1，142成功码为0**，二者不能混用；`can_rece` 为数字0/1；客户端自己给 `end_time` 加1，因此服务端发送今日结束时刻减1。`week_prize_config` 只发送今日星期键，因为原生代码按1～7找到第一个键即采用。周一 `prize_list` 是含 `consume_count/attach_data` 的对象；歇业时它是价格数字，商品在 `show_list` 中。活动提示在登录及进入原界面时刷新，不改变其他玩法的回包事件顺序。

主要实现：[activity_monday.py](../network_redirect/activity_monday.py)、[activity.py](../network_redirect/activity.py)、[backend.py](../network_redirect/backend.py)、[achievements.py](../network_redirect/achievements.py)。角色状态位于 `activity.monday`，保存周期、时间、玉圭、待领资格、四格商品与换货时间、今日任务。与 `activity.pavilion` 完全独立，不把原有金砖兑换为玉圭。

请求校验及奖励编码成功后统一保存。失败不扣余额、不消耗换货次数；后端既有序列号重放缓存确保同一请求不会重复发奖。回收邮件以 `monday-recycle-周期` 为稳定键，由既有系统邮件事务发送和领取，重启或多次进入不重复生成。
