# 普通道具出售模块规则与修复说明（3.87）

更新日期：2026-10-26。适用：本仓库原版 3.87 客户端及本地离线后端。

## 标记与范围

- **【A】原版客户端规则**：来自原包 CSV、LuaJIT 字节码、协议定义；不表示取得了官方服务端源码。
- **【B】推测规则**：缺失官方服务端实现后，本地补齐的校验、扣除顺序、原子结算与边界处理。

本次接入 `1088 / msg_sell_items`。原版所谓普通道具出售，实际只在 **28 种四星装备碎片**上开放；蟠桃、包子、礼包、五星碎片等不在原售价表内，继续不可出售。`1056` 装备批量出售、`1086` 神仙回收、`1074` 材料分解是其他模块。

## 【A】原版入口、数量与确认

1. 包裹的“道具”页为 `packageTagDef.props=6`。`packageUI.lua:382–396` 根据 `d_data.g_ep_price[itemInfo.type_id]` 是否存在添加出售按钮。
2. `data.lua:986–994` 的 `getEquipPiecePrice()` 从 `csv_config/item_price_config.csv` 读出 `item_type → silver_count`。**不是**装备使用的 `item_sell_config.csv`。
3. 点击出售调用 `createBatchSale(parent, type_id, itemInfo.count)`，弹出原版数量选择窗口。
4. 数量初值与下限是 1，上限是当前条目的数量。四个按钮为 `−10、−1、+1、+10`，到边界时截断。通用计算器在未传上限时才默认 999；本模块传了库存，**不存在固定 999 或装备模块的 500 件上限**。
5. 预览银两为 `单价 × 选择数量`。取消（tag=1）只关闭窗口；确认（tag=2）关闭窗口并发送 `1088`。
6. 原普通道具出售窗口没有另加四星二次确认，也没有出售等级／VIP限制；本次不凭空添加。

证据：`packageUI.lua:383–385`、`data.lua:3410–3458`、`guildPartyUI.lua:412–476`。保留原版按钮、计算器和回调，不新增客户端替代界面。

## 【A】请求和回调契约

请求 `1088` 的二进制字段为 `serial_num=I,data=s`。`data` 是静态 Lua 表文本，例如：

```lua
{item_list={[7010]=2}}
```

`item_list` 的键是**物品类型 ID**，值是数量，不是背包对象 ID；原界面每次发一种类型。后台兼容同一表中的多类型原子结算，属于【B】扩展处理，不新增批量选择界面。

成功使用 `2998 / event 153 (sell_items)`，内容：

```lua
{silver_count=2000}
```

`event_mgr.lua:1715–1716` 转交 `packageUI.onGetSaleResult`；`packageUI.lua:1989–1992` 显示本次获得的银两并刷新包裹。`silver_count` 是本次收益，不是银两余额。

## 【B】缺失的服务端规则与实现

实现文件：[item_sale.py](../network_redirect/item_sale.py)。路由接入现有 [formation.py](../network_redirect/formation.py)，复用后端已存在的事务、响应编码与序号缓存。

- 仅接受静态 Lua 字面量解析；拒绝执行表达式、重复键、空列表、错误类型、非白名单道具、零数／负数／小数／布尔／字符串数量，以及额外伪造价格字段。
- 每批最多包含白名单中的 28 种类型；数量按实际可出售库存校验，不从客户端读取单价或到账金额。
- 只消费 `attach_type=5、level=1` 的正常堆叠。锁定、绑定、装备位置及异常养成状态的条目不进入可消费库存。可售碎片原本没有养成系统，该保护用于历史或调试异常存档。
- 同类型若有多个堆叠，按背包对象 ID 从小到大扣除；跳过锁定或绑定条目。请求量超过剩余可售库存时整批拒绝；不自动解锁，不卖部分后才报错。
- 先验证全部类型与数量并生成扣除计划，再统一扣物品、加银两。数量归零的对象从背包移除，其他物品保持原状。
- 本地 `1032` 属性协议的值是有符号 32 位整数，因此银两到账上限采用 `2,147,483,647`。超过时拒绝整批，避免溢出、显示负数或只扣物品不到账。这是本地同步边界，不宣称为官方经济上限。
- 服务端依次产生物品数量增量（全售时为零）、完整背包快照、角色银两余额属性和事件153，最后 `1106` 结束本次等待。所有业务响应编码成功后才写入 SQLite；编码失败不会保存扣除。
- 失败走已有 `event 55 / op_string`，并发送 `1106`，不给虚假成功回调。
- 同一游戏会话中，完全相同的请求序号与数据返回缓存响应；相同序号换内容、过期序号拒绝。缓存淘汰后仍用最高序号拒绝旧请求。`1105` 重传不重新结算。
- 成交结果持久化，关闭并重开后端后库存与银两保持一致。**请求防重缓存随本地后端进程／新登录会话重置**；原协议没有跨新会话交易凭证，不能把相同内容的新请求识别为历史交易。此处不宣称跨新会话永久幂等。

- 专项 11 项测试通过，含全部 28 种原版可售道具逐个出售、多类型批次、部分与全部出售、大于999的库存、锁定／解锁、绑定保护、拆堆叠、非法参数、混合批次失败原子性、余额上限、编码失败回滚、重复请求／重传和后端重启持久化。
