## 【A】原版证据与契约

【A】表示原包协议、文案及LuaJIT字节码证据；【B】表示缺失官方服务端后补充的本地规则。

- `other_functionUI.lua:237–238` 检查 `g_new_config[7].gift_card`，使用原 `cdkey1.png/cdkey2.png` 按钮，点击调用 `systemSetUI.exchangeGiftBag()`。本次补齐服务端 `gift_card=true`，保留原版版本判断。
- `systemSetUI.lua:672–678` 将输入限制为18字符。空输入不发送请求。尽管协议固定字符串有32字节，发行配置仍限制在18位以内。
- `systemSetUI.lua:711–732` 发送 **1104 / msg_pickup_gift_attach**：`serial_num=I,sn=S[32],flag=B`；普通礼包使用 `flag=0`。
- 响应使用 **2998 / event 18（gift_attach）**，不是1104回包。`event_mgr.lua:1309–1311` 转交 `recvExchangGiftBag()`。
- `systemSetUI.lua:957–1031`：成功码1，读取 `name` 和 `attach_list`，调用原 `messageUI.createGetItemsLayer` 并关闭输入窗；失败按 `coupon_ret_code_编号` 提示并清空输入。未知编号使用原版兜底文本。
- `client_flag>1` 转好友兑换回调。普通礼包直接到账，不走1102／1103系统邮件。

证据：[原版兑换窗口](../analysis/evidence/lua_named/lua/ui/systemSetUI.lua.txt)、[其他功能菜单](../analysis/evidence/lua_named/lua/ui/other_functionUI.lua.txt)、[协议表](../analysis/evidence/protocol_tables.json)、[事件路由](../analysis/evidence/lua_named/lua/event_mgr.lua.txt)、[原版枚举](../analysis/evidence/lua_named/lua/common/common_def.lua.txt)。中文错误文案位于原包 `assets/release_/08b0428edce64d19f304d30c3829ec87.data` 的 `coupon_ret_code_*`。

## 【B】发行配置

配置：[gift_code_rules.json](../server_config/gift_code_rules.json)，启动时读取并校验，修改后重启。原服发行清单、绑定数据库、额度和有效期缺失，因此标记 `mode=inferred`。

| 字段 | 本地含义 |
| --- | --- |
| `revision` | 配置修订号，随领取写入账本 |
| 顶层 `platform` | 服务端可信平台，默认 `local`，不从兑换请求取值 |
| `code` | 唯一发行码，1—18位大写英文字母、数字或连字符 |
| `name` | 成功提示中的礼包名，1—60字符 |
| `group` | 互斥组，每账号每组限领一次 |
| `enabled` / `issued` | 是否开放／是否已发行 |
| `starts_at` / `expires_at` | Unix秒，开始包含、结束不包含；结束为0表示永久 |
| `max_uses` | 同一数据库内所有账号的总领取额度，0无限、1即一次性码 |
| `account` | 可选绑定，本地登录账号，不是角色显示名 |
| `role_id` / `server_id` | 可选绑定，存档角色ID／区服ID |
| 行内 `platform` | 可选绑定，可兑换的平台 |
| `random_prizes` | 可选类别数组：`weapon`、`armor`、`artifact`、`passive`；每项从对应五星原表模板等概率抽1件等级1成品 |
| `prizes` | 固定奖励 `[类型,编号,数量,等级]`；与随机奖励合计1—20项，支持类型5、6、10、11、12 |

货币编号0、等级1，单项数量1—1000000；物品编号须在原表存在。兑换码现支持道具／装备5、法术6、神仙魂魄10、元宝11、银两12；不直接发放神仙或灵兽。装备和法术使用独立实例分配器，装备初始属性和法术效果随背包同步；魂魄通过1046同步。

输入首尾空白移除、英文字母转大写，中间空白不合法。当前所有礼包永久有效、总量不限、每账号一次，互不排斥。绑定角色建议同时绑定 `account`：历史存档中，不同账号可能有相同 `role_id`。

例如发行一个仅供指定账号使用的一次性码，可复制礼包行，换新 `code/group`，增加 `account`，将 `max_uses` 设为1。限制活动时间则填写Unix秒。发行后保持码和组的身份稳定；改奖励或修订号不会清除已领记录，新活动使用新码、新组。

## 返回码

编号及文案来自【A】，以下触发条件和优先级属于【B】：

| result | 触发条件（按检查顺序） |
| --- | --- |
| 2 | 不存在、格式不合法或已关闭 |
| 4 | 未发行或尚未开始 |
| 14 | 已到期 |
| 6／7／8／9 | 账号／角色／区服／平台不符 |
| 13 | 本账号已经领取同一码 |
| 12 | 本账号已经领取同组其他码 |
| 5 | 全局额度耗尽，包括被其他账号使用的一次性码 |
| 1 | 校验通过，成功发奖 |
| 15 | 非普通兑换标志、旧序号、数据或保存失败；原版未知码文本兜底 |

失败不发奖、不写领取记录，使用原版事件18回调；非零序号附1106结束等待。好友邀请码生成、邀请关系及奖励不属于普通礼包模块，非零 `flag` 明确失败并保留 `client_flag`，不伪造邀请成功。

## 原子结算与防重复

实现：[gift_codes.py](../network_redirect/gift_codes.py)，路由：[backend.py](../network_redirect/backend.py) 的 `redeem_gift_code`。

1. 完成既有存档迁移，再获取 SQLite `BEGIN IMMEDIATE` 写锁，锁内重新读取账号存档。
2. 查询独立 `gift_code_claims` 账本，校验次数、互斥组和全局额度。数据库对 `(code,account)`、`(account,gift_group)` 分别设置唯一约束，多个后端连接共用配额。
3. 在内存发奖，生成物品数量增量、完整背包、魂魄快照、货币属性和事件18。所有业务消息编码成功后，同一次SQLite提交保存角色和领取账本。
4. 编码或保存失败回滚，不消耗兑换码。货币超过有符号32位协议上限时整包拒绝。
5. 同会话相同序号、相同数据返回缓存；相同序号换内容或旧序号拒绝。缓存256项，淘汰后仍以最高序号防旧请求。新登录清理会话缓存，账本继续防重领。
6. 断线重传复用1105响应历史；重启后已领码返回13。提交后响应丢失也不会重复加奖。

账本位于既有 `.runtime/offline/game.sqlite3`，记录码、账号、组、时间、修订号和实际奖励快照（随机成品记录抽中的编号，不记录未抽取的候选池）。普通礼包不增加充值金额或VIP等级，不触发首充，不生成系统邮件。不要删除账本来恢复资格。
