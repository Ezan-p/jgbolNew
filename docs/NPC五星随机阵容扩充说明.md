# NPC 五星随机阵容扩充说明 V2

日期：2026-10-26。基础设计：[NPC玩家设计说明 V1](NPC玩家设计说明.md)。

本次在原有模板上**新增1,485个NPC玩家**，覆盖1～99每一级、T1～T5每一档，每个“等级×战力档”保存3种不同随机阵容。原有240个NPC保持原样，两批合计**1,725个**。新批次采用更多五星神仙、不同神仙组合、混合培养流派、随机阵位和随机装备，但继续遵守V1逐级战力区间。

本次是静态对手设计扩充，没有改动生产养成／战力／战斗算法，没有写入真实玩家存档，也没有将联机入口切换为NPC。所有数字是当前本地实现的结算结果，不是官方战力分布或玩家资源获取统计。

## 2. 覆盖与五星比例

T1最高，T5最低；每档均有99×3＝297个新增NPC。配额分母是**首发＋战斗替补**，不使用背包或助威中的五星来凑出战配额。

| 档位 | 每阵最低五星占比 | 八人阵至少五星人数 | 本批实际出战五星数／出战总人数 | 实际占比 |
|---|---:|---:|---:|---:|
| T5 | 50% | 4 | 1,397／2,016 | 69.30% |
| T4 | 67% | 6 | 1,689／2,016 | 83.78% |
| T3 | 80% | 7 | 1,854／2,016 | 91.96% |
| T2 | 100% | 8 | 2,016／2,016 | 100% |
| T1 | 100% | 8 | 2,016／2,016 | 100% |

最低人数按`ceil(出战人数×最低比例)`取整，因此低等级少人阵可能要求全五星，例如两人阵的T4至少2名五星。配额外的位置另有35%概率升级为五星；其余位置T5采用三星，T4／T3采用四星。该概率是候选生成概率，经过战力筛选后实际占比不必等于理论概率。

全批10,080个出战成员实例中有**8,972个五星，约89.01%**；**821个NPC为全五星出战阵容**。原表46种可选五星基础神仙全部在本批出战阵容中出现。助威及两个背包候补也独立随机选取，候选品质为65%五星、35%四星；此比例同样属于抽取权重，不保证每个小阵容恰好满足比例。

人数规则继承V1：角色1／7／11／18／24／30／36级分别可用2／3／4／5／6／7／8个总出战位。1～4为首发，5～8依次接替1～4，最多**4首发＋4战斗替补**。2号是中路前位，1号是中路后位，3、4号为两条边路。助威在60级／80级按当前配置开放正／逆八卦，人数仍按原档位培养深度控制。背包候补每NPC保持2名，不自动登场、不直接贡献团队战力。

## 3. 随机性如何实现

### 3.1 候选池更广，仍使用真实模板

候选池由原表筛选：品质3、4、5，类型ID在3000～5999，且`type_id==base_type_id`。共有三星35种、四星66种、五星46种。品质只读取原表`quality`，不靠ID的千位猜测。保留已有基础神仙及自带法术，不混入主角占位或直接赋予进化变体。

每名NPC的出战者、助威者和背包候补共同无放回选取，同名神仙不重复占多个职责。高等级T1／T2需要主角二重以上境界时，先保证至少3名具转生资格的五星出战者，再随机布阵；其实际转生进度还需满足各次境界前置。

### 3.2 有偏好的随机抽取

候选权重为：

```text
1
+ 3 × 当前流派关键成长 / 本次候选中该项最高成长
+ 2 × 是否属于V1该流派优先池
+ 2 × 是否与已选神仙存在伙伴仙缘关联
```

攻击流看攻击成长，法术流看法力成长，持久流看防御成长。仙缘关联仅提高抽取概率，不表示仙缘条件一定凑齐；生产结算器按真实目标组合判定是否生效，不另外加“配队奖励分”。所有合法候选都有非零权重，避免永远只选几名固定强者。

选完出战组合后，按防御成长加权抽取2号前位，其余位置随机排列。每名成员的培养方向有60%概率直接使用本NPC主流派，其余40%在三流派中均匀抽取，所以主流派的单次理论概率为73.33%；接收筛选后的最终比例可能变化。`archetype`表示**主偏好**，不是“每名神仙都必须同一种职责”的承诺，逐仙方向保存在`unit_styles`。

2、6号仍按V1承伤模板培养；其他位置使用各自抽到的方向。培养点在原分配附近进行小幅随机调整并重新分配，使用总数和剩余潜力保持守恒。法术、精魄及觉醒方向由该成员的方向决定，因此相同主流派也会出现不同的技能组合。

装备在相同部位、相同品质的真实装备中随机选择；能对应该神仙装备仙缘者权重为3，其余为1。保留强化、进阶、封神、铸造、六星和灵石归属条件，不把随机装备名称套在其他装备的属性上。助威受益阵位也随机绑定，允许多个合法助威指向同一出战位。

### 3.3 可复现、去重复

主种子为`20261026`。每次抽取的独立种子由“主种子＋角色等级＋档位＋主流派＋尝试序号”的SHA-256前8字节生成。每个NPC使用自己的`random.Random`实例，生成其他等级不会推进它的随机序列。

使用**排序后的出战神仙类型集合**判断重复，忽略站位和养成差异。因此不能把相同8人换位置后当作新组合。本批1,485个组合两两不同，且与V1保存的240个样本没有相同的出战神仙集合。助威和背包不同不能用来绕过这项出战组合去重。

相同完整生成顺序与种子能够复现整个目录。跨NPC去重会参考已接受的组合集合，因此独立生成单个NPC时，如果不传入同样的已使用集合，可能接受完整批次曾拒绝的较早尝试。单个保存结果同时记录`seed`、`roster_attempt`和`development_percent`；固定这三项可以单独还原该NPC。

## 4. 五星更多，但仍落在原战力档

本次没有因为五星增多而整体上移分档。继续使用V1的495行逐级区间；生成前将旧240个保存角色以最新代码复算，结果均与原战力一致。

具体流程：

1. 按档位模板生成随机神仙、合法养成、自带法术、额外技能、装备、精魄和助威。
2. 在原区间内部20%～80%位置随机选择目标分。T1原区间没有上界，生成时另用该级V1最高样本战力的1.2倍作为本批保护上限；它不是修改T1分类上界，也不是理论最大战力。
3. 搜索0～100的整数养成比例：缩减等级增量、飞升次数、已投入培养、装备强化等级及未觉醒法术等级，并重新计算潜力预算和最终战力。这个比例作用于进度输入，**不乘最终四维或最终战力**。
4. 已发生的转生保留，当前等级不低于该转重置等级；觉醒法术保留10级。进阶、铸造、六星、精魄、命星和助威基础进度不参与该缩减，以保留已满足的前置条件。缩减后依然逐项校验。
5. T5缩减比例低于15%时，普通装备退到背包；它们不再提供面板属性，物品和灵石归属仍保留。这使低等级五星神仙可以处于尚未投入装备的状态。
6. 取落入原区间且最接近目标的候选；若整个合法进度范围无法入档或组合重复，则重抽神仙。最多80次，无法满足就报错，不把高分结果硬贴成低档。本批最高尝试序号为58，即第59次抽取成功。

保存战力调用当前`combat_power.recalculate`，单仙为`floor(3A+2.5D+1.5M+0.2H+E)`，团队汇总1～8出战位。背包不贡献分数；助威通过实际属性传递间接贡献。全批不写`combat_sources`补分，不修改角色等级门槛、成长配表或原分档边界。

这批继承V1的“无额外宠物、灵阵、称号、洞府修炼、收集和法术参悟”基线。项目中新接通的宠物和灵阵系统保持未激活状态，因此没有引入无来源的额外收益。五星占比高不代表经济获取过程已验证，也不意味着等级低的真实新玩家普遍能获得这些神仙。

## 6. 验证结果

全部1,485个样本通过原有状态校验及新增的逐级档位、五星配额、组合去重、玩家ID／名字唯一检查。具体包括神仙等级上限、培养点收支、飞升、转生和境界前置、法术与精魄槽位、灵石双向归属、觉醒／命星条件、总分一致和重复重算幂等。495个等级×档位格子均恰好有3个样本。

最终`--check`全量重建比对通过：108个产物文件逐字节一致，包括99个等级配置文件、汇总表、对战记录和来源指纹。来源清单仅跟踪生成及战斗实际依赖，工作区中无关活动后台的同期修改不影响本批复现判断。

新增生成器测试与已有战力、分路、战斗引擎测试共**66项通过**，覆盖种子复现、随机流独立、关键门槛等级五档合法性、相同神仙组合重抽、缩减不修改原始候选，以及非法潜力和同名出战成员拒绝。

对战抽样保持与V1相同口径：7、36、60、80、99级，三种主流派同档两两对局，以及相邻档同主流派对局，每组种子17／83并交换攻防，共540场。双方都装载各自精魄、命星和实际法术效果，始终使用普通八位模式。

- **539场正常全灭结束，1场触及`event_budget`返回未决0**，没有更改协议预算或伪造胜利。
- 240场相邻档对局均由较高战力方获胜；这是有限抽样的梯度检查，不是保证任意阵容胜率。
- 抽样涉及75名新NPC：73名在所测对局中正常结束；2名至少涉及一次回放限制；其余1,410名完成数据及战力校验，但没有做对战抽样。
- 未决对局为80级T1固守对强袭、种子83：`npc_v2_l80_t1_endurance` 对 `npc_v2_l80_t1_attack`，双方战力1,284,536／1,450,751，126个动作后触及事件预算。两名NPC标记为`replay_limit_observed`。

后续接入时应先避开已观察到回放限制的两名NPC，对`not_sampled`样本继续做目标玩法回放验证。不能把“数据合法”视为“客户端回放已验收”；本次没有逐个原客户端手工测试，也没有模拟真实账号获取全部五星和材料的经济过程。

## 7. 重建及读取

在仓库根目录执行：

```sh
.runtime/venv/bin/python analysis/tools/build_npc_expansion.py
.runtime/venv/bin/python analysis/tools/build_npc_expansion.py --check
.runtime/venv/bin/python -m unittest tests.test_npc_expansion tests.test_combat_power tests.test_combat_lanes tests.test_combat_engine -q
```

默认只写`analysis/npc_design/v2/`。`--check`重新生成全部样本、重跑抽样对局并逐字节比较产物，不修改已保存文件。原V1文件另做前后SHA-256检查；配置和当前源码若变化，来源摘要差异会使复现检查失败，需要复核后再重建。

读取指定NPC并独立复算：

```python
import json
from pathlib import Path
from network_redirect import combat_power, formation

root = Path('analysis/npc_design/v2')
index = json.loads((root / 'catalog.json').read_text())
entry = next(x for x in index['index'] if x['npc_id'] == 'npc_v2_l36_t3_attack')
batch = json.loads((root / entry['file']).read_text())
npc = next(x for x in batch['npcs'] if x['npc_id'] == entry['npc_id'])
report = combat_power.explain(npc['role'], formation.load_rules())
assert report['total'] == npc['settlement']['total'] == 97852
```

所有保存状态均可通过该方式查看逐阶段战力来源。完整JSON中的附件是装备与法术真值；CSV为便于查阅的展开表，背包中未装备物品可在JSON中查到。

新NPC使用`npc_v2_...`业务ID和910000000起的独立角色编号区间。神仙与附件实例ID在每名NPC内部唯一，不保证跨角色全局唯一；未来接入需要按原业务协议做作用域映射。快照是战斗角色数据，不是可以直接替换完整登录存档的账号。后续匹配仍应联合实际等级、当前绝对战力、主流派和对战验证状态选人，不能仅因五星多就把T5当作T1。
