# 独立宠物系统规则与修复说明

修复日期：2026-10-25；补全日期：2026-10-26。适用客户端：仓库中的原版 3.87。

【A】表示能从原版客户端字节码、协议或配置表直接确认的规则；【B】表示缺失官方服务端时，为本地运行补齐的规则、策略或模拟实现。【A】客户端显示的概率与公式，不等同于已经取得官方服务端源码。

## 修复范围

接通独立宠物 `1330` 的进入、吞噬、融合、出战/收回、培养、升星；接入奖励获取与仙盟捕捉所得宠物；与洞府幻化共享 `activity.home.pets`；修复属性结算、重复请求与持久化。原版图鉴、说明和界面布局继续使用原客户端。

仙盟兽栏及其离线聊天养成是另一套既有模拟玩法。本次没有把兽栏对象直接当作独立宠物对象；新增捕捉成功时，通过奖励适配器创建独立宠物，二者后续成长独立【B】。

## 原版客户端规则【A】

### 入口与协议

- `petUI.canJoin` 检查 `pet_is_open` 和人物等级，等级门槛为 **50**。`actNoticeUI` 从服务端福利响应读取 `animal_open`。
- 客户端发送 `1330`：`serial_num, flag, id, data`，其中 `flag=1`，`id` 为操作码，`data` 为 Lua 字面量表。
- 服务端通过公共事件 `2998 / id=174`（`animal_grow_event`）响应，事件数据中的 `flag` 对应宠物操作码。

| id | 操作 | 客户端请求参数 | 客户端读取结果 |
|---|---|---|---|
| 1 | 吞噬升级 | `des_id, src_list` | `del_list, update_list` |
| 2 | 三材料融合 | `des_id, src_list` | `del_list, update_list` |
| 3 | 选择出战宠物 | `des_id` | `update_list` |
| 4 | 进入/查询 | 空表 | `const_config, update_list` |
| 5 | 培养方向 | `des_id, pos` | `update_list` |
| 6 | 升星 | `des_id, src_list, order_list` | `del_list, update_list` |

【A】宠物界面使用 `id,type_id,quality,level,order,cur_exp,grow_values,star_level,train_levels,prob_compen`。`grow_values` 的顺序为攻、防、命、法。`order>0` 表示出战。

【A】`addInfo` 在收到 `main_type` 时提前返回，不再补名称、经验需求和经验宠物标记。因此服务端回包省略 `main_type`，由客户端原表补齐；服务端存档仍保留该字段。缺失 `prob_compen` 会使融合预览做加法时出错。

### 配置表

| 原版文件（`analysis/configs/`） | 作用 |
|---|---|
| `animal_base.csv` | 11种宠物、妖/灵分类、四项基础成长、阵位加成、特殊属性、经验宠物标记 |
| `animal_control.csv` | 分类×品质的开放方向、特殊属性开关、星级上限 |
| `animal_upgrade.csv` | 按分类和当前等级查升级经验，表内最高等级200 |
| `animal_exprience.csv` | 分类×品质的基础吞噬经验、融合品质价值 |
| `animal_pet_exp.csv` | 特定类型的吞噬经验覆盖值；101为经验宠物 |
| `animal_growup.csv` | 按基础成长所在区间查四种品质的成长范围 |
| `animal_train_config.csv` | 0—9星固定加成、最终成长率、升星宠物/道具消耗、培养消耗 |

【A】品质为1—4。品质1、2星级上限0；品质3上限6；品质4上限9。妖兽开放方向数依品质为1、2、3、3，均不开放特殊属性；灵兽为2、3、3、4，品质3、4开放特殊属性。

### 吞噬

【A】最多选择六只材料；选择列表排除当前宠物和出战宠物。客户端预览：

`获得经验 = Σ(材料基础经验 + upgrade_exp_rate × (材料当前经验 + 已升级消耗的累计经验))`

【A】基础经验优先取 `animal_pet_exp` 的类型/品质覆盖值，否则取 `animal_exprience`。按 `animal_upgrade` 逐级扣除需求。经验继承系数由服务端下发，原值未找到。

### 融合

【A】选择三只材料；经验宠物不能作为融合材料。客户端取目标的 `prob_compen`，加上三只材料的 `base_quality_value`，得到 `x`，使用目标分类下的品质价值表 `V(q)` 预览概率。

【A】原版 `mathProcess` 的数值常量为 **3、1**，低材料分支的阈值是 `3×V(q)`，不是0.5倍。完整分支已复原到 `pets.fusion_probabilities`：

- 没有下一品质：保持当前品质，概率1。
- `x < 3V(q)` 且没有上一品质：升一品概率 `x/(V(q+1)-V(q))`，其余保持。
- `x < 3V(q)` 且有上一品质：保持概率 `p0=1-3V(q)/(V(q+1)-V(q))`；升一品概率 `p1=(x+(1-p0)(V(q)-V(q-1)))/(V(q+1)-V(q-1))`；降一品概率 `1-p0-p1`。
- 其余情况下，若 `x < V(q+1)-V(q)`，升一品概率为 `x/(V(q+1)-V(q))`，其余保持。
- 若足以升一品但没有再下一品质：升一品概率1。
- 否则升两品概率 `min(1,(x+V(q)-V(q+1))/(V(q+2)-V(q+1)))`，其余升一品。

【A】原版只提供预览算法、成长区间和补偿字段；随机抽取、补偿如何累计、成长是否重抽，不能仅凭客户端证明。

### 升星、培养

【A】升星使用当前星级行的 `star_consume1` 与 `star_consume2`。宠物需求实际格式为 `类型或分类|品质|数量`，虽然CSV表头写了四段说明。类型1/2表示分类，101以上表示具体宠物。总计五只材料，材料星级必须为0，排除自身和出战宠物。

【A】道具消耗格式是 **`物品类别|类型ID|等级|数量`**。例如 `5|1347|1|5` 表示5个1347，不是1个；不能复用洞府的三段消耗解析器。

【A】培养方向为1—4，各方向最多4次；阶段增益及消耗取当前星级的 `each_stage_plus` 和 `each_stage_consume`。历次星级培养满的累计增益为各历史星级 `4×each_stage_plus` 之和。九星成长范围加成配置为四项各10%。

### 属性显示与服务端结算

【A】原版 `showAttrPlusLayer` 的基础加成是：

`属性值 = grow_values[属性] × 宠物等级 × plus_rate_list[属性]`

默认系数为 `[0.4,0.3,0.7,0.2]`。按 `plus_order` 的顺序、品质开放方向数，为对应阵位加上指定属性。特殊属性开放时，附加源属性值除以配置的除数（例如5表示除5），不是乘5%。

【A】每个方向最终显示值：

`floor((基础值+该阵位特殊值) × (1+(历史培养累计百分比+当前方向次数×当前阶段百分比)/100) + 当前星级该方向固定值)`

服务端现按这一显示算法计算永久加成，交由既有面板/战斗结算链处理【B：客户端算法在本地服务端的采用策略】。旧实现未乘等级、未限制品质开放方向、把特殊系数当百分数、把星级固定值提前乘培养率，均已更正。

## 缺失服务端部分的实现【B】

配置：`server_config/pet_rules.json`；服务实现：`network_redirect/pets.py`。配置明确包含 `mode: inferred`，不能作为官方数值证明。

| 项目 | 本地实现与默认值 |
|---|---|
| 系统开关 | 福利完整查询下发 `animal_open=true`，服务端仍校验人物50级 |
| 培养最低品质 | 3，与原版星级上限表保持一致 |
| 吞噬经验继承率 | 1（100%），同时回传客户端供预览使用；获得经验统一向下取整 |
| 等级上限 | 200；到达上限清空剩余经验，满级后拒绝吞噬，避免继续损失材料 |
| 背包容量 | 120；原协议单包上限32768字节；120只满背包查询已验证可编码，达到上限拒绝新增，旧宠物不会被截断删除 |
| 初始宠物 | 首次进入且从未初始化、背包为空时赠送102品质1；只执行一次，不按日期重复发 |
| 洞府初始灵兽 | 沿用洞府已有一次性赠送策略；使用统一ID分配，不再固定id=1，也不挤掉已出战宠物；满背包时延后赠送，查询与吞噬仍可操作 |

| 融合抽样 | 采用原版预览概率，服务端随机数决定结果；保留类型、等级与星级，按结果品质重抽成长 |
| 融合补偿 | 未提高品质时保留本次总价值供下次使用，上限100万；提高品质后清零；旧存档缺失按0处理 |

| 升星前置 | 0星可直接升1星；后续须先把四方向培养至4次；升星后当前培养次数重置，历史增益按原表累计 |
| 九星成长 | 升到9星时按原表的10%对保存成长值增幅取整；具体服务端应用时机为推测 |
| 材料验证 | 服务端重新核对身份、数量、品质、分类、星级与出战状态；不信任客户端 `order_list`、经验、概率、余额或消耗 |
| 持久化与重放 | 复用活动事务：副本结算、编码成功后保存；错误整体回滚；同连接同序列同包返回缓存，不重复扣料；过期请求拒绝 |
| 奖励适配 | `journey.grant` 的类别15创建宠物；编号单调递增，删除材料后不复用；仙盟新捕捉成功通过该入口发放 |
| 洞府幻化 | 继续使用原有1348/22查询与幻化处理器；与独立系统共享宠物实体及出战状态，幻化成长记忆仍属既有推测规则 |

原版UI没有独立的买宠物/抽宠物请求；界面的“召唤”指选择出战。未伪造新的1330操作码。持续获取沿用本地仙盟游历捕捉、既有类别15奖励入口，培养道具仍使用原物品体系。补齐洞府商店三种升星石来源【B】：1347/1348/1349每份5个，分别消耗1361道具300/600/1200个，每日各限10份；原有1345培养材料兑换保留。价格和限购为推测，商品展示与扣料沿用原版洞府商店协议。
