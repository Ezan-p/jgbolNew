# 金卡充值系统实现说明

更新日期：2026-10-27。

**本轮修正：** 充值和背包用卡后的活动状态改为静默同步，不再自动打开活动页；移除新增的月卡日奖底栏、底栏续期按钮及“剩余份数”机制；成长基金原购买按钮直接进入金卡选择，绕过真实支付渠道开关，支付后在原基金页刷新可领奖状态。

本次把离线游戏的免费模拟充值改为**消耗背包中的传世金卡支付**。充值入口、元宝六档布局、VIP页、集市／仙灵店铺跳转、首充和月卡入口继续保留；点击金额后先打开金卡数量选择面板，确认后才扣卡和结算。旧 `1111/event_id=250` 免费充值及无卡 `1112` 预购不会再发放额度。

这里的“充值”是离线道具结算，不调用渠道支付。已实现的充值活动统一读取这一结算的本金；尚未实现的旧活动列在第9节，不能把统一充值服务理解为这些活动的玩法也已完成。

## 1. 面值与原版证据

| 道具 | 模板ID | 本次使用面值 | 说明 |
|---|---:|---:|---|
| 大传世金卡，即原「传世金卡」 | 1152 | 50元／张 | 与原名称表文案一致 |
| 小传世金卡，即「传世金卡（小）」 | 1156 | 5元／张 | **按本次用户明确要求设置；原包文案实际为10元，不能把5元写作原版确认值** |

本金换算固定为 `1元 = 10充值元宝`。大卡每张增加500本金，小卡每张增加50本金。客户端适配器同步小卡的离线说明，避免充值面板与原道具提示矛盾。

原始证据与实现规则分开：

- 原元宝六档及赠送、月卡／基金价格来自 [order_config.csv](../analysis/configs/order_config.csv) 的大陆 `category=1/7`；`item_price` 的单位是分。
- 月卡原UI [monthCardUI.lua.txt](../analysis/evidence/lua_named/lua/ui/monthCardUI.lua.txt)：原源码L158显示每日100元宝，L356发送月卡领奖，L410判断到期时间，L421按自然日检查领取，L430检查剩余时间少于33天才可购买。
- 金卡原名称、图标与10元小卡文案见 [原版金卡说明](至尊金卡、道尊金卡、传世金卡原版机制与图标说明.md)。该文记录原包证据，不被本次5元离线规则覆盖。
- 小卡5元、单充补全奖励、部分活动数值及背包兑卡赠送策略属于本次离线规则；未取得原官方服务端经济配置。

|---:|---:|---:|---:|---:|

普通元宝商品价格和赠送沿用上表原配置。基金原表450元宝用于确认45元计费本金；本地基金沿用“购买开通、按等级返还”的规则，不额外即时发450元宝，属于离线结算选择。

面板展示当前商品、应付金额、两种可用卡数量及所选卡张数。可以增减大小卡，使用推荐组合或纯小卡组合，提交前取消不扣卡。提交后按钮变为“关闭面板”，关闭不会撤销已提交订单；重新打开会保留待确认订单并以同一订单号重试，明确失败回执才允许重选。必须满足：

```text
50 × 大卡数量 + 5 × 小卡数量 = 商品金额
```

例如100元可用2张大卡，也可用1张大卡加10张小卡，或20张小卡；45元基金使用9张小卡。**不支持超额支付、找零或把一张大卡拆成小卡**。锁定、占用或装备中的卡不属于可用库存，数量不足会明确失败。

服务端只接受服务器商品表中的ID及合法非负整数张数，不接受客户端自报价格、元宝、赠送或VIP额度。面板预检查用于提示，最终以服务端重新读取的库存和价格为准。

背包原 `1051` 使用入口也接入1152／1156，支持一次1～15张，严格扣除请求指定堆叠；这一批使用视为一笔充值。背包兑卡按面值给本金，不套用六档商城额外赠送；符合条件时仍享有一次首充本金翻倍，并触发同一套VIP及活动统计。

## 3. 统一统计口径

每笔金卡支付依次完成：验证订单和库存 → 扣除金卡 → 商品到账／权益开通 → VIP和各活动计本金 → 编码客户端响应 → 一次提交存档。

| 统计／奖励 | 本次接入内容 | 金额口径 |
|---|---|---|
| VIP | `charge_gold`、VIP升级、下一档进度、VIP礼包和相关玩法额度刷新 | 累计支付本金；消费不降级 |
| 首充 | 首次普通元宝充值／背包兑卡翻倍；首充礼包资格及原领奖入口 | 只翻倍本金，赠送不翻倍 |
| 单充 | 金卡面板中的单充奖励列表，各档独立领取 | 当前活动期最大一笔本金 |
| 即时充值狂放送23 | 活动期累计、达标状态、批量领取 | 活动期本金合计 |
| 独立充值礼包 | 活动入口30、原1215／1216查询领取链 | 活动期本金合计 |
| 七天充值送礼71 | 当日金额、连续充值天数、已达成最高连续记录 | 当日本金和连续有充值的日期 |
| 天天有礼74 | 当日礼包、周累充礼包 | UTC+8当日本金、当周本金 |
| 其他已接福利 | 幸运轮盘33、感恩充值34、VIP嘉年华21、年年有吉48、周年礼包60、金猴有礼67 | 延用各活动条件，充值输入统一用本金 |
| 仙灵店铺 | 月累计、礼包资格和提示 | 当月本金 |
| 天机阁 | 周期累计、金砖邮件及相应兑换额度 | 当前天机阁周期本金 |
| 两周年／元始祈愿 | 充值礼包解锁、当日充值及已激活礼包资格 | 活动期本金累计，并记录当日是否充值；已激活资格按活动期保留 |
| 如来转盘 | 充值次数、累计抽奖机会和豪礼 | 当前如来周期本金 |

月卡购买和基金购买都计入上表的充值额度，包括VIP和单充。月卡每日100元宝、成长基金等级返还、首充双倍、档位额外赠送、领奖所得元宝、邮件里直接发的元宝，**均不再次计入充值本金**，不会产生“领奖又触发充值”的循环。

例如使用1张大卡购买50元档，普通元宝为500+50；若是首个普通充值，再加500首充奖励。无论另有多少活动奖励，所有充值统计本笔只增加50元／500本金。

## 4. 首充、单充、累充与领奖

### 首充

普通元宝商品或背包直接兑卡，首次额外发放一倍本金；持久化 `first_charge` 保证只享受一次。月卡和基金可取得首充礼包资格，但不占用普通元宝首充翻倍。

首充礼包沿用 `charge_gift_config.csv` 和 `1201/flag=6`，只能领取一次。原充值页专用首充按钮恢复预览和领奖，不再显示“尚未开放”。

### 单充

离线单充默认门槛为6／30／98／198元，奖励为12／60／196／396元宝，分别来自 `welfare_rules.json.single_charge`。这是复用现有本地福利档位的补全配置，不能标成原官方单充奖励表。

每笔充值记录最大本金；任一笔达到门槛即可逐档领取，每期每档一次。两笔5元只构成10元累充，不构成一笔10元单充；一笔100元可达到6、30、98三个档。一个订单混用多堆大小卡仍只算一笔。历史存档仅有每日合计而没有单笔明细的部分，不反推单充记录。

### 累充和周期

- 期间累充和独立充值礼包：使用当前福利活动期合计，奖励各档一次；独立礼包与福利23的领奖记录互相独立。
- 天天有礼：原字符串明确写“周累充礼包周一重置”，本次由错误的整期累计修正为**UTC+8周一00:00重置**。日礼包每天重置，周礼包按周分别记账；旧版本已领周礼包保守迁移为升级当周已领，下一周正常重置。
- 连续充值：漏一天中断当前连续段，已经达成的最高连续日数保留，避免已获资格丢失；只按服务器记录的成功充值日期累计。
- 福利30天活动期从角色首次启用福利开始，到期不自动重开。单充、独立充值礼包及其他期间福利在结束时刻停止充值计入和领取；成长基金等级返还、首充礼包不受这一期限限制。天机阁、如来、元始、仙灵各自沿用其专项周期，不把它们强制合并为30天。

到期前可领取的期间奖励应及时领取，未提供过期补领；单充／礼包过期会返回明确提示。原本独立的等级活动按期末等级结算，仍遵守原有规则。

### 成长基金

从福利中的成长基金点击原“购买”按钮，会保留基金页并打开45元金卡选择面板，使用9张小卡。取消不会扣卡；确认扣卡成功才写入永久购买标记，同时增加450充值本金。每个角色只能购买一次，重试订单不会再次扣卡；未购买不能领取。

现有离线返还档位如下，数值沿用本地配置，不视为已还原的官方服务端奖励表：

| 主角等级 | 该档返还元宝 |
|---:|---:|
| 10 | 300 |
| 20 | 500 |
| 30 | 800 |
| 40 | 1200 |
| 50 | 1800 |
| 60 | 2400 |

合计7000元宝。原“领取”按钮一次发放所有已达等级且尚未领取的档位；每档仅一次，重登保存领取记录。低等级购买后可以后续升级再领；高等级购买可以一次领取全部已达档位。基金返还不再次增加充值额度，且不受福利30天活动期限限制。购买、发奖及领取记录都在服务端校验，失败整体回滚。

充值后的状态通过 `80/local_welfare` 下发，更新现有缓存与已打开的内容；不使用会导航的活动回复47／93／127来推送充值结果，也不自动发起活动查询。玩家主动打开活动或领取奖励时，仍走原生查询／领奖协议。

## 5. 月卡完整流程

1. 从充值页或原月卡入口打开月卡页面，购买时进入金卡面板。
2. 支付50元金卡，到账500元宝，VIP及所有已接充值统计增加500本金。
3. 到期时间按 `max(当前时间, 现有到期时间) + 30 × 86400秒` 计算，续期保留剩余时间。
4. 月卡剩余时间少于33天允许购买，达到或超过33天拒绝；此门槛来自原UI。购卡后立即再续一次可能被允许，续至约60天后不能继续囤叠。
5. 有效期内每天按UTC+8领取100元宝，使用原 `1201/flag=9,id=0` 和事件74。只判断有效期和当日是否领取，不再使用额外的日奖份数；当天续期不重置当天领奖记录，错过的日期不补发。
6. 到期时间等于当前时间即失效，不再发每日奖励；续期后按新有效期恢复。

按本轮要求，删除月卡下方新增的“剩余日奖×份／每日100元宝／金卡续期”底栏，恢复原月卡页面。充值页的50元月卡购买入口、原月卡领取入口及月卡玩法权益保留。有效期仍为30×24小时，按自然日领取，因此非零点购买可能覆盖31个自然日，不再人为限制为30份。

月卡时间同步至原角色属性21／22及客户端状态；已有唤神额外次数、洞府一键施肥、九幽宝图快速寻宝等权益读取同一个 `month_card_time`，无需分别开通。它们原有的材料、次数和玩法条件继续生效。

原月卡页写的“天缘召唤每日增加1次”对应唤神，不是普通元宝召唤。战斗加速及非历险立即跳过由原 `fightUI` 读取月卡到期时间生效，只改变回放；服务端战斗结算保持权威。月卡还增加**集市特惠魂缘丹1024每日1个购买额度**（原 `item_buy_config.csv` 第15项，单价100元宝，默认每日1个变为2个），本次已补入服务端商品表及购买校验。续期不清空已买次数，到期立即失去额外额度，其他商品和普通价页不增加额度。

旧存档的 `month_card_rewards_remaining` 不再参与资格判断，即使值为0也不阻止有效期内的当日领取；下次月卡购买或领取会清理该废弃字段。已购有效期、已领元宝及当天领取时间不回退。

## 6. 金卡发行：邮件 → 背包 → 支付 → 奖励

本次不向真实存档自动赠卡，不增加用充值奖励无限兑换金卡的循环。正常发行使用既有系统邮件工具；以后也可由活动奖励调用同一物品发放路径。

下面是可复用的操作示例，**文档中的命令未在此次实现过程中对真实账号执行**。在项目根目录创建 `/tmp/gold-card-issue.json`，例如：

```json
{
  "key": "gold-card-issue-20261027-001",
  "title": "传世金卡发放",
  "body": "大传世金卡每张50元，小传世金卡每张5元。领取后可在充值入口支付。",
  "prizes": [[5, 1152, 2, 1], [5, 1156, 10, 1]]
}
```

附件数组顺序是 `[对象类型, 道具模板ID, 数量, 等级]`。按实际存档账号替换 `YOUR_ACCOUNT`：

```sh
# 预览校验，不写入存档
.runtime/venv/bin/python -m network_redirect.system_mail --account YOUR_ACCOUNT --file /tmp/gold-card-issue.json

# 确定发行后停服，发放，再恢复离线服务
.runtime/venv/bin/python redirect_game.py stop
.runtime/venv/bin/python -m network_redirect.system_mail --account YOUR_ACCOUNT --file /tmp/gold-card-issue.json --send
.runtime/venv/bin/python redirect_game.py start --offline --probe
```

重登后在“其他 → 消息 → 附件”领取，金卡进入背包；再从任意现有充值入口打开金额档位、选择卡数、确认支付，最后去单充／福利／活动／VIP页面领取已解锁奖励。

发邮件只是给卡，尚未增加充值额度；领取邮件也不计充值，只有成功消耗金卡时才计入。相同邮件批次重复发放不会恢复附件领取状态；相同批次换内容会被拒绝。工具有停服排他锁、原存档备份和发行审计，详见 [系统邮件说明](其他模块与系统邮件调试.md)。

## 7. 持久化、幂等与回滚

- 新金卡订单使用 `1111/event_id=251`，数据为 `item_id/order_id/large_count/small_count`。单充领取使用 `event_id=252,index`；背包兑卡由适配器转为 `event_id=253`，携带唯一订单号及原道具使用字段。
- 每账号保存已结算订单、请求指纹、商品、卡数、本金、赠送和结算时间。相同订单同内容重试不再次扣卡、发元宝或触发活动；相同订单改内容会拒绝。
- 正常背包兑卡的253订单跨重启保留，避免原客户端每次启动重置请求序号导致新兑卡与历史记录冲突。服务端仍兼容原1051，兼容路径使用 `bag-请求序号` 与完整道具指纹保守防重；正常游戏使用新253路径。
- 充值和福利领奖以SQLite写事务重新读取最新存档，扣卡、订单、VIP、活动统计、奖励和邮件共同提交，避免并发领奖把新的充值存档覆盖。库存不足、锁卡、非法参数、响应编码失败或事务失败会回滚，不留“扣了卡却没有额度”的半笔订单。
- 成长基金购买标记、月卡每日领取时间、单充／累充档位标记、首充翻倍和礼包领取记录持久保存。客户端刷新或重登不重置资格。
- 新充值订单、月卡领奖和单充领奖拒绝比上一次成功充值更早的服务器时间；月卡每日领奖也比较记录日期，防同日和向已领取日期回拨重复领。系统时间仍是离线游戏的计时来源，不接可信外部时钟。
- 旧模拟充值已经保存的元宝、VIP和已领取奖励保留，不倒扣历史存档；只是关闭旧的无道具增额入口。旧记录不能自动补造不存在的单笔信息。
