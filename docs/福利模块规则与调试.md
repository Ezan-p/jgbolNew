# 福利模块规则与调试

本次针对主界面右侧“福利”（`actNoticeUI`），不是“日常”签到或独立 VIP 页。原包能证明的协议、界面条件和 CSV 规则标为【A】；原服务端缺失而补出的配置、离线结算策略标为【B】。不能据此宣称恢复了官方完整经济数值或真实全服活动。

## 实现与证据

- 【A】原包 `lua/ui/actNoticeUI.lua`：查询、列表、17 个有内容的活动分支、按钮、预览、领奖回调。`createFightRank`（类型2）仅为空壳，不将空白页伪装成可玩福利；封神榜沿用已有活动模块。
- 【A】`common/common_def.lua`、`event_mgr.lua`：1127 查询/领奖（flag=1/2）；1239 团购；1352 每日充值（id=1查询、2累计奖、3当日奖）；1201 flag=6 首充礼包；1112 event_id=3、item_id=8 成长基金预购。
- 【A】奖励状态1=未达成、2=可领、3=已领；事件127、135、202、60分别对应原版回调。提示通过配置事件80的common_config更新。
- 【A】可复核的原始资源路径和 SHA-256：[audit.json](../analysis/evidence/welfare/audit.json)。反汇编包含原源码行号及数字常量，位于同目录；重新生成：`.runtime/venv/bin/python analysis/tools/audit_welfare_rules.py`。
- 【B】服务端实现：[welfare.py](../network_redirect/welfare.py)；完整数值：[welfare_rules.json](../server_config/welfare_rules.json)。奖励数组顺序为`[对象类型,编号,数量,等级]`，不要与原 CSV 的`类型|编号|等级|数量`混淆。

## 时间、存档与防重

【B】服务器按UTC+8自然日切换；活动以角色首次启用福利的时间为起点，周期30天，不冒充2018年的官方排期。没有自动重开活动。成长基金长期保留；等级奖励到期结算。原子结算先验证、生成响应，再写入SQLite；非法参数、材料不足或序列冲突不发奖、不扣款。同包重放返回缓存；重启后的领取记录和模拟订单仍能防重。

【B】与仙灵店铺共享模拟充值基础金额；VIP、月累计与福利在同一角色事务中更新。历史存档不追溯补发未知充值活动奖励。

## 客户端修复

【A】保留原版布局、资源、按钮发送和主要回调；补齐团购礼包的item/buy_count、兑换双来源、周年两行奖励结构、周年礼包status_list。领奖结果使用原版要求的prize_list，首充使用attach_list。

【B】小型运行时适配器 `welfare_client.lua` 处理每日充值独立数据初始化、重复添加74标签、每日奖励显示，以及本地基金购买说明。模拟支付说明不代表官方渠道支付成功。适配器可恢复，不改原APK资源。

## 验证及边界

- 后端福利、VIP、仙灵专项：40项通过，包括材料不足回滚、全部手动领奖分支、重复领取、跨日、重启、伪造转盘结果、团购返差额及返利结算窗口。
- 完整测试通过330项（本机临时端口测试需要沙箱外运行）；结果见 `.runtime/welfare-full-tests.log`。
- 原版客户端56项检查全部通过，涵盖17个页面、各类领奖回调、基金购买请求和每日标签去重；测试脚本 `analysis/tools/build_welfare_client_fixture.py` 使用临时服务端角色，恢复客户端玩家和发送函数，不增加真实存档资源。最终结果保存于 `analysis/evidence/welfare/client_result.json`。
- 【B】全服排行及好友邀请使用离线实现，不连接官方系统。类型34采用本地单人第一名，达标和排行两行奖励在结算期生成持久化邮件，查询1102、领取1103，防止重复领取。离线邀请不产生真实社交关系。

## 使用

重启本地离线服务并重新登录，点击主界面右侧“福利”。充值相关项目通过“本地模拟充值”达成条件；正常状态下未达成项目保持灰色，不能为了测试随意解锁。配置调整后需重启服务；不要删除 `.runtime/offline/` 存档。
