# 小包子与贡献令使用机制及调试说明

## 2026-10-28 恢复道具批量使用更新

用户指定小包子1020、包子1022、仙丹1023支持批量使用。背包库存至少2个时，使用按钮调用原版数量选择框，范围为1至当前道具库存；只有1个时保留原单次入口。服务端1051按所选数量一次性扣除库存，小包子总恢复量为数量×5体力，包子为数量×10体力，仙丹为数量×10精力，事件21返回实际数量和总恢复量。原版结果回调直接展示总恢复量，无需修改提示。

三种道具均无每日使用上限；普通包子和仙丹按实际消耗个数递增每日计数及成就，小包子仍不计入普通包子计数。快捷购买仍为单个，沿用此前额度与价格规则。保留旧客户端包子／仙丹`item_count=0`表示使用1个的兼容，小包子数量必须为正整数。库存不足、锁定、错误目标等请求不扣物不加资源，相同请求重传不重复结算。

实现：`network_redirect/resource_item_client.lua`、`journey.resource_item`。回归：`tests/test_small_bun_contribution.py`及`analysis/tools/verify_resource_item_client.py`。以下原有单次使用说明是本次调整前的历史记录。

更新日期：2026-10-27（Asia/Shanghai）。适用于本仓库3.87离线后端。两种道具已接入原版背包1051请求，不需要修改APK；正在运行的本地服务需重启后加载新代码。

## 已修复的问题

小包子1020、贡献令1029原来都落入 `immortal.exchange`，返回事件55“请选择正确的界魂”。现在分别进入旅途恢复道具和仙盟贡献处理器，完成库存扣除、效果到账、属性同步和事件21提示。

另外，原 `commonLayerUI.recvUsedItem` 用 `effect_value` 格式化恢复／贡献提示。原1022包子、1023仙丹回包也缺此字段，本次一并补齐，避免实际到账后客户端提示报错。

**【A】** 表示原包CSV／Lua及原版客户端验证；**【B】** 表示无法从原服务端确认的离线结算选择。

|---|---|---|

## 完整链条与事务边界

- **小包子**：现有乾坤袋 `small_bun` 奖池 → 背包1020 → 1051 → `journey.resource_item` → 库存减少、体力增加 → 1032属性101与背包快照 → 事件21显示增加5体力 → 可用于旅途战斗。
- **贡献令**：现有高级礼盒1121等奖励 → 背包1029 → 1051 → `guild.use_contribution_token` → 累计／可用贡献同时增加 → `guild.prepare` 同步成员的 `totalcontrib/contrib` 和排名 → 1032属性146／148与背包快照 → 事件21显示实际贡献 → 仙盟商店可以消费可用贡献，累计贡献保留。

回调格式为 `{result=1,type_id=1020或1029,count=实际消耗数,effect_value=实际增加值}`。库存及属性包先发送，提示回调随后发送。贡献令批量15个的提示为增加1500贡献。

服务端校验模板与实例ID、道具类别、锁定、库存、数量及目标角色。目标必须为自身或原客户端默认0；失败返回事件55，不提交扣物品或奖励。清空堆叠后删除实例，属性增量与背包快照负责更新客户端。现有处理器先编码业务响应，再保存角色；异常导致本次结算不提交。

沿用旅途／仙盟处理器的会话内序号防重：相同包重发返回缓存，不重新扣物品或到账；相同／过期序号更换内容被拒绝。效果及库存写入SQLite，关闭重开后保留。**防重缓存属于当前后端会话，不是跨服务重启的永久请求账本**；新会话再次发送合法使用请求是新的消费。

当前原名称表称小包子来自“主角升级奖励”，本次验证了已有乾坤袋产出到消费链，没有凭该文案新增升级赠送数量或自动补发。未接的升级奖励入口仍按总清单记录。其他活动能否产出贡献令取决于各玩法开放状态，不因接通道具使用而自动开放。
