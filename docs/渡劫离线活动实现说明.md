# 渡劫离线活动实现说明

发布补记（2026-10-30）：本文所述本轮修复已整合进最新v106（25项版），详见[v106发布及存档验证](v106内容整合与存档兼容说明.md)。下文“需重新打包／未构建”等为功能开发时的历史记录。

更新日期：2026-10-30；当前规则版本 `offline-rape-4-players`。入口「活动 → 渡劫」，8级开放，对应 `crossDoomUI`，不是 `undergo_ordeal` 历练。本版继续使用本地 `analysis/npc_design/players` 具名NPC替代玩家对手，扩大刷新候选和近期避重范围，并补齐旧盘身份迁移。沿用骰面人数、整列奖励、剩余刷新次数和“继续”换盘规则。

## 1. 当前玩法

| 项目 | 实现 |
|---|---|
| 三列守卫 | 每列骰面为1～6，该列就生成1～6名守卫；例如骰面4／6／2，对应4／6／2名守卫；全盘共3～18名 |
| 挑战消耗 | 每场1精力，真实模拟战斗；失败保留目标，可调整阵容后重试 |
| 单守卫奖励 | 无法术、无银币；只记录击败状态。骰面为1时，击败唯一守卫即完成该列 |
| 整列奖励 | 全部守卫击败后，只发该列预览的法术类型和数量，每列一次 |
| 顺子 | 骰面升序或降序连续时，每列预览2本；普通盘每列1本，结算始终与预览一致 |
| 豹子 | 保留原客户端骰面动画，但不自动击败守卫、不自动发奖，仍须逐列完成 |
| 单守卫刷新 | 5元宝，替换为另一NPC，保留显示位置；已击败守卫不能刷新，不扣整盘免费次数 |
| 整盘免费刷新 | 每次扣1次免费额度；响应立即返回扣除后的剩余次数，普通账号当前额度3次，VIP沿用现有表 |
| 整盘付费刷新 | 20元宝；不再增加免费使用计数，剩余免费次数不会变负数 |
| 一键渡劫 | 选项始终显示，使用条件为25级或VIP5；VIP5（含）以上显示“免费”、免元宝，VIP0～4显示预计元宝费用、每场扣1元宝；按当前位置逐场模拟，场数受剩余精力限制 |
| 通关后继续 | 点击“继续”立即请求新盘；优先消耗1次免费刷新，额度不足则扣20元宝；资源不足保留已完成盘并提示 |

普通盘完成三列共发3本法术，顺子盘共发6本，与守卫总数无关。法术均为1级独立物品。一键渡劫完全复用单场战斗与整列结算，不直接判胜；失败也消耗该场精力及扫荡费用。

普通查询、退出后重进或重连只读取当前盘，不会暗中刷新或扣费。整盘仍有守卫未击败时，服务端拒绝“继续”；玩家可以使用正常刷新按钮放弃本盘重新开始。

## 2. 本次两个界面问题的原因与修复

### 一键渡劫费用、奖励及残留守卫（2026-10-30）

- **费用显示**：事件40新增 `sweep_gold_per_fight`，与服务端实际扣费共用函数：VIP5以下为1，VIP5起为0。客户端按钮旁费用与确认框统一计算 `min(未击败守卫数, 当前精力) × 单场费用`，点击时重算；零精力、元宝不足或未开放时不发送扫荡请求。原按钮是 `createCardPage` 内的局部闭包，补丁在建菜单时替换其绑定，并保留原确认框样式。兼容旧服务端时按VIP等级回退计算。
- **入口显示（同日追加）**：取消原客户端按等级或全盘通关隐藏“一键渡劫”的行为，选项始终保留。VIP5（含）以上按钮旁显示“免费”，VIP0～4显示“预计数量元宝”；精力不足或没有目标导致的0元宝不显示为VIP免费。25级以下且不足VIP5的玩家点击时仍提示“一键渡劫需25级或VIP5”。免费仅指免元宝，精力仍按实际场数消耗。
- **虚假法术奖励**：原生 `showRapeSweepRet` 只判断 `skill_type` 和 `skill_count` 是否为真，Lua中的0也是真，导致每次普通胜利都加入一个零数量法术条目。事件114现在只在实际发奖的场次携带法术字段，客户端也过滤旧响应中的零数量；完成普通列显示1本，顺子列显示2本。
- **残留守卫**：原生 `flipCard` 的排序比较器实际为 `a.v.rand < b.v.rand`，即升序；旧记录中“降序显示”的结论有误。旧扫荡按字典保存顺序、分别在每个对象类型内编号，部分扫荡、失败或旧盘混合对象类型时会标错头像。服务端现在按整列全部守卫的显示顺序编号，保留已击败者的位置；结果同时携带 `object_type/object_id`，客户端按实际头像映射匹配身份，随后同步盘面数据。失败及未挑战守卫仍可挑战和更换。

### 免费刷新次数

原客户端 `setFreeFreshTink` 直接显示 `card_data.free_count`，`freshCard` 也以该字段判断免费或付费；它不计算“总额度减已用次数”。旧服务端一直把总额度发送为 `free_count`，导致服务器已扣次数而左侧仍显示初始值。

现改为：

```text
free_count = max(0, rape_flush_limit - rape_refreshes)
```

只有成功免费刷新增加 `rape_refreshes`，事件40直接携带新剩余次数。客户端原回调收到响应后重绘次数，无需退出活动。另设 `rape_total_refreshes` 统计免费、付费和“继续”的成功换盘，供日常活跃度使用；两个计数都按UTC+8跨日清零，失败及普通查询不累计。

### 一键渡劫后的“继续”

原版 `pressGoOnCard → pressInfoBegin` 发送1029的 `flag=1`，只查询服务端仍保存的已完成盘。服务端并不知道这是点击“继续”，因此重复显示已击败的三列。

新增可恢复的 [rape_client.lua](../network_redirect/rape_client.lua) 补丁，让“继续”发送1029的本地扩展 `flag=4`。服务端先核对整盘已结算，再选择免费或付费刷新，返回原生事件40的 `update_type=2/3`。补丁同时清除上一盘 `is_all_pass`，避免一键渡劫完成状态残留。普通查询仍为 `flag=1`。

连续双击时，首个请求生成新盘，第二个请求因新盘未完成而被拒绝，不会连续扣费；相同请求序号的重放沿用Backend缓存。客户端不预先扣除本地次数，最终显示以服务器成功响应为准。

补丁通过 `summon.client_source` 随现有客户端兼容代码加载，并在卸载时还原原函数；需要重新启动本地重定向／游戏以加载新版补丁。

### 骰面为1时敌人不显示（2026-10-28）

原客户端 `createCardHead` 的布局分支只覆盖2～6名守卫（原Lua源码行1751～1775）；仅有1名时位置表为空，既不创建头像，也不建立点击目标映射。服务端已生成的守卫因此无法在界面挑战。

`rape_client.lua` 现在补充单人居中布局，沿用原头像、点击菜单、`列号*100+序号` 标签及 `cardPage_enmey_map` 字段。保留显示延迟、奖励展示回调和已击败头像变暗；2～6人继续调用原函数，卸载补丁时恢复原函数。无需重新投骰或修改存档。

运行 `.runtime/venv/bin/python analysis/tools/verify_rape_single_guard.py` 在原生Cocos中使用独立节点验证；加 `--install` 可在检查通过后更新当前客户端，并补画当前盘缺失的单人头像。验证先复现原函数漏画，再覆盖三列、1～6人、普通／快速显示、点击与挑战目标、已击败状态、替换目标重绘及安装／恢复，共41项，另运行既有“继续”和免费次数Lua回归。测试请求被拦截，不消耗账号资源。记录见 [single_guard_validation.json](../analysis/evidence/rape/single_guard_validation.json)。

## 3. 离线NPC匹配（players扩充）

渡劫通过独立的 [activity_rape_npc.py](../network_redirect/activity_rape_npc.py) 直接接入 [players/catalog.json](../analysis/npc_design/players/catalog.json)，不再依赖逐鹿模块的候选策略。资料库共1,725名具名NPC：V1的240名及覆盖1～99级的V2的1,485名；运行时排除源阵容已标记 `replay_limit_observed` 的样本。所有正式姓名、玩家ID、头像、VIP和个人资料均来自players配置，不随机伪造新身份。

每名NPC使用players记录的 `source_file` 所指向的完整阵容，经生产战力算法重算后匹配。每列位置仍循环采用玩家出战战力55%／70%／85%的目标；角色等级不超过玩家。具体筛选规则：

1. 按绝对战力差、等级差和NPC标识排序，取最近最多72名（上一版24名）。
2. 只保留战力误差不超过“最近样本误差＋目标战力20%”的候选。不为增加人数任意放大属性或跨越等级限制。
3. 优先随机选择既没有在本盘出现、也不在最近108名记录中的NPC；没有新面孔时，先回退到本盘未出现的候选，最后才允许重复。
4. 单守卫刷新先按原候选池确定战力窗口，再硬性排除刚才的NPC，并优先避开本盘其他守卫。不能因排除旧对手而把窗口推向更强的远端样本；没有合适替代者时提示“当前战力范围内没有其他渡劫NPC”，不扣元宝、不改变目标或历史。
5. 历史按账号保存，只记最近108个唯一NPC；普通查询不改变历史或对手，生成新盘和成功单人刷新才更新。旧存档首次接入时把当前盘身份加入历史。旧真人栏位缺少NPC身份时，按同一匹配策略替换为players角色并参与同盘避重、记录历史；已有NPC但缺少玩家ID时补齐原身份。保留场景对象ID、原栏位、顺序、胜利、已领奖及反击进度。

因此1,725名并不代表任意等级都能匹配全部NPC。极低战力、低等级或稀疏区间可能重复；匹配强度优先于绝对不重复。概率、72人候选窗和108人避重长度属于离线设计规则，可在 `rape_rules.json` 调整。

新守卫保存两种编号：递增的场景对象ID用于挑战与刷新；players的 `npc_player_id` 用于身份一致性。展示姓名、资料页、阵容和实际战斗引用同一NPC；守卫头像继续使用原渡劫神仙头像字段，资料页使用玩家头像。反击记录仍保留原NPC，不随刷新重新抽取。

战斗保留完整首发、替补、装备、法术、精魄、命星、飞升、转生和助威结算。生成后的对手保持固定，升级不会让旧对手同步变强；刷新时才重新匹配。NPC源文件只读，玩家不会获得NPC背包或养成资源。

## 4. 离线反击与持久化

反击为独立玩法，保留上一版策略：每天首次未胜最多生成一次本地NPC反击机会，有效期24小时，不抢走玩家库存。反击胜利发消息指定法术1本和原配置银币；此处不属于三列守卫结算。消息可查看阵容或忽略；伪造、过期、已完成消息不能重复领奖。

主盘、守卫胜利状态、整列已领奖、序号、刷新次数和反击记录均保存到当前账号。操作在离线副本完成，编码成功后提交；资源不足或非法请求不残留扣费和奖励。请求缓存仅在当前服务会话有效，重启后以持久化击败／已领奖状态防止重复发奖。

### 2026-10-30 反击胜利后无法退出修复

原生 `fightUI` 第2688—2694行在反击战斗结束后返回消息页，并调用 `showFightBackTink`。后者从事件77读取 `skill_type`，传给 `createBackSkillPrize`。旧服务端只发 `result/request_id`，遗漏了法术编号；原生奖励窗口先在第2318—2319行添加高层弹窗和触摸拦截层，再在第2357行用缺失编号创建法术图标，异常导致第2384行的确认按钮未创建，因此画面仍显示但无法操作。

- 服务端事件77补齐与实际奖励一致的 `skill_type`，保持胜负码、发奖与防重复结算规则。
- 客户端在创建奖励窗口前校验法术编号；兼容旧响应时仅从相同 `request_id` 的反击消息补取编号，兼容数字／字符串键。
- 编号仍无法恢复时显示普通提示，不创建触摸拦截层；正常奖励窗口继续使用原生确认按钮退出。
