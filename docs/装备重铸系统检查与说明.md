# 装备重铸系统检查与说明

检查日期：2026-10-28。范围：当前工作区的本地后端、3.87 原包配置与客户端反汇编、临时数据库验证。

装备重铸已接入本地服务：从背包使用装备重铸符，选择一件允许的五星装备，再指定武器或防具，随机生成另一件装备并继承养成。当前为主角25级开放，每次消耗1张重铸符，不消耗元宝或银币。

本次确认正常独立装备的候选池、扣费、养成继承、灵石返还、防重和持久化链路可用；同时复现了**六星装备前后端规则不一致**、**旧叠加装备可能重复返还灵石**两项问题，详见第七节。本次只生成检查资料并修正文档表述，未修改游戏逻辑、规则配置或实际账号存档。

证据标记沿用项目约定：**【A】**为原包能核实的客户端行为或配置；**【B】**为当前本地服务端补全策略，不代表原服认证规则；**【检查】**为本次代码检查或隔离验证结果。

## 一、玩家操作流程

1. 准备“装备重铸符”（道具ID `1100`），主角达到25级。
2. 将待重铸装备卸下；如已锁定，先解锁。装备必须属于第二节的十种白名单。
3. 在背包选中装备重铸符并使用，打开重铸界面。
4. 点击装备选择框，选中空闲五星装备；再选择结果类别“武器”或“防具”。
5. 点击重铸按钮。条件满足后立即扣除1张符并结算，成功页显示新装备；确认／关闭成功页只是关闭展示，不是再次确认扣费，也不能撤销结果。
6. 到背包查看新装备及卸下的灵石，需要时重新穿戴、镶嵌。

【A】入口来自 `packageUI` 原源码行1959–1960，`type_id == 1100` 时调用 `d_equipTransUI.show()`。重铸不是装备兑换活动，也不是铁匠铺的装备分解；它不占装备兑换的每周一次额度。

【A】原选择器要求品质至少为五星、未穿戴、位于白名单，并排除 `star_level == 1` 的六星装备。原选择器没有相同的锁定过滤，锁定装备即使显示在列表中，仍会被本地后端拒绝。【B】25级门槛在后端执行；不能把“可打开界面”理解成已经满足结算等级。

依据：[原背包入口](../analysis/evidence/lua_named/lua/ui/packageUI.lua.txt)、[原重铸界面](../analysis/evidence/lua_named/lua/ui/equipTransUI.lua.txt)，其中 `[L数字]` 是原Lua源码行号，不是反汇编文本的文件行号。

【A】输入与输出都取自原版 [item_exchange_config.csv](../analysis/configs/item_exchange_config.csv) 的第一行，二者名单相同。不能仅根据“五星”或“非VIP礼包”描述自行扩大范围。

【B】玩家只能指定类别，不能指定名称。服务端先按目标类别筛选，再排除原模板，通过 `secrets.choice` 等概率选取一个结果：

| 原装备 → 目标类别 | 结果数量 | 单件结果概率 |
|---|---:|---:|
| 武器 → 武器 | 4 | 25% |
| 武器 → 防具 | 5 | 20% |
| 防具 → 武器 | 5 | 20% |
| 防具 → 防具 | 4 | 25% |

例如火尖枪重铸为武器，只会得到混铁棍、芭蕉扇、九齿钯、乾坤拂尘之一；重铸为防具则从全部五件防具中选择。不存在法宝结果、同名结果、保底计数或累计概率机制。条件满足后的结算没有随机失败分支，随机的是装备名称。

【检查】专项验证遍历了十种输入 × 两种目标类别，共20组候选集合。等概率结论来自抽样实现，不是用少量随机结果估算出来的原服概率。

## 四、养成继承与灵石处理

| 数据 | 当前处理 | 依据／注意事项 |
|---|---|---|
| 强化等级 `level` | 保留 | 【A】原提示明确保留装备等级 |
| 打孔数 `drill_count` | 保留 | 【A】原提示明确保留打孔数 |
| 进阶等级 `advance_level` | 保留 | 【A】原提示明确保留升阶等级 |
| 进阶星数 `star_count` | 保留 | 【B】本地继承策略 |
| 当前注灵进度 `cur_spirit_count` | 保留 | 【B】跨武器／防具也直接继承进度值 |
| 封神标记 `reborn_bit` | 保留 | 【B】本地继承策略 |
| 铸造等级 `cast_level` | 保留 | 【B】按目标装备类别重算效果 |
| 六星标记 `star_level` | 后端保留 | 【检查】正常原UI不允许选六星，不能作为玩家可用功能承诺 |
| 镶嵌灵石 | 卸下回背包 | 【A】原提示要求自动卸下；本地实现见下文 |
| 装备模板 `type_id` | 改为随机结果模板 | 名称、类别、基础及成长属性随模板改变 |
| 装备实例 `id` | 分配新ID，删除旧实例 | 避免原客户端沿用旧模板缓存 |
| 穿戴位置 | 新装备保持空闲 | 输入原本必须未穿戴，`equip_pos` 归零 |
| 最终属性 `effect_value` | 重新计算 | 不直接复制旧攻击／防御数值 |

这里的“保留养成”是保留等级／阶段／进度字段，不是保证数值或战斗力不变。武器变成防具后，原攻击成长转换为新模板对应的防御成长；卸下灵石也会改变当前属性。

`detach_stones()` 对四个孔位逐一处理：若存在真实关联灵石实例，将其 `owner_id`、`equip_pos`、`equip_order` 清零，保留该灵石的其他数据；若旧档只有孔位等级、没有关联实例，则按**原装备类别**补回同等级灵石。武器／防具对应1090／1091。随后清空装备的四个 `stoneN_level` 字段。因此武器变防具不会把攻击灵石变成防御灵石。

依据：[equipment_crafting.py](../network_redirect/equipment_crafting.py) 的 `transform()`、`detach_stones()`；[equipment.py](../network_redirect/equipment.py) 的 `base_effect()`、`effect()`；[formation.py](../network_redirect/formation.py) 的 `prepare()`。

## 五、请求、结算和存档链路

请求使用原协议 **1225 `msg_item_transform`**：

| 字段 | 含义 |
|---|---|
| `serial_num` | 请求序号；参与缓存及过期校验 |
| `state` | 1＝武器，2＝防具 |
| `item_id` | 待重铸装备的实例ID，不是2001等模板ID |

线格式为 `serial_num=I,state=B,item_id=d`，见 [protocol_tables.json](../analysis/evidence/protocol_tables.json)。

当前链路为：`Backend.formation()` → `formation.settle()` → `equipment_crafting.settle()` → `transform()`。关键步骤：

1. 从临时角色副本读取目标并校验等级、空闲状态、装备类别、白名单和目标类别。
2. 构造候选池，扣除1张1100及配置元宝费用。
3. 必要时拆分历史叠加装备，卸下灵石，删除旧实例并创建新ID。
4. 用新模板重算装备与角色相关属性，生成物品变动、背包快照与结果事件，保存角色。
5. 返回事件 **124**：`result=0`、`item_id=新ID`、`old_item_id=旧ID`。背包更新在结果回调之前发送，原UI通过新ID查找结果。

可预期的校验失败走通用事件 **55** 的 `op_string` 提示，不要求客户端走原生 `eTransTip2/3/4` 分支。常见提示包括“尚未达到装备重铸等级”“已装备、锁定或专属物品不能消耗”“材料不足”“该装备不能重铸为指定类型”。拒绝时不会保存局部扣费结果。

【检查】同一后端实例中，同序号同请求命中响应缓存，最多保存256条阵容类请求；未命中且序号过期的请求拒绝。缓存驻留内存，不能表述为永久的跨重启交易日志。正常成功后旧装备ID已删除，用新请求序号重发旧装备ID也会被拒绝；装备结果本身已落库，重开数据库后仍存在。

## 七、发现的问题与修复建议

### 1. 六星装备前后端规则不一致（中优先级，已复现）

原 `equipTransUI.getTransformEquipsExcept()` 在源码行229排除 `star_level == 1`。本地 `transform()` 只检查模板品质五星、白名单和目标类别，没有检查六星标记。模板品质仍为五星的六星装备可绕过选择器，经协议1225成功重铸并保留六星状态。

影响：正常原UI玩家无法操作，但后端可以执行，导致规则边界不一致。已有总说明“保留六星”只能描述后端字段继承，不能证明原版支持六星重铸。

建议：如按原3.87选择器规则运行，在扣费前拒绝 `star_level` 非零的目标，并增加六星请求整笔拒绝验证；若要主动开放六星重铸，应同时明确新的玩法规则、修改选择器并验证六星养成效果，而不能只保留后端放行。

### 2. 历史叠加装备可能重复继承养成和返还灵石（高优先级，已复现）

触发条件：旧存档存在 `count > 1`、同时含强化／孔位／灵石信息的装备。正常新发装备按独立实例保存，不应产生这种结构。

原因：重铸直接调用 `equipment.split_one()`，它深拷贝养成及孔位字段给剩余叠加数量，然后仅卸下当前目标上的灵石。与 `dispose()` 不同，重铸没有先拒绝“带养成的叠加装备”这种有歧义的存档。

临时数据库复现：

1. 火尖枪 `count=2`、强化30级、开孔1、`stone1_level=3`，实际关联三级攻击灵石1颗。
2. 第一次重铸其中一件为防具，实际灵石回包；剩余火尖枪仍保留30级和三级孔位记录，但没有对应关联灵石。
3. 再重铸剩余火尖枪，旧档孔位补偿分支额外生成1颗三级攻击灵石。
4. 最终原有1颗变为2颗；复制的养成字段也被剩余装备保留。

建议：在扣费和拆分前检查叠加装备；只允许无养成、无孔位、无关联灵石的纯净堆叠拆分，遇到有歧义的旧档先拒绝并走专门整理／迁移流程。不要直接删除剩余装备的养成或灵石记录，因为缺少历史证据无法判断哪些投入真实存在。

### 3. 界面提示与规则配置仍有缺口（低优先级，静态检查）

25级限制和元宝费用来自后端配置，原重铸页没有对应的明确等级／费用展示；锁定装备的客户端过滤也弱于后端。现状由后端拒绝保护资源，体验上可能表现为“能看到／能选择，但点击后不能重铸”。建议同步展示等级、符数量、实际费用，并与服务端统一可选条件。

以上均为检查结果和建议，本次未实施修复。测试通过表示已有正常行为成立，不表示这些已复现问题已经解决。
