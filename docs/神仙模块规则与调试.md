## 【A】原版客户端规则与证据

下列行号是反汇编保留的原始 Lua 源码行号，不是生成 txt 的行号。完整模块及数值常量池保存在 [原版反汇编证据](../analysis/evidence/immortal_official_bytecode.txt)。数值指令中的常量索引不能当作字面数值。

### 列表和图鉴

- 【A】`lineupUI.create:845` 检查 `soulExchangeUI.g_self.isOpen`；`soulExchangeUI.initData:128–137` 从配置 15 读取 `adaptive_visible` 和各品质银币价格。
- 【A】精魄属于物品：`attach_type=5`、`item_base.main_type=15`；五法界魂 `main_type=11`；神仙魂魄走 1046。这三类不能混用。
- 【A】`lineupUI.pressHandBook` 设置 `ready_open_tag=4`，经 `other_functionUI.menuHandbookCallback` 请求图鉴；`runeUI.onGetHandbookResult` 收到 event 25 后展示。
- 【A】1044 按 `object_type` 下发 `first_send/label_count/label_list`，每条 `type_id/status`；1045 为单项状态更新。对象类型 4/5/6/15 分别对应神仙、物品、法术、宠物。
- 【A】`data.getHandbookStatus` 缺省返回 0；状态 1 显示灰色，2 显示彩色，大于 2 使用红色边框；客户端仍按 `book_hide`、品质等自身规则筛选。
- 【A】`data.lua:2300–2345`：1046 首片清空原魂魄缓存，续片追加；神仙魂魄属于类型总量，不是物品实例。

### 铭刻与升级

- 【A】`jpmkUI.show:68`：角色 38 级开放铭刻界面。`jpmkUI.create:283`：第二、第三槽可以飞升 6、12 次自动开启，也可铭刻随机开启；第四槽仅铭刻随机开启。界面最多四槽。
- 【A】原版说明：铭刻会随机顶替已有精魄或开新槽；未开槽增加幸运值，幸运值越高开槽概率越高；紫色优先替换同类型金色。金色 101xx、紫色 102xx，同系编号相差 100。
- 【A】不能铭刻同品质同类型精魄。紫色可以临时锁定，锁定仅对本次铭刻有效；协议锁定列表是**槽位索引数组**，不是物品 ID。最多锁定三槽。
- 【A】`ext_skill_lock_cost.csv`：锁 1/2/3 槽分别消耗 100/300/700 元宝。
- 【A】1311 字段为 `ext_skill_id/des_cortege_id/lock_list`；148 回传 `ext_skill_id/owner_id/object_type`；147 的 `result=0` 表示铭刻成功，触发原版面板重建。
- 【A】`jpmkUI:55–56,472–495`：最高 5 级；1→2、2→3、3→4、4→5 所需进度分别为 500、1000、1500、3000。升级材料为物品 10000 精魄石；每次最多 `min(500, 当前材料量, 本级剩余进度)`；进度存于 `prob_compen`。
- 【A】1322 提交精魄实例 ID 和 `cost_count`；146 的 `result=0` 触发升级刷新。`item_base` 中部分精魄的 `top_level=3` 与当前界面上限冲突，本实现采用实际运行的 jpmkUI 上限 5。
- 【A】精魄各级技能描述及效果参数沿用 `ext_skill.csv`，客户端可正确展示。

### 分解与转换

- 【A】列表分解入口：`lineupUI:1013–1016` → `data.getTransInfoByTypeid` → `smithUI.show`。`smithUI.pressConvert` 在分解页发 1074、`flag=3,count=1,num=次数,des_type=1,id_list={{id=实例ID}}`。

- 【A】`jpChangeUI:160–177`：转换发 1074、`flag=4`，每次一枚，`des_type` 是界面选择的目标物品类型。不能误用法术还原的 flag 5。
- 【A】`jingpo_transform.csv` 给出可转换源、目标组、最低角色等级 38、消耗转换丹 1342×1。严格限制目标属于源精魄的原版组。

### 界魂和收集

- 【A】界魂 1051 的 `item_id` 是物品实例，`item_type` 是界魂类型，`des_type=4`，`des_id` 是**神仙类型**，不是神仙实例。
- 【A】兑换目标必须已经拥有并列于 `adaptive_spirit_convert.csv`，品质和种族与界魂匹配；每枚目标魂魄所需界魂数量取 `need_count`。
- 【A】`soulExchangeUI.getExchangeMaxCount` 按材料、银币、999 上限和下次飞升魂魄缺口计算按钮次数，满足缺口后通常以 10 为批量上限；客户端保留该逻辑。服务端校验总量、比例及余额，并将 999 作为单包硬上限，不强制 UI 的便捷批次选择。
- 【A】event 21 `result=1,type_id,count` 走 `commonLayerUI.recvUsedItem`，再刷新兑换界面。先同步魂魄和材料，后发回调。
- 【A】收集 1305 查询；1306 的 `index/value` 为**组合编号/组合内位置**。158 数据为 `line_up[组合][位置]=0或1`，`flag` 为尚未激活的数量；157 包装在 `activate_data.line_up` 下。
- 【A】`collector_cortege.csv` 定义 14 组合、成员和奖励。奖励类型 1/2/3/4 为血量/攻击/防御/内力。原版确认提示要求消耗人参果；物品 ID 为 1002。

## 【B】缺失服务端规则的完整推测方案

配置位于 [immortal_rules.json](../server_config/immortal_rules.json)，明确 `mode=inferred`，版本 `2026-10-24-immortal-1`。加载时验证字段和取值，错误配置拒绝启动，不暗中降级。

| 项目 | 实现值与理由 |
| --- | --- |
| 模块开关 | `adaptive_visible=true`，开放原版已存在的精魄分页和界魂功能；不额外赠送任何材料 |
| 界魂银币价格 | 品质 3/4/5 每枚目标魂魄分别 1000/2000/5000；原包仅有价格读取协议，没有价格值，按品质递增 |
| 图鉴获得状态 | 全目录未获得为 1，曾获得为 2；不伪造大于 2 的红框状态。历史记录持久化，获得后消耗、替换也不熄灭；旧存档只能从当前持有内容补建，无法还原已遗失历史 |
| 初始槽位 | 默认 1；保留已解锁槽位，并依据飞升达到 6/12 自动补足至 2/3 |
| 随机开槽 | 未满四槽且无空槽时，概率 `min(100,10+幸运值)%`；失败增加 10 幸运值，上限 100；成功新增一槽并清零幸运值。原版只证实随幸运值提升，无法恢复原服概率曲线 |
| 替换顺序 | 同系紫色优先覆盖金色；否则先填已有空槽，再尝试开槽，失败在未锁槽位中等概率替换；被替换精魄销毁，不自动返还材料。原服未提供空槽与同系覆盖冲突时的优先级，采用此一致策略 |
| 全锁场景 | 一至三槽全部临时锁定且尚有可开槽位置时强制开一槽；四槽全部锁定不接受。避免出现收费却无可写入位置的请求；该分支无法由原服务端验证 |
| 铭刻实例 | 从堆叠拆出一枚，绑定神仙实例 ID、槽位，普通装备位置归零。材料奖励只合并未铭刻、未锁定、1 级且零进度的物品，防止转换、购买、分解奖励污染已铭刻实例 |
| 升级结算 | 每枚精魄石确定增加一点进度；满阈值升一级并清零。原界面存在进度和阈值，但没有服务端成功概率表，故不虚构失败概率；从 1 到 5 合计 6000 石 |
| 转换结果 | 虽 CSV 标有 `is_random=1`，现版 UI 明确让玩家选择目标并提交 `des_type`，因此按合法选择确定产物；新实例 1 级、零进度。对已铭刻/锁定源拒绝处理 |
| 分解保护 | 只接受未铭刻、未锁定且足量的原版精魄，按数量线性扣费返还；不额外退还历史升级消耗。仅实现精魄对应的分解组，不扩展为整个铁匠合成系统 |
| 收集激活 | 每位置消耗人参果 1 枚，要求持有对应神仙，不消耗神仙；重复激活拒绝。整组全激活后永久应用一次配表奖励。原客户端未给出材料数量和服务端叠加次序 |
| 收集加成顺序 | 配表奖励作为固定值加到各神仙已有阵容属性公式末尾，重新计算战力；每次由激活记录重算，避免重复累加。角色属性 87–90 同步 UI，重登也补发 |
| 请求保护 | 资源不足、非法目标、锁定实例、越界数量均不保存变更；先在独立角色副本结算并序列化，再持久化。会话内缓存最近 256 个请求结果，同序号同包重放不重复扣款，同序号不同包拒绝；登录重置会话缓存。这不是跨会话交易编号系统 |

## 实现位置与边界

- `network_redirect/immortal.py`：配表加载、图鉴历史、收集、铭刻、升级、兑换、分解、转换。
- `network_redirect/backend.py`：启动配置、协议路由、快照与回调排序、资源同步、存档和重放保护。
- `network_redirect/summon.py`：安全堆叠、魂魄分片、神仙初始槽位；`formation.py`：收集加成重算。
- `tests/test_immortal.py`：17 项神仙专项测试，包含随机分支控制、余额/锁定/非法参数、失败回滚、重登和重复请求。

**边界：** 本次完成上述界面、库存、成长和收集链路。仓库仍缺少完整战斗服务端；精魄技能描述沿用原版，但战斗内的触发、减伤、连击、反制等不能仅靠面板和库存处理验证，本次不声称已复原战斗引擎。原服概率、历史图鉴及服务端属性结算无法由客户端唯一反推，已明确归为【B】。未把本地推测冒充原版配置。
